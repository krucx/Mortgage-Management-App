Problem

Each page and hook re-implements loading, error, race guards and caching in its own style, and "what to refetch after a change" is a hand-fired window event that most writes forget.

Solution

Adopt TanStack Query as the server-state module and openapi-fetch as the client; api.ts shrinks to query keys and one invalidation rule per kind of change.

Wins

  • locality: invalidation declared once
  • leverage: one interface, 19 pages
  • delete ~245 lines of hand-rolled hooks
  • delete 51 hand-written URL builders
  • query params type-checked like bodies
  • pages testable behind a fake fetch

The generated types (pass 1, #04) already exist, so openapi-fetch is the natural next step from openapi-typescript, not a new direction.

Problem

The backend already makes a Preview by running the real change and rolling back, but every change still has twin routes, twin fetch functions, and a page that re-wires debounce, preview error, confirm dialog, saving flag and navigation by hand.

Solution

A change is declared once per tier: the backend serves Preview and save from one declaration; the frontend has one hook that owns the draft-to-save flow, so pages only supply the form and the confirm summary.

Wins

  • ~150 lines of preview routes become declarations
  • a new change gets Preview for free
  • "Save disabled while Preview errors" once
  • no JSON.stringify memo keys

Builds on 01: the hook is a useQuery for the Preview plus a useMutation for the save. Do not do it first.

Problem

Finding where a concept lives means scanning 32 names; nothing tells a reader that ledger, replay and changes belong together.

Solution

Move files into packages named after the glossary's sections; no interface changes.

Honest rating: this aids navigation, not depth. No module gains leverage or locality. Cheap and safe, so do it between features, not instead of 01.

Looked at, not worth it now

  • HTTP errors raised inside the changes modules (38 sites in changes.py, customer_changes.py). FastAPI is the only caller; turning them into domain errors moves code without concentrating it.
  • Replaying every Mortgage to sort Mortgages by Outstanding. One Lender's book; replay already runs once per request. Revisit only if lists get slow (ADR-0001 stands).
  • allocate.ts vs the backend's Overpayment check (pass 1, #05). The Payment Preview now gives the server's answer; allocate.ts is only a suggestion. Settled.

Top recommendation

01 · One server-state module for the frontend

It replaces hand-rolled code with tools built for exactly this job, fixes refetch-after-change for good, gives the frontend its first seam for page tests, and 02 sits on top of it.
