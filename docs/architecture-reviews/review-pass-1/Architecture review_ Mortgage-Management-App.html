Mortgage replay

replays(conn, ids) → .ledger(as_of) · .outstanding(on) · .redemption(on) · .project(…)

row → Terms non-Voided Allocations Term Changes closed_on / Forfeited exclude Redemption's final Payment compute_ledger
Problem
The pure ledger engine is deep and well tested, but turning a Mortgage's stored facts into a replay is spelled out by ~8 callers, each passing a different subset of compute_ledger's 9 parameters; the rules ("a Voided Payment is in no Ledger", "ignore the Redemption's own final Payment", "Forfeited settles the debt") live in whichever caller remembered them.
Solution
One Mortgage replay module that loads a set of Mortgages' facts once and answers Ledger, Outstanding, Redemption Amount and Projection questions; compute_ledger becomes its internal seam.
Wins
  • locality: replay rules live once
  • leverage: one interface, ~8 call sites
  • tests hit the replay without HTTP
  • delete terms_of, outstanding_of wrappers
  • no triple queries in load_mortgage
  • no N+1 in ready_to_redeem
Consistent with ADR-0001: the Ledger stays derived; this deepens how it is derived, it does not store anything.

Mortgage changes

1 · refuse: status, dates, ownership 2 · write rows 3 · replay every touched Mortgage (Overpayment → refusal) 4 · History entries, worded in one place

Preview = apply, snapshot, roll back, for all 8 changes

Problem
Three changes (edit, Term Change, Void) have an apply_* function that Preview can run; the other five keep their checks inline in route handlers. So the "is it Active", "does the replay still hold" and History steps are re-assembled per change, with different status codes and wording, and Payment, Redeem, Forfeit, Reopen can't be previewed.
Solution
Each change becomes one function in a Mortgage changes module that checks, writes, re-replays the Mortgages it touches and records History; route handlers and Preview both call it.
Wins
  • locality: invariants enforced once
  • Preview covers every change
  • "Callers check it first" disappears
  • History wording in one module
  • tests: one change, one interface
03

Projection as one replay that reports at chosen dates

Worth exploring in-process
  • backend/…/projections.py _series, baseline, project
  • backend/…/ledger.py compute_ledger, HypotheticalPayments
  • backend/…/mortgages.py quote_redemption

Before: 13 points × 2 replays + 2 more, per series

paid_off_on found by scanning for payment_id is None: couples Projection to how the Ledger marks hypothetical Payments

After: one pass, snapshots on the way

replay.project(dates, hypothetical) → snapshots

Problem
A Projection series replays the Mortgage from its start once per point, again per point for the Redemption Amount, then twice more; "paid off" and "coming Term Changes" are re-derived by scanning Ledger steps outside the engine.
Solution
The replay yields a snapshot (including the Redemption Amount if closed that day) at each requested date in one pass; Projection reads snapshots instead of re-running the engine.
Wins
  • Projection maths stays in the engine
  • no test_projections.py today: gains one interface
  • ~28 replays become 1

Natural follow-on to 01: the snapshot method lives on the Mortgage replay interface.

05

Payment Allocation rules live on one side of the seam

Speculative in-process
  • frontend/src/allocate.ts, frontend/src/pages/NewPaymentPage.tsx
  • backend/…/payments.py PaymentIn.allocations_add_up, check_no_overpayment

Before: two "too much?" rules

After: the Payment preview answers it

Problem
NewPaymentPage refuses amounts above Outstanding on the Payment date, but the backend's replay also refuses a back-dated Payment that makes a later Payment an overpayment; the client and server disagree on edge cases.
Solution
Once 02 exists, the Payment preview returns the refusal (or before/after); the page drops its own copy of the rule and keeps allocate.ts as a pure split suggestion.
Wins
  • one overpayment rule
  • Payment gets a before/after preview

Depends on 02; not worth doing alone.

Top recommendation

01 · Deepen the Mortgage replay

Every recent feature (Payments, Voids, Term Changes, Closure, Previews, Projections, Call List) re-assembled the same replay by hand, and the rules that make it correct are scattered across those callers; one interface concentrates them, gives tests a seam below HTTP, and is the base that 02, 03 and 05 build on.
