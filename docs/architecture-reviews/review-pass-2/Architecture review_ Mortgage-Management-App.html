Problem. Notice status rules sit in four places across three triggers. Each of the last three commits patched one edge (queue-on-read, days-before lowered, approve-first turned on).

Solution. A Notice queue module whose sync makes the unsent Notices match today and the current settings. Every trigger calls it. Transitions raise domain errors, not HTTP ones.

  • locality: Notice lifecycle in one module
  • settings changes stop needing special cases
  • approve/skip testable without HTTP
  • leverage: four triggers, one interface

Problem. The Mortgage replay is deep, but callers fan out around it. Counting Notices builds the full message text and replays each Notice's Mortgages, twice over.

Solution. call_list, the Notice builder and ready_to_redeem accept replays already built. Counting "Notices with something to send" is a Notice queue question that needs no message text.

  • ~4 replays per Mortgage become 1
  • Dashboard and Notices agree by construction
  • tests pass replays, skip HTTP

Consistent with ADR-0001: nothing is stored. Only how often the replay runs changes. Pairs naturally with 01.

Top recommendation

01 · One Notice queue module

It is the hottest code in the repo: the last three commits each patched one edge of the Notice lifecycle in a different place. A single sync turns those special cases into derived state, and it sets up 03 (shared replays) and 05 (settings change hooks).
