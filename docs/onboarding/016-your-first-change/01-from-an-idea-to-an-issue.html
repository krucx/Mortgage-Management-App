From an idea to an issue

A small feature still needs a clear boundary. Turn “change a future rate” into behavior tests can pin.

By the end: you can write a scoped issue with repo vocabulary, a triage label and an ADR decision.

The problem

Meera's bangles have a Term Change recorded 12 Oct to take effect 25 Oct. The sample book is served on 19 Oct. If the date or rate is wrong, the current screen offers Remove and a separate add. A focused edit should preserve the record and show exactly what changed.

The idea

Start with the user's observable need, then specify allowed states, refusals and History. Read the glossary's Avoid list before naming the issue. “Amendment” and “rate edit” are avoided terms here; use Edit a Term Change.

Flow

# Edit a coming Term Change

Label: ready-for-agent

## Need
Edit a coming Term Change in place so a corrected date or Terms keeps its identity.

## Rules
- Only a coming Term Change on an Active Mortgage can be edited.
- Require an Accrual Date, no date clash, and at least one changed field.
- Record each changed field in History; Preview uses the same validation.

## Language and decision
Use “Term Change” from Documentation/GLOSSARY.md. The ADR test fails: this is reversible,
does not shape system quality, and has no consequential alternative.

That example is sufficiently specified for ready-for-agent.
