The change, test-first

The backend owns the rule. Start with a failing API test, then add the smallest change function and save route.

By the end: you can implement a tested edit from the API down.

The problem

A date must be an Accrual Date, must still be coming, and cannot collide with another Term Change. An edit that has already taken effect would rewrite past interest. The nearest examples are adding and removing a Term Change.

The idea

Keep refusal rules in changes.py so a route and Preview can call the same function. API tests in tests/test_term_changes.py use the app's fixed 20 Apr 2026 clock. That test cast is different from the sample book's 19 Oct date (trap #17).

Code to compare

Mirror the checks in the add path, but find the existing row by both ids and refuse if its date is today or earlier. Recompute what differs against Terms at the chosen effective date; then update the row and record History.

Run-through: Meera's bangles

From the practice branch, add one API test at a time. Begin by moving 25 Oct to 25 Nov; change the rate to 1% (100 basis points). Then add refusal tests for a non-Accrual Date, a clashing date, no effective difference, a Term Change effective today, and one already in the past. Run each specific test before implementing.

Nuance: check_replays

The edit path calls check_replays like other Ledger changes. For an ordinary coming Term Change this check cannot trip; keep the shared sequence, but don't invent a test that claims to exercise an impossible refusal. Chapter 006 · Lesson 5 explains the route checklist.

Why is an edit of a Term Change effective today refused?

A Term Change applies from its Accrual Date onward. Once that date arrives, add a later Term Change to change future Terms.
