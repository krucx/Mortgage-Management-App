Chapter 014 · Lesson 1

The app in Docker

On most laptops the app runs in Docker: one image, one Compose service, the Lender's data in two folders outside it. This lesson has you run your own code that way, on a copy of the sample book, and look inside when something is off.

By the end you can run your own code in Docker on scratch data, and debug it with ps, logs and exec.

The problem

The Lender has one laptop. It could be a Mac or a Windows PC. Nobody on it knows what Python, Node.js or a virtual environment is, and nobody should have to. The app has to install as one thing, start as one thing, update as one thing, and keep the Lender's records safe through all of it.

The obvious design, "install Python and Node and run the two servers", fails here three ways. It needs a different installer per operating system. Each install drifts (a different Python, a package that failed halfway). And the records end up wherever the code happens to be, so replacing the code risks replacing them.

You, the developer, have the opposite problem. You need to run your code exactly the way the Lender runs the released code, and you must never point it at real records by accident.

The idea

Ship the app as one Docker image, and run it with Docker Compose. The image holds the backend, Python, every package and the built screens. Compose starts it with the database folder and the Backup folder mounted from the laptop's own disk, so the records live outside the container and survive any update. The Lender's Compose file pulls the published image. A second, development file builds it from your folder instead (ADR 0004, ADR 0013).

Think of the image as a sealed appliance and the two folders as the Lender's filing cabinet beside it. Swap the appliance for a newer model and the cabinet stays exactly where it was.

A correction to the plan. This chapter was planned (issue #202) when Docker ran two services: nginx serving the screens and passing /api to the backend, from frontend/Dockerfile and frontend/nginx.conf. Commit 3137302 (ADR 0013) replaced them with one image built by the root Dockerfile, and one service, app. Those files are gone. If you meet backend, frontend or nginx in an old issue or an old version's folder, that's what it means.

The flow

Notice that the only things that cross the container's wall are two folders and one port. Everything you'll debug in this lesson is one of those three.

The code

The image

  1. A multi-stage build: this stage exists only to produce files; nothing of Node ends up in the final image. $BUILDPLATFORM runs it on the building machine's own CPU. The built screens are the same bytes on every platform, so they're built once, never under slow arm64 emulation (ADR 0013).
  2. The two package files are copied first, alone, so Docker can reuse this layer's node_modules until they change. Copying the rest after keeps a screen edit from reinstalling every package.
  1. The zip program writes password-protected Backups. Without Docker there's no such program, which is why Backups are plain zips there (chapter 015).
  2. The first stage's built screens land in /app/screens.

Line 33 is the whole contract between the image and the backend: three environment variables. DATA_DIR and BACKUP_DIR are the two mount points; SCREENS_DIR tells the backend to serve the screens too (lesson 2). The backend reads them through create_app's module-level call (chapter 010, lesson 1). Line 36 binds 0.0.0.0: inside a container that's needed for the port to be reachable at all, and it's safe because of what Compose does next.

The Lender's Compose file

  1. The published image on Docker Hub. ${APP_VERSION:-latest} is Compose's shell-style fallback: APP_VERSION if set and not empty, else latest.
  2. The time zone decides every business date: when "today" changes, and so every Accrual Date and every day of Interest to Date.
  3. Published on 127.0.0.1 only: reachable from this laptop, never from the café's Wi-Fi.

Line 14's ${DATA_DIR:?message} means "this variable is required: stop with this message if it's missing". Compose fills variables from your shell first and from a .env file beside the Compose file second. .env.example is the template the README tells the Lender to copy: DATA_DIR, BACKUP_DIR, BACKUP_PASSWORD, TZ, APP_PORT and APP_VERSION, each with a comment.

The development overlay

  1. Given a second -f file, Compose merges it over the first, key by key. This one adds a build from the repo root's Dockerfile.
  2. …and gives the result its own name. Without line 7 the build would be tagged krucx11/mortgage-management-app:latest, quietly replacing the published image you'd pulled. pull_policy: build says never try to pull this name, always build it.

Run-through: your code, on a copy of the book

You'll run the dev build on a copy of your served sample book (chapter 002, lesson 4), so lesson 2 can compare it with the book itself. Like chapter 002, it uses its own project name (-p mortgage-dev) and port (8081), so it never touches a copy of the app already running from this folder on 8080. From the repo root:

export COPY=$(mktemp -d)
cp -R "$BOOK/data" "$COPY/" && mkdir "$COPY/backups"

# Every compose command below starts with these three variables. Every one.
DATA_DIR="$COPY/data" BACKUP_DIR="$COPY/backups" APP_PORT=8081 \
  docker compose -p mortgage-dev -f docker-compose.yml -f docker-compose.dev.yml up -d --build

The first build takes a few minutes (it runs npm ci and uv sync); later ones reuse the cached layers and take seconds. Then look:

Nuances

Leaving the variables out

Predict: you rebuild after a screen change and, in a hurry, type docker compose -p mortgage-dev -f docker-compose.yml -f docker-compose.dev.yml up -d --build without DATA_DIR and BACKUP_DIR. What happens?

It depends on whether there's a .env beside the Compose file. In a folder without one, Compose refuses before doing anything, with line 14's and 15's messages:

error while interpolating services.app.volumes.[]: required variable DATA_DIR is missing a value: Set DATA_DIR in .env
error while interpolating services.app.volumes.[]: required variable BACKUP_DIR is missing a value: Set BACKUP_DIR in .env

With a .env there (the README's "Anywhere with Docker" has the Lender copy .env.example to one, and a developer who runs the app for real from their clone has one too), it says nothing. It takes .env's folders and starts your unreleased build on them. scripts/run_throughs.sh checks this with config, which only prints: beside this repo's .env, both mounts resolved to "a folder from .env".

That's trap #12's second half, and why trap #9 follows from it: the app migrates whatever DATA_DIR it's given, on start, with no way back but a Backup (chapter 010, lesson 5). Pass the scratch variables on every compose command, including logs, exec, stop and a rebuild of one service. Each one re-reads the configuration.

Leaving the dev file out

Predict: after your dev build is running, you type the variables and plain docker compose -p mortgage-dev up -d, without -f docker-compose.dev.yml. What runs now?

The published image, in place of yours. Compose sees the service's image change to krucx11/mortgage-management-app:latest and recreates the container:

 Container mortgage-dev-app-1 Recreated
mortgage-dev-app-1 krucx11/mortgage-management-app:latest Up Less than a second

And latest means the latest you pulled, not the latest released. On the machine this chapter was checked on, it was 3.4.0 while the code said 3.4.1, and because the plain file sets CHECK_FOR_UPDATES to "true", GET /api/update answered {"running":"3.4.0","available":{"version":"3.4.1",…}}: the banner offered an update. Adding the dev file back (up -d with both files) put mortgage-management-app:dev back, answering {"running":"3.4.1","available":null}.

That's trap #12's first half. The dev build never replaced the pulled image (line 7's own name), so nothing was lost, but nothing of yours was running either.

The rest, briefly

  • restart: unless-stopped brings the app back whenever Docker Desktop starts, unless someone stopped it. The Lender never starts it by hand. A container you stop stays stopped across a restart.
  • The upload cap is in the backend now. nginx used to refuse bodies over 20 MB. Since one image, platform/upload_limit.py does it, in both modes: a 21 MB photo got {"detail":"The file is too large (over 20 MB)."} with HTTP 413, and nothing was stored.
  • Two projects can share the :dev name. The image name doesn't include the project. If this folder also runs the app for real from a dev build (project mortgage-management-app), your --build retags mortgage-management-app:dev. The running container keeps the image it started with; its next up --build rebuilds anyway.
  • CI checks the image too. The image job in test.yml builds it, runs it on empty folders, checks that / is no-cache and a hashed /assets/ script is immutable, and that /api/backups answers. The release runs it first, so a broken image is never published (chapter 015).

Quiz

Why does docker-compose.dev.yml give the image its own name?

Without line 7, the build would take the plain file's name, krucx11/mortgage-management-app:latest, and overwrite the pulled image locally. Nothing here pushes to Docker Hub. The port comes from APP_PORT, not the image's name.

The same copy of the book shows Meera's chain at ₹83,333 in serve.py and ₹84,293 in Docker. Why?

serve.py passes today=lambda: THE_DAY; the image runs the module-level app, whose today is date.today. Eighteen more days of Interest to Date make the difference. Both run the same code, and a time zone moves the date by at most a day.

Where do the database and photos live while the app runs in Docker?

Line 14 bind-mounts the host folder DATA_DIR at /data. The image holds code and screens only, so replacing it never touches the records (ADR 0004). A named Docker volume would hide them from the Lender and their Backups.
