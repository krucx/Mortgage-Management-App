Chapter 014 · Lesson 4

Each version in its own folder

An update replaces the code the Lender's business runs on, on a PC nobody is watching. This lesson shows how Setup makes that safe: the new version goes in a folder of its own, starts beside the old one, and becomes "the app" only once it answers. Then it shows the one thing Setup can't undo.

By the end you can explain how Setup switches versions, and what it can and can't undo.

The problem

A Tuesday morning. Arjun Patel is at the counter to pay towards his ruby ring. The Lender sees the update banner, presses Install now, and while Setup works, Arjun waits. Suppose the update fails halfway: the download breaks, uv sync can't reach the internet, or the new version won't start.

The way Setup used to work, that was a disaster. It replaced the code in MortgageManagement\app, then installed into it. A failure partway left half a new version and none of the old one. The Lender couldn't record Arjun's Payment, and couldn't go back (ADR 0009).

The idea

Never touch the running version. Put the new one in versions\<version>, start it, and only once it answers, point app at it. app is a Windows directory junction: a folder entry that points at another folder, like a symlink. Everything that names app (the Desktop shortcut, the mortgage-management:// link, app\.env, app\windows\Uninstall.bat) keeps working through every update, and follows the junction to whichever version runs.

It's how a theatre swaps a lead actor: the understudy is dressed and waiting in the wings, and walks on only when ready. If they never get ready, the original actor never left the stage.

The flow

Notice how short the gap is. X runs during the download and the install, which are the slow, failure-prone steps. It stops only for the seconds between "Y is ready to start" and "Y answers".

The code

The junction

  1. [IO.Directory]::Delete with no "recursive" flag removes the junction itself, never what it points at. The code never uses Remove-Item -Recurse on app: on Windows PowerShell 5.1 that has been known to walk into the junction and delete what it points at. The uninstaller removes the junction the same careful way first, at its line 190, before deleting the install folder.
  2. An install from before versions had folders: the code is in app itself. The next update moves it into versions\<its version> (Move-ToVersionsLayout) and puts a junction in its place.

The switch

  1. Before anything stops: are the data and Backup folders outside the version folders? See the nuances.
  2. When both versions run in Docker, X isn't stopped first: Y's docker compose up -d --remove-orphans replaces X's container in one step (below). Otherwise X is stopped, and Stop-RunningApp reports whether it was running.

$AppDir is the folder of the code running this script: Y's. Wait-Version asks http://127.0.0.1:<port>/api/backups for up to $StartMinutes (7) minutes, enough for Docker Desktop to start or a database update to take its Backup first.

  1. A mortgage-backup-*-before-update*.zip written since the switch began means Y got as far as migrating the database (chapter 010, lesson 5: the app takes that Backup just before it migrates).
  2. X is started again only if it was running. A Lender who'd closed the app's window before updating doesn't get it reopened.

Then throw goes up to setup.ps1, which removes Y's folder (unless the junction already points at it) and prints "Update failed; still on X." followed by the reason.

Docker: the same project, each version's own images

  1. Compose names a project after its folder unless told otherwise. Before versions had folders, every install's folder was app, so the project was app. Forcing that name means X's containers (run from versions\X) and Y's (from versions\Y) are the same project, so Y's up replaces X's.
  2. Each version runs its own release's image (krucx11/mortgage-management-app:3.4.1), not :latest. Going back to X runs X's image again, not whatever latest is now. "which Docker images a version runs" pins all three lines.
  3. --remove-orphans removes the project's containers for services this Compose file doesn't have. Versions before 3.4.0 had two services, backend and frontend; without this flag, switching to a one-image version would leave the old frontend container holding port 8080 (ADR 0013). "switching versions with Docker" pins it, both ways.

Nuances

When Y fails

Predict: suppose Y has a database migration. It starts, takes its -before-update Backup, migrates the database, and then crashes before answering. What does Setup do, and what state is the Lender left in?

After 7 minutes Wait-Version gives up. The catch finds the Backup Y took (Find-UpdateBackup), stops Y, leaves the junction on X (it never moved), and starts X again. Then it throws, and the Lender reads, in Setup's window (the file name is an example):

Setup stopped: Update failed; still on 3.4.0. Version 3.4.1 did not start within 7 minutes. It had already updated the database, so the version before it may not start on it; if it doesn't, restore C:\Users\…\backups\mortgage-backup-2026-11-10-0930-before-update.zip (see Backups in the README).

X probably won't start: it finds a database "from a newer version of the app" and refuses (trap #9). A migrated database can't be un-migrated. So Setup names the exact Backup to restore, and leaves restoring it to the Lender. Pester's "says which Backup to restore when the new version had already updated the database" pins the message.

Why not restore it automatically? ADR 0009 rejected that "for now": Setup would change the Lender's data on its own, and with Docker the Backups are password zips Setup can't open. Restoring a Backup is chapter 015's.

The rest, briefly

  • The data must live outside the version folders. Assert-DataOutside (common.ps1 line 121) stops the update if DATA_DIR or BACKUP_DIR is inside the running version's folder, or relative (which would mean inside whichever version runs). Otherwise the switch would leave the database behind in X's folder, and Y would start on an empty one. "is left as it is when its data folder is inside the app folder" pins it.
  • Only two versions are kept: the running one and the one before it, to go back to. Select-OldVersions picks the rest for removal, but never a folder that holds the data or Backup folder. A folder that won't delete (Windows still has a file open) is reported and left for next time.
  • Each version gets a copy of the .env before it (Copy-EnvForward), and X's is left as it was. Going back is just pointing app at X again: nothing in X needs changing. "switches to it once it answers, with the same .env, and the old one's left as it was" pins it.
  • A failure before the switch changes nothing. If the download or uv sync fails, X was never stopped: "leaves the old version running, untouched, when installing the new one fails" asserts Stop-RunningApp ran zero times.
  • Why the junction, not new paths? ADR 0009 rejected rewriting the shortcut and link at each switch: every path in the docs (app\.env, app\windows) would change, Docker would need an explicit project name and --env-file, and Uninstall.bat would move with each version.

Quiz

When does app start pointing at the new version?

Set-AppJunction is the last line of the try, after Wait-Version returned true. Until then, everything that goes through app (the shortcut, the link) still reaches the old version, which is why a failure anywhere earlier leaves the Lender exactly as they were.

An update fails after the new version migrated the database. What does Setup do with the Backup?

ADR 0009 chose to name the -before-update Backup and not restore it automatically: Setup would be changing the Lender's data on its own, and Docker's Backups are password zips. Deleting it would throw away the only way back.

Why is the Compose project always called app?

Compose names a project after its folder, and X and Y live in different folders. With the same project name, Y's up -d --remove-orphans replaces X's containers instead of starting a second app that fights for port 8080. app is also the name older installs already had. The image's name comes from the Compose file.
