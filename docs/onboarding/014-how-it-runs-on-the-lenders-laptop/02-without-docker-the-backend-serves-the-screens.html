Chapter 014 · Lesson 2

Without Docker: the backend serves the screens

Some Lenders' PCs can't run Docker. There the app is one Python process that serves the API and the built screens from the same port. Since ADR 0013, Docker runs that same process too. This lesson shows the twenty lines that do it, and has you check, with curl, that both ways cache alike.

By the end you can serve the built screens from the backend, and check that both modes cache the same way.

The problem

Docker Desktop needs virtualisation switched on, a recent Windows, and often admin rights to install. On some PCs it never works. The app still has to run there, from one double-click, with nothing a Lender can't install.

The screens are a React app: npm run build turns them into plain files in frontend/dist (an index.html, hashed scripts in assets/, the service worker sw.js, the manifest). Something has to send those files to the browser, and send /api/… to the backend. In development that's Vite (chapter 002, lesson 5). On the Lender's PC it used to be vite preview, which meant Node.js and some 220 MB of node_modules on the laptop, installed through winget, the step that most often failed (ADR 0010).

And whatever serves the files decides how the browser caches them. Get that wrong and the installed app keeps showing last month's screens after an update (chapter 012, lesson 6).

The idea

The backend serves the built screens itself, at every path that isn't /api, when it's told where they are (SCREENS_DIR). One process, one origin, nothing to proxy, no Node.js. Pages and the service worker are sent "check every time"; the hashed files "keep a year". Docker's image sets SCREENS_DIR too, so both modes serve the app with the same code (ADR 0013).

The flow

Notice the two 404 branches. Without them, a typo'd API path or a missing script would get index.html with a 200, and the frontend would try to parse a web page as JSON or JavaScript.

The code

no-cache doesn't mean "don't cache". It means "you may keep it, but ask me before using it", so the browser sends a cheap conditional request and gets the new index.html the moment there is one. immutable with a year's max-age means "never ask again". That's safe only because Vite names each built script after a hash of its contents (index-DJTOgnFd.js): a changed script is a new name, which the new index.html points at. (MDN: Cache-Control.)

  1. {path:path} is a Starlette path parameter that matches the rest of the URL, slashes included. HEAD too, so curl -I works. include_in_schema=False keeps it out of openapi.json, and so out of the frontend's generated types (chapter 011, lesson 1).
  2. An unknown /api/… path falls through to here (no API route took it). It must stay a JSON 404, the same answer FastAPI gives without screens.
  3. resolve() turns ../ into a real path, and is_relative_to(root) refuses anything that ends up outside the screens folder. Checked: with a secret.txt beside the folder, /../secret.txt, /..%2Fsecret.txt and /%2E%2E/secret.txt all got the app's index.html, never the file.
  4. Any other path is a page of the app (/mortgages/2, /payments/new). The browser gets index.html, and React's router reads the path and draws that page (chapter 012, lesson 1).

Line 35 is the whole caching policy: under assets/ kept a year, everything else checked every time. That "everything else" includes sw.js, registerSW.js, the workbox-*.js runtime and manifest.webmanifest, which sit at the top of dist/. The check-yourself page breaks this line.

Starlette tries routes in the order they were added, so the catch-all goes in after every include_router. Added first, it would answer /api/customers with a 404. Without SCREENS_DIR (as in uvicorn --reload during development, or every test but test_screens.py), there's no catch-all and only the API is served. You met the rest of create_app in chapter 010, lesson 1.

Nuances

The old two-server mismatch is gone

Before ADR 0013, Docker's screens came from nginx, whose add_header lines had to match screens.py by hand, and no test compared them. That gap was filed while planning this chapter as #117; it closed when nginx went. The plan for this lesson was to show that gap. It no longer exists: screens.py is the only place the headers are set.

The retired trap #13 was the risk of keeping two servers' HTTP headers in sync. ADR 0013 removed that second path. The browser's HTTP cache and the service worker's own cache still follow separate rules: HTTP headers come from screens.py, while vite.config.ts defines the service worker's cache (chapter 012, lesson 6). If sw.js were kept a year, the browser would not fetch the new service worker and its precache list until the year was up. tests/test_screens.py pins the HTTP headers:

A stopped backend

Predict: stop each one (the variables, then docker compose -p mortgage-dev -f … -f … stop app; and Ctrl-C serve.py), then curl -sS http://127.0.0.1:<port>/api/customers. What does each answer?

Nothing, both times:

curl: (7) Failed to connect to 127.0.0.1 port 8081 after 0 ms: Couldn't connect to server
curl: (7) Failed to connect to 127.0.0.1 port 8765 after 0 ms: Couldn't connect to server

The plan for this lesson expected a 502 from Docker, because nginx stayed up when the backend stopped and answered "Bad Gateway" for it. With one container there's no one left to answer. The 502 lives on in development only: Vite's proxy answers 502 when nothing is on port 8000.

StartGate treats both as stopped: a failed fetch, or any status of 500 or more (chapter 012, lesson 6). StartGate.test.tsx's "a 502 from a proxy in front of a stopped backend counts as stopped" pins the second, since #116 was closed (chapter 013, lesson 5). It still matters, for Vite, and for a Lender whose PWA was installed from an older version.

The rest, briefly

  • 127.0.0.1, not localhost. On Windows (and macOS) localhost may resolve to IPv6 ::1 first, where uvicorn bound to 127.0.0.1 isn't listening. The Windows scripts probe 127.0.0.1 for that reason (run.ps1 line 51 says so). Docker publishes on 127.0.0.1 too (lesson 1).
  • Why not something else? ADR 0010 rejected shipping node_modules with vite preview (220 MB, per platform, still Node), a tiny node:http server (still Node, plus a hand-written /api proxy carrying 20 MB uploads), a bundled Caddy or nginx for Windows (a binary to update and get past SmartScreen), and Python's http.server or PowerShell's HttpListener (another process and another proxy). The backend was already there and already on the right port.
  • Without Docker, the screens must be built. A release's ready-built download has frontend/dist in it; run.ps1 refuses to start without frontend\dist\index.html ("The app screens are not built: run Setup again."). Lesson 3 shows where it comes from.

Quiz

Why is serve_screens called after every include_router?

Starlette tries routes in the order they were added; /{path:path} matches everything, so added first it would answer every API path. Leaving it out of the schema is include_in_schema=False's job, and the folder is only read per request.

Why may /assets/index-DJTOgnFd.js be kept a year, but not /sw.js?

Vite puts a hash of the contents in each built file's name, so a new version is a new name, which the always-checked index.html points at. sw.js keeps its name across releases, so it must be checked each time. Releases do change assets/, by adding new names.

With the backend stopped, what does curl /api/customers get on the Docker port today?

Since ADR 0013 the container is the backend, so stopping it leaves nothing on the port. The 502 came from nginx, before; now only Vite's dev proxy gives one. curl has no service worker; and the service worker never caches /api/.
