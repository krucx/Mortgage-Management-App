Chapter 006 · Check yourself

Check yourself

Questions mixed from all five lessons: which step refuses it, 409 or 422, what a History entry records, what a Preview saves. Then delete one line from edit_mortgage, and watch the refusal, the History and the Preview fail together.

Quiz

1. On the served book (19 Oct), the Lender asks for a Term Change on the bangles from 19 Oct. What's the answer?

Line 379 of add_term_change needs both "today or later" and an Accrual Date. The bangles accrue on the 25th, so it's "422 A Term Change starts on an Accrual Date, today or later (the next is 25 Oct 2026)". The 409 only comes for the same date as an existing one. From scripts/run_throughs.py, section 99. Lesson 1.

2. Someone deletes conn.rollback() from _preview. The Lender Previews a Payment. What is saved?

The Preview route opened the connection with engine.connect(), and closing it rolls back anything uncommitted. All 607 tests still pass. The real guard is never using engine.begin() in a Preview; making _preview commit breaks 13 tests. Lesson 4.

3. A trace. The Lender lowers Meera's chain to ₹1,000. The refusal names her 10 Dec 2025 Payment of ₹1,600. What did it say was owed then?

On 10 Dec, ₹20 of interest is added for the month from 10 Nov, and the new month's Interest to Date already has one day (today always counts): ₹0.67, rounded to ₹1. ₹1,000 + ₹20 + ₹1 = ₹1,021, less than ₹1,600, so Overpayment. Lesson 2.

4. In the bangles' History you find one row: action term_change_removed, no field, note "from 25 Oct 2026". What happened?

remove_term_change records no fields, just the date in its note. A Preview leaves no History: it's rolled back. Taking effect isn't a change at all; nothing is recorded. From scripts/run_throughs.py, section 99, on a copy. Lesson 3.

5. A Void is sent with the reason " " (just spaces). Which part refuses it?

VoidIn.tidy strips the reason and raises "A reason is needed", so FastAPI answers 422 with a list detail before post_void calls anything. A rule about one field's shape belongs on the model. Lessons 1 and 5.

6. A trace. Meera's chain owes ₹83,333 on 19 Oct. The Lender Previews a cash Payment of ₹83,333 to it. Which is true of the Preview?

Paying exactly the Outstanding Redeems in the same request (trap #3), so the "after" side has a closure of kind redeemed. Paid in cash, the sum appears in cash for the Cash Limit's warning. Nothing is saved. Lesson 4.

7. Which of these changes never calls check_replays?

void_payment calls it, although it can't trip today. forfeit calls it at line 757. A Collateral Value isn't a fact any Ledger is replayed from, so set_collateral has nothing to check. Lessons 2 and 5.

8. The Lender Reopens the coin. In what order do the new History rows appear, newest first?

reopen calls void_payment, which records its own voided row first; reopen records reopened last. Newest first, reopened is at the top. Lessons 2 and 3.

Hands-on: delete the check from edit_mortgage

You'll remove the one line that checks an edit by replaying it. Work from the repo root. This touches only source code, never data.

  1. Run all the backend tests. All 607 pass:

    cd backend && uv run pytest -q

  2. Open backend/src/mortgage_backend/lending/changes.py at line 468, in edit_mortgage, and delete this line:

        check_replays(conn, [mortgage_row(conn, mortgage_id)], today)

  3. Predict before you run: which tests fail? Think about all three ideas of this chapter. Which test checks the refusal itself? Which checks that a refused edit leaves no History? And which checks a Preview of an edit? Write your guess down.

    uv run pytest -q

Check your prediction.

Exactly 4 fail, 603 pass (checked at commit d6a92ab):

  • test_changes.py::test_an_edit_that_would_make_a_payment_too_large_is_refused
  • test_changes.py::test_a_refused_change_records_no_history
  • test_corrections.py::test_an_edit_that_would_leave_a_payment_too_large_is_refused
  • test_previews.py::test_an_edit_that_would_be_refused_cannot_be_previewed

One missing line, and all three of the chapter's ideas fail together:

  • The refusal. The first and third tests make an edit that leaves a Payment too large, once by calling edit_mortgage directly and once through PUT /api/mortgages/{id}. Without the check, the edit simply saves.
  • The History. test_a_refused_change_records_no_history makes the same edit and expects no edited entry. Now the edit isn't refused, so it reaches audit.record, and the History says the Mortgage was edited.
  • The Preview. test_an_edit_that_would_be_refused_cannot_be_previewed expects a 422 from /edit-preview. The Preview runs the same edit_mortgage, so it lost its refusal too. Nobody touched previews.py (trap #5).

Notice what didn't fail: every test of an edit that should save. A missing check makes the app accept too much, which only a test of a refusal can catch. That's why each change has tests for its refusals as well as its saves.

Recap

  • Every change to a Mortgage or Payment is one function in lending/changes.py: refuse (409 for a state that blocks it, 422 for a request that can't stand) → write → check → History. Its route only parses, calls and answers, inside one engine.begin() transaction, so any refusal saves nothing (lesson 1).
  • check_replays writes first and replays after, because every figure is replayed from stored facts. It refuses if any Payment is now larger than what was owed on its date, naming the first one. Pass the row as it is after the write (lesson 2).
  • History is append-only, one row per changed field, written by each change function itself as its last step, so a refused change leaves none. A Mortgage's History includes its Payments'; every entry shows the Mortgage's current name (lesson 3).
  • A Preview runs the real change inside engine.connect(), reads before and after, and rolls back, so it's refused exactly when saving would be (trap #5). The routes are hand-written on purpose; the rules live once (lesson 4, ADR 0007).
  • A new change needs a request model, a change function, a History Action, a save route, a Preview route, tests at both levels, and regenerated types (lesson 5).

Keep the routes sheet open when you work on changes: it now has every save and Preview route, with its refusals and History Action. The traps sheet marks #5 as this chapter's.
