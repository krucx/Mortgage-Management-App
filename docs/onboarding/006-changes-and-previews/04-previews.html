Chapter 006 · Lesson 4

Previews: make it, then roll it back

Before the Lender saves a change, the page shows what it would do: what's owed before and after, the Projection, and the Ledger steps that move. This lesson shows how previews.py gets those figures without a copy of a single rule.

By the end you can say exactly what a Preview runs, and why it is refused exactly when saving would be.

The problem

The Lender is about to remove the bangles' coming 1.5% Term Change. What would that cost Meera over the next year? Or Meera hands over ₹83,333 by UPI for her chain: will that close it, or leave something owing? The Lender wants to see the answer before pressing Save.

The obvious design is a separate "what if" function for each change: take the request, work out the new figures in memory, and return them. Picture preview_payment doing its own version of record_payment's checks, its own version of "does this Redeem?", its own version of the Closure. Every rule now lives twice. The day someone fixes a bug in record_payment and forgets the copy, the Preview and the save disagree. The Lender is shown a Preview, presses Save, and gets a refusal, or gets different figures from the ones they agreed with the Customer.

The idea

A Preview makes the real change, inside a transaction, by calling the very same change function the save route calls. It reads every figure it needs while the change is in place, then rolls the transaction back. Nothing is saved, and there is no second copy of any rule.

That gives the glossary's promise for free: a Preview is refused exactly when saving would be, because it is the save, up to the moment of committing.

Trap #5, owned here. Previews run the real change and roll it back. So a bug in a change shows up in its Preview too, and a refusal you see in a Preview is the save's refusal. When a Preview looks wrong, debug the change function (in changes.py, payments/recording.py, lending/closing.py or collateral/), not previews.py. See the traps sheet.

The flow

Notice that the change function even writes History during a Preview. It is rolled back with everything else, which is how the tests check that nothing was saved.

The code

1. The heart: _preview

  1. change is any function that takes no arguments. Each route passes a lambda that calls one change function with the route's own arguments. _preview doesn't know or care which change it is.
  2. before_change and cash_sums work out which sums the change would write in cash, so the page can warn about the Cash Limit. Chapter 007, lesson 4 owns them; here they're just two more reads around the change.
  3. The real change. If it refuses, its HTTPException passes straight up through _preview and the route, and the page gets the save's own 409 or 422.
  4. finally runs whether or not the change raised, so the transaction is always undone.

2. A Preview route

  1. The same request model as post_payment, so the page sends the Preview and the save the same body.
  2. engine.connect(), not engine.begin(). A SQLAlchemy connection starts a transaction by itself on its first query, and connect() never commits it: closing the connection rolls back anything left. Compare post_payment, which uses engine.begin() and commits.
  3. The same call post_payment makes.

Every other Preview route has this shape. Here's the one you'll use in the run-through:

The save is DELETE /api/mortgages/{mortgage_id}/term-changes/{change_id}. A Preview is always a POST to a path ending in preview, because it computes something new for you rather than changing anything.

3. What a Preview reads: _snapshot

  1. The Projection with no further Payments (chapter 004, lesson 5), only for an Active Mortgage. A closed one has nothing to project.
  2. The whole Ledger up to today, kept to compare before with after.
  3. The Closure (chapter 005, lesson 4), or None while Active. This is how a Payment Preview shows that it would Redeem.

The response models, PreviewSide, LedgerChange, MortgagePreview and PreviewOfChange, are at lines 65–105. A PreviewOfChange has one MortgagePreview per Mortgage touched, each with a before and an after side, and a list of ledger_changes.

4. Which Ledger steps moved

  1. A step is "the same step" in both Ledgers if it has the same date, the same kind and the same Payment. The kind is turned into its position in LedgerEvent, so sorting puts steps in the order the engine applies them inside a day.
  2. | on two sets of keys is their union: steps on either side.
  3. Keep only steps that were added, removed, or whose figures differ.

Nuances

(a) Refused exactly when saving would be

Predict: send the same body with ₹83,334 (8333400), first to /payments/preview, then to /payments. What does each answer?

POST /payments/preview  422  2025-Meera-GoldChainPendant: the Payment on 19 Oct 2026 would be more than the ₹83,333 owed then
POST /payments          422  2025-Meera-GoldChainPendant: the Payment on 19 Oct 2026 would be more than the ₹83,333 owed then

Word for word the same, because it's the same check_replays raising it (lesson 2). That's the guarantee: there's no Preview that a save then refuses, and no refused Preview that would have saved. Saving it is safe to try: it's refused, so nothing is written.

(b) A rupee less

Preview ₹83,332 instead, and the chain stays Active, owing ₹1 today. Its Projection says ₹1,117 in three months, not ₹1. The month that started on 10 Oct is still charged on the ₹80,000 it started with (ADR 0006, trap #7). The Preview shows the Lender that before they save, which is exactly what it's for.

(c) Belt and braces: what really stops a Preview saving?

Predict: delete conn.rollback() at line 174 of previews.py (leave the finally with a pass). Does a Preview now save its change? How many of the 826 tests fail?

Nothing saves, and no test fails. The route opened the connection with engine.connect(), which never commits; when the with block closes it, SQLAlchemy rolls back whatever is left. conn.rollback() is a second guard, so the snapshot-and-undo inside _preview doesn't depend on how the route opened the connection.

The guard that matters is the route never using engine.begin(). Change line 174 to conn.commit() instead, and 13 tests fail: nine in test_previews.py, three in test_closing.py, one in test_redeeming_payments.py. Each one Previews a change and then checks that nothing was saved, by reading the Mortgage, or its History, back.

Both checked at commit d6a92ab by running uv run pytest with each edit, then git checkout.

(d) Why the routes are written out by hand

Every change has a save route beside its change function and a Preview route in previews.py that look very alike. Couldn't one declaration generate both? ADR 0007 decided not to. Generating them would mean rewriting FastAPI route signatures at import time, to save about a hundred lines. And not every pair fits one mould:

  • The Void and Reopen Previews take no body, but their saves need a reason (VoidIn). So preview_void (line 228) and preview_reopen (line 337) pass the reason "preview". It's written into History and rolled back with it.
  • Two Previews return their own shapes: preview_new_mortgage (line 398) returns a NewMortgagePreview, since there's no "before" for a Mortgage that doesn't exist yet, and preview_collateral (line 433) returns a CollateralPreview (lesson 5). Both do their own try … finally: conn.rollback() instead of calling _preview.

The ADR's argument: the repetition is shallow, because the rules live once, in the change functions. What repeats is only each route's parameters.

(e) Bulk Previews are all or none

The bulk Closure Previews (/closures/redeem-preview and the others) run redeem_all and the rest, exactly like their saves. If any one Mortgage would be refused, the whole Preview is refused with that Mortgage's name, as lesson 2's waive-preview showed. You can't Preview "the ones that would work".

How the frontend asks for Previews while the Lender types, and shows them beside the form (usePreview, useProposedChange), is chapter 011, lesson 4.

Quiz

A bug in void_payment makes Voids record the wrong reason. Where else does it show?

A Preview runs the real change (trap #5). Any bug in void_payment runs in preview_void too, even if, here, the History it writes is rolled back.

A Preview route used engine.begin() by mistake, and _preview still calls conn.rollback(). What is saved?

conn.rollback() undoes the change, so when the with engine.begin() block ends there's nothing left to commit (checked with SQLAlchemy directly). The second guard is now the only one, which is why both exist.

Why was ledger_changes empty for the Term Change removal, but not for the Payment?

Both snapshots take mortgage.ledger(today). A Term Change from 25 Oct has no step before 19 Oct, so nothing differs; its effect shows in the Projection. A Payment today adds a step today.
