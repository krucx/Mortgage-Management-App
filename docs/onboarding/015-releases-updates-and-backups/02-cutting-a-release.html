Chapter 015 · Lesson 2

Cutting a release

Nobody pushes a version tag by hand. The release owner asks for a candidate and does nothing else: the full test suite runs once, the release pull request merges itself only if machine-checked conditions hold, and merging it publishes the release. With nobody approving anything, how does that chain safely produce an image for Docker and a download for Windows?

By the end you can trace a release from the candidate workflow to the published image and zip, run every check it makes locally without publishing anything, and say where each rule lives.
Changed in 3.4.10, and again since. A required version-bump check (.github/workflows/test.yml, tested by .github/scripts/test-check-version-unchanged.mjs) fails any pull request that changes VERSION, unless it is the release candidate's. It also refuses a non-release edit to CHANGELOG.md: a feature pull request adds a small fragment file under changelog/unreleased/ and leaves the version alone. The candidate workflow collates the fragments into the dated section.
Changed with ADRs 0022 and 0023. This lesson used to teach a flow in which a human approved the release pull request. The owner is the only developer and agents act under the owner's account, so that approval could never be given by anyone else (ADR 0022). ADR 0023 replaced the approval with machine conditions, and the full suite now runs once per release instead of on every pull request and push.

The problem

Docker installations pull a versioned image. Windows Setup downloads the repository files plus already-built screens in a zip. If either claims a version different from the code, a Lender may install mismatched pieces. The update banner shows the release notes, so they must be the reviewed ones. And a release must never move latest backwards or publish a commit the full suite has not passed.

Until 3.4.6 a release started with a tag pushed by hand, and the rules lived in shell inside three workflow files, copied between them. Four of the twelve commits before architecture review pass 7 fixed that shell, each proven only by shipping a real release.

The idea

Three workflows, each a thin wrapper around one tested module, .github/scripts/release.mjs, which talks to GitHub through an adapter (github-adapter.mjs for real, fake-github-adapter.mjs in tests). The release owner's whole job is one action, running Prepare release candidate with a version; the release checklist is now just that trigger and what to do when a release is blocked. The change author only adds a fragment under changelog/unreleased/ and never edits CHANGELOG.md or VERSION.

What replaces the human approval is one pure function, judgeReleaseCandidate() in .github/scripts/lib/release-conditions.mjs. The workflow asks it before merging, and the publisher asks it again after. If any answer is no, the pull request is left for the owner and nothing is published, because a published Docker image cannot be recalled.

The flow

The code

  1. No tag yet: publish-release.yml creates it at the release PR's merge commit, with RELEASE_WORKFLOW_TOKEN (the built-in token can't create a tag for a commit whose workflow files changed).
  2. A rerun after a failure finds the tag already at the same commit and reuses it. A tag at any other commit is refused: tags never move once something may have been published.
  1. The branch name and VERSION must agree, and the pull request must target main.
  2. judgeReleaseDiff allows only what the candidate workflow writes (the list lives in lib/release-candidate-files.mjs): version-only edits, one new dated CHANGELOG.md section with nothing removed, and deleted fragments. A renamed file or any other path refuses.
  3. judgePreflight wants a successful Tests run, dispatched on release/X.Y.Z, at exactly the head commit. A commit pushed after the preflight is therefore a commit nobody validated, and it refuses.
  4. judgeChecks wants every check main's ruleset requires to be reported for the head commit and passing. Several answers are possible: a string is a refusal, while a still-running check returns waiting: true so the caller may wait and ask again. Fewer than the required checks, or none, also refuses.

The same function runs twice, before the merge and again in release.mjs validate-candidate, so a pull request that changed between the two cannot be published. Nothing here counts reviews at all: a CodeRabbit comment, or anyone's approval, changes no answer.

release.yml runs validate-candidate again with --expect-commit the tagged commit, so even a hand-dispatched run can only publish a merged PR that still meets the conditions. Its version job then runs check-version.mjs --tag: one canonical VERSION file, which the backend and frontend package metadata, the lockfiles, openapi.json and the current-version labels on the GitHub Pages site must all match. The image is published before the GitHub Release, so the update banner never offers a release Docker can't pull yet; latest moves only for the highest version tagged.

Running the suite once, and what a failure does

The preflight is the only time the full Tests suite (QA, Windows and the image included) runs for a release. It records the tree it validated as a commit status, and the release pull request's own run, the push to main after the merge and the Tests call inside release.yml look that record up by tree hash and report "Reused result". If main moved and the tree changed, they run in full instead (the mechanism is the one in chapter 013, lesson 1).

Nobody watches a release, so a failure has to speak for itself. A failure or timeout in preparation, preflight, merge, validate, tag or publish runs release-blocked.mjs report, which opens, or comments on, one release-blocked issue per version, naming the stage, the run and the safe rerun command; a later successful publish closes it. Nothing retries and nothing rolls back by itself, because a published image or GitHub Release may already be installed on a Lender's laptop and cannot be recalled: a second automatic attempt could make a half-published release worse. A person reads the issue and reruns, or cuts a new patch version.

Nuances

A valid version is exactly x.y.z, with no leading v. The CHANGELOG section starts with a plain summary that says whether the database changes, and, when it does, an ### Upgrading section; those notes appear in the banner, so write them for the Lender with the glossary terms. The candidate workflow stops when changelog/unreleased/ holds no authored fragment, so a pull request that prepares a release adds a fragment and leaves VERSION alone: the workflow bumps it, and a hand bump on main would make the workflow refuse the same version. The file naming is in changelog/unreleased/README.md. Third-party actions in every workflow are pinned to a full commit SHA, and Dependabot proposes their updates in one grouped pull request.

Predict: the release workflow fails half-way, after the image is on Docker Hub but before the GitHub Release. The release owner reruns the publisher. What happens to the tag?

planReleaseTag finds the tag at the same merge commit and returns reuse; the release workflow replaces the same version's image, notes and zip. If the fix needs a different commit, that is a new patch version, never a moved tag.

Quiz

How does a release start?

Tags are created only by publish-release.yml, at the merge commit of a release/x.y.z PR that met the machine conditions.

After the preflight passed, someone pushes one more commit to release/3.4.8. What happens?

judgePreflight needs a successful Tests run at exactly the head commit. Nothing retries; the owner reruns Prepare release candidate once the cause is fixed.

The publish step fails after the image reached Docker Hub. What does the system do by itself?

A published image cannot be recalled, so a second automatic attempt could make things worse. A person reruns the command the issue names, or cuts a new patch version.
