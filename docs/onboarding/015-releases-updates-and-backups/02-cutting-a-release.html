Chapter 015 · Lesson 2

Cutting a release

Nobody pushes a version tag by hand. A release owner asks for a candidate, a human approves its pull request, and merging it publishes the release. How does that chain safely produce an image for Docker and a download for Windows?

By the end you can trace a release from the candidate workflow to the published image and zip, run every check it makes locally without publishing anything, and say where each rule lives.

The problem

Docker installations pull a versioned image. Windows Setup downloads the repository files plus already-built screens in a zip. If either claims a version different from the code, a Lender may install mismatched pieces. The update banner shows the release notes, so they must be the reviewed ones. And a release must never move latest backwards or publish code nobody approved.

Until 3.4.6 a release started with a tag pushed by hand, and the rules lived in shell inside three workflow files, copied between them. Four of the twelve commits before architecture review pass 7 fixed that shell, each proven only by shipping a real release.

The idea

Three workflows, each a thin wrapper around one tested module, .github/scripts/release.mjs, which talks to GitHub through an adapter (github-adapter.mjs for real, fake-github-adapter.mjs in tests). The release owner follows the release checklist; the change author only writes notes under ## Unreleased in CHANGELOG.md, and never edits VERSION (ADR 0018).

The flow

The code

  1. No tag yet: publish-release.yml creates it at the release PR's merge commit, with RELEASE_WORKFLOW_TOKEN (the built-in token can't create a tag for a commit whose workflow files changed).
  2. A rerun after a failure finds the tag already at the same commit and reuses it. A tag at any other commit is refused: tags never move once something may have been published.
  1. The author can't approve their own release.
  2. CodeRabbit is a bot: its review is advisory and never counts. Only reviews of the head commit count, so a push after approval needs approving again.

release.yml runs validate-candidate again with --expect-commit the tagged commit, so even a hand-dispatched run can only publish an approved, merged PR. Its version job then runs check-version.mjs --tag: one canonical VERSION file, which the backend and frontend package metadata, the lockfiles, openapi.json and the current-version labels on the GitHub Pages site must all match. The image is published before the GitHub Release, so the update banner never offers a release Docker can't pull yet; latest moves only for the highest version tagged.

Nuances

A valid version is exactly x.y.z, with no leading v. The CHANGELOG section starts with a plain summary that says whether the database changes, and, when it does, an ### Upgrading section; those notes appear in the banner, so write them for the Lender with the glossary terms. A pull request that only prepares a release writes notes under ## Unreleased and leaves VERSION alone: the candidate workflow bumps it, and a hand bump on main would make the workflow refuse the same version. Third-party actions in every workflow are pinned to a full commit SHA, and Dependabot proposes their updates in one grouped pull request.

Predict: the release workflow fails half-way, after the image is on Docker Hub but before the GitHub Release. The release owner reruns the publisher. What happens to the tag?

planReleaseTag finds the tag at the same merge commit and returns reuse; the release workflow replaces the same version's image, notes and zip. If the fix needs a different commit, that is a new patch version, never a moved tag.
