Chapter 015 · Lesson 1

A Backup, start to finish

A folder of files is useful only if it holds a consistent database and its photos, and someone can find and open it later. Let's follow one Backup from database snapshot to the Lender's synced folder.

By the end you can say where a Backup goes, what it contains, how its filename is made, and what Settings tells you about it.

The problem

A database and ID Photos form one lending book. Copying just the database loses photos; copying the live database file while the app writes can produce an inconsistent copy. A weekly attachment also grows beyond common email limits and leaves personal data in a mailbox.

The idea

The app snapshots SQLite consistently, zips the snapshot and photos, and moves a completed archive into BACKUP_DIR by renaming a hidden partial file. The folder can be synced by Google Drive or iCloud. A configured password encrypts the zip; Settings reports whether encryption is on. With no password, the zip is plain. The compatible classic zip password is weak encryption, accepted because the synced folder is expected to be private (ADR 0003). The default retention is four archives.

ADR 0003 chose a synced folder over email: it avoids SMTP credentials, attachment limits and a second store of Customer data.

The flow

The code

The hidden work folder holds the archive while it is built. The destination only gets a completed zip, and finally removes temporary files even after failure.

SQLite's online backup API reads a consistent snapshot even while the Lender continues using the app. A plain file copy can catch the database halfway through a write.

The response's running field matters because the route accepts a background job. Settings shows the same status and lets the Lender change how many Backups to keep.

Run-through: make a Backup from a copy of the served book

The sample book builds its data in a temporary folder. Copy that folder, serve the copy on port 8766, and make the Backup from its API. Its empty password makes this a plain zip, as it is on Windows without Docker when no password is configured.

cd backend
export BOOK=$(mktemp -d)
uv run python ../docs/sample-book/book.py "$BOOK"
export COPY=$(mktemp -d)
cp -R "$BOOK/data" "$COPY/"
mkdir "$COPY/backups"
uv run python ../docs/sample-book/serve.py "$COPY" 8766 >"$COPY/serve.log" 2>&1 & SERVER_PID=$!
curl --retry 10 --retry-connrefused --retry-delay 1 -s http://127.0.0.1:8766/api/backups
while [ "$(curl -s http://127.0.0.1:8766/api/backups | python3 -c 'import json,sys; print(json.load(sys.stdin)["running"])')" = true ]; do sleep 1; done
curl -s -X POST http://127.0.0.1:8766/api/backups
while [ "$(curl -s http://127.0.0.1:8766/api/backups | python3 -c 'import json,sys; print(json.load(sys.stdin)["running"])')" = true ]; do sleep 1; done
BACKUP=$(ls -t "$COPY"/backups/*.zip | head -n 1)
unzip -l "$BACKUP"
kill "$SERVER_PID"

Nuances

Predict: The Lender sets BACKUP_PASSWORD but the computer has no zip program. What happens?

The Backup fails with an explicit error. The pure Python fallback makes a plain zip only when there is no password; it will not silently drop the requested password. On Windows without Docker, an unencrypted zip can be created by that fallback. The configured password uses classic ZipCrypto, which is weak; ADR 0003 accepts it only for the Lender’s private synced folder. The app image installs the zip program for this (Dockerfile). With no Backup folder configured, the route refuses with 409; a failed background Backup is recorded in last_error, and its temporary files are cleaned up on the next start.

Quiz

Why copy the archive to a hidden partial name, then rename?

The app atomically renames the fully copied archive into its final name.
