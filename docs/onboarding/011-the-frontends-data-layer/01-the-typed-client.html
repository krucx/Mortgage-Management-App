The typed client and the generated types

The backend says what every route takes and returns in Python. The frontend is TypeScript. This lesson shows how the one becomes the other without anybody copying it by hand, and what the frontend does with an answer it didn't want: a refusal, a failure, or no answer at all.

By the end you can say how a backend model becomes a TypeScript type, what to run when you change one, and what happens to a refusal.

The problem

Here's the obvious way to read Meera's chain from a React page:

All three lines compile. The first typo is found when the Lender opens the page and gets a 404. The second shows undefined where a figure should be. And when the backend renames a field next month, nothing tells the frontend at all. With 71 paths, and models that change every few releases, hand-written requests drift from the backend one by one.

Errors have the same problem. FastAPI answers a refusal with a JSON body whose detail is sometimes a string, sometimes an object with a message, and sometimes a list of validation errors. Show detail as it comes and the Lender sees [object Object].

The idea

Generate the types from the backend. FastAPI can describe every route as an OpenAPI schema (a JSON document listing every path, its parameters, its request body and its answers), built from the Pydantic models the routes use. A tool, openapi-typescript, turns that schema into TypeScript types, api.gen.ts. Nobody writes those types; one command regenerates them.

Ask through one typed client. openapi-fetch is a thin wrapper around fetch that takes those types. Its client.GET('/api/mortgages/{mortgage_id}', …) only compiles if that path exists, with those parameters, and its answer has the right type. Every request in the app goes through one such client, and fetch itself is banned everywhere else.

Turn every answer into data or one readable error. dataOrThrow wraps each call: the data if the backend answered 2xx, otherwise an Error whose message is one sentence for the Lender.

The flow

Notice that the chain has two links and each has its own test. The backend test checks that openapi.json matches what the backend would write now. The frontend test checks that api.gen.ts matches what openapi-typescript makes of openapi.json.

The code

1. From the backend's models to a schema file

  1. The schema comes from the real app, built by the composition root (chapter 010, lesson 1) on sqlite://, an in-memory database that is never used. FastAPI's .openapi() walks every route and its Pydantic models.
  2. Sorted keys and a fixed indent, so the same backend always writes byte-for-byte the same file. That's what lets a test compare it.

One command, two steps: write openapi.json from the backend, then generate api.gen.ts from it. Today's schema has 71 paths and 98 models; openapi.json is 7,602 lines and api.gen.ts 5,483.

2. What the generated types say

This is the backend's def read_mortgage(mortgage_id: int, …) -> Mortgage (in lending/mortgages.py), as a type: the path needs a numeric mortgage_id, and a 200 answer is a Mortgage. The name is FastAPI's generated operation id: function name, path and method run together. The file starts "This file was auto-generated by openapi-typescript. Do not make direct changes to the file."

api.ts only gives generated types short names, so pages write Mortgage, not components['schemas']['Mortgage']. It never declares a field itself.

3. The one client

  1. The only line in src/ that touches fetch. Tests pass their own fetch here (a fake backend), so the same code runs against canned answers.
  2. createClient<paths> is openapi-fetch. The <paths> type argument is the generated paths interface, which is what makes every client.GET(…) checked. baseUrl is wherever the page came from: localhost:5173 in development (Vite passes /api on), the backend itself when it serves the screens.
  3. The cache (lesson 2) is made here too, with one retry rule for every read: below.

Line 58 is a typed request: the path is a string literal the compiler checks against paths, and mortgagePath(id) is { path: { mortgage_id: id } }. Lesson 2 explains queryOptions and the key.

4. Data, or one readable error

  1. errorMessage (lines 13–28) turns any FastAPI error body into one line: a string detail as it is; an object's message; a list of validation errors as field: message; field: message; otherwise Request failed (status).
  2. openapi-fetch doesn't throw for a 4xx or 5xx; it returns { data, error, response }. It only throws when fetch itself fails, and a browser's fetch throws a TypeError when it can't connect at all.
  3. Any answer that isn't 2xx becomes a BackendError that remembers the status. Callers never check response.ok themselves.

TanStack Query calls this after a read fails, with how many times it has failed so far. A refusal (4xx) is never asked again: asking twice gets the same "no". Anything else (a 5xx, or no connection) is asked once more, in case it was a blip.

Hands-on: a path that doesn't exist

In frontend/src/requests.ts, line 58, change '/api/mortgages/{mortgage_id}' to '/api/mortgage/{mortgage_id}'. Then, from frontend/, run npm run typecheck.

Predict: does it compile? If not, how many errors, and where?

51 errors. The first one that matters is the line you changed:

src/requests.ts(58,30): error TS2345: Argument of type '"/api/mortgage/{mortgage_id}"' is not assignable to parameter of type 'PathsWithMethod<paths, "get">'.

The other 50 are knock-on errors in the pages that read a Mortgage: 43 in MortgagePage.tsx, 5 in RedeemPage.tsx, 1 each in ChangeTermsPage.tsx and EditMortgagePage.tsx. With a path it doesn't know, the client can't tell which answer comes back, so it types the data as any route's answer (the errors list the Backups settings among them), and every mortgage.name downstream stops type-checking. Always read the error in requests.ts first. (Run at commit 87a96c7.)

Undo it: git checkout -- src/requests.ts.

Nuances

(a) Change a model, regenerate, commit both files (trap #10)

Trap #10. Change a Pydantic model a route takes or returns, or add a route, and the types are out of date until you run npm run gen:types in frontend/ and commit both openapi.json and api.gen.ts. Never edit api.gen.ts by hand: the next regeneration throws your edit away.

Predict: you add a field to the backend's Mortgage model and forget to regenerate. Which of the two tests fails?

Only the backend one. test_openapi.py compares the checked-in openapi.json with what the backend writes now, so it sees the new field. api-types.test.ts only compares api.gen.ts with the checked-in openapi.json, and those two still agree with each other. It fails in the other case: you regenerate openapi.json but not api.gen.ts (run the backend half by hand, say), or edit api.gen.ts yourself. Between them, the two tests cover both links of the chain.

A new column you only store and never return through a model changes no schema, so it needs no regeneration (chapter 010, lesson 6).

(b) What the schema leaves out on purpose

The other test in test_openapi.py, test_ready_to_redeem_is_retired_from_the_api, checks that four words never appear in the schema: ready_to_redeem, ready-to-redeem, ReadyToRedeem and received_with. Paying the whole Outstanding Redeems a Mortgage (ADR 0011), so nothing waits to be Redeemed, and a Final Payment's link back to its first part is the backend's business (chapter 007, lesson 2). If a field isn't in the schema, the frontend can't even name it.

(c) No fetch outside the client (trap #11)

Trap #11. The frontend never calls fetch itself: every request goes through the typed client, by way of a function in requests.ts. A request made with fetch isn't type-checked, isn't cached, and isn't made stale by any save.

(e) When the server stops

The Lender's app is installed as a PWA, so its screens open even when the backend isn't running. With the app open on Meera's chain, stop the backend (Ctrl-C in terminal 1) and click Customers in the menu.

Predict: what does the Customers page say, and how many times did it try?

GET /api/customers?page=1&q= was tried twice (no connection isn't a refusal, so it's asked once more), then the page says:

The app's server isn't running: start Mortgage Management, then try again.

That's UNREACHABLE, from dataOrThrow's TypeError branch. Reload the page instead, and StartGate catches it before any page shows: "The app isn't running. Start its server: this page loads the app as soon as it is running." That screen is chapter 012, lesson 6's. (From scripts/network.mjs, section L1, which made every /api/ request fail to connect.)

Start the backend again (serve.py "$BOOK" 8000) before you go on.

(f) A sort column that doesn't exist won't compile

SortOf digs the type of the sort query parameter out of the generated route: for the Customers list, "name" | "phone" | "address" | "referrer", the backend's CustomerSort. (infer S is TypeScript for "whatever type sits here, call it S".) Record<Sort, true> demands an object with exactly those keys. So if the backend adds a sort column, columnsOf fails to compile until the frontend lists it; rename one, and the old name fails too. A plain array, ['name', 'phone'], would only catch the second. Lesson 3 uses CUSTOMER_SORTS.

Quiz

You add nickname: str | None to the backend's Customer response model. What must the commit also contain?

npm run gen:types rewrites both files, and both are checked in; test_openapi.py fails until openapi.json is current. api.ts never declares fields: Customer there is just Schemas['Customer'], so it gets nickname for free. Nothing reads the schema at run time: it's a build-time input.

A Payment Preview answers 422 with a string detail. What does dataOrThrow do?

Any answer that isn't 2xx becomes a BackendError(status, error), and errorMessage passes a string detail straight through. UNREACHABLE is only for a TypeError from fetch itself (no connection). And a 4xx is never retried.

A new page reads the Reminders with fetch('/api/reminders'). Which check fails?

oxlint's no-restricted-globals rule flags it, and showPage swaps the global fetch for one that throws. The compiler is happy: fetch is a perfectly typed browser function. CI runs the typecheck, lint and tests, so lint stops the unused call before it reaches a page test.
