Check yourself: The frontend's data layer

Questions from all five lessons, mixed up. Then make Previews refetch after a save like everything else, and see which two tests catch it.

Quiz

1. A page imports type MessageSettings from api.ts. Where do its fields come from?

api.ts only names generated types (Schemas['…']). They come from the backend's models: openapi.py writes openapi.json, and openapi-typescript turns it into api.gen.ts, both by npm run gen:types. Nothing about types happens at run time. (Lesson 1.)

2. On the served book, with the dev server, you type "8000" into the Payment form at four keys a second, then wait. How many POST /api/payments/preview requests go out?

usePreview keeps enabled false until the draft's key has stayed the same for 400 ms, so only ₹8,000 is asked about. The script measured it 408 ms after the last key (lesson 4, run-through).

3. A Payment is saved while the Dashboard is not on screen. When is GET /api/dashboard asked?

invalidateQueries marks every matching key stale but asks again only for those on screen (active). The Dashboard is asked when its page mounts, as the run-through after Sunita's Reminder showed (lesson 5).

4. Why is keys.search(query) ['customer', 'search', query] rather than ['search', query]?

A key is a path, and STALE_AFTER.customer names the prefix ['customer']. A saved or deleted Customer can change who a search finds, so searches are filed under it on purpose. Keys don't decide types, and the route is /api/search. (Lesson 2.)

5. Meera's chain, ₹90,000 in UPI, its Preview answered. Why is Save disabled?

canSave needs !preview.error, and the Preview answered 422 "…would be more than the ₹83,333 owed then". The draft isn't null: it's a complete PaymentIn. The Cash Limit only warns, never blocks, and this is UPI anyway. (Lessons 1 and 4.)

6. You add "skip all Reminders for a Customer". It changes nothing owed. Which save hook does its page use?

It's a Reminder action, and STALE_AFTER.reminder already says what those make stale: the Reminders list and the Dashboard. Bulk or not, it isn't a Ledger change. useMortgageChange is only for changes that return the Mortgage they changed. (Lesson 5.)

7. The backend is stopped while the app is open. The Lender clicks Customers. What do they see, and how many tries were made?

fetch throws a TypeError, which dataOrThrow turns into UNREACHABLE. That isn't a refusal, so retryUnlessRefused asks once more: two tries. (Lesson 1, nuance e.)

8. On the Customers list sorted ?sort=-name, the Lender opens Meera and presses Back. What is asked for?

The sort lives in the URL, which Back restores, so the key is the same one cached. Being stale at once (staleTime 0), it's asked again in the background while the cached rows show. (Lessons 2 and 3.)

Recap

  • The frontend's types are generated: openapi.py writes the backend's schema to openapi.json, openapi-typescript turns it into api.gen.ts, and api.ts only names its types. Change a model, run npm run gen:types, commit both files, or test_openapi.py (and, if they disagree, api-types.test.ts) fail. Every request goes through one openapi-fetch client, so a wrong path won't compile; fetch is banned elsewhere (oxlint in CI, and showPage in tests). dataOrThrow makes every answer data or one readable error; a refusal is never retried, a failure once (lesson 1, traps #10 and #11).
  • One QueryClient holds every answer, made in main.tsx and given to every page by ServerStateProvider. Each read in requests.ts has a key from keys, built like a path so a prefix reaches a whole branch. Answers are stale at once: a page shows the cached answer immediately and asks again behind it. Settings, payment methods and the update check are read once (staleTime: Infinity) and updated from what saving returns (lesson 2).
  • A list is a ListRequest (key and loader) in lists; useListPage does the rest. The sort lives in the URL (?sort=-name), so Back and reloads keep it; a new sort or filter starts at page 1; an emptied page steps back; each page and order is its own key, so a slow old answer never shows (lesson 3).
  • A form makes a draft (or null); usePreview asks for its Preview 400 ms after it settles, under ['preview', …draft], and never shows an old draft's answer as current. useProposedChange enables Save only with a draft, a loaded Preview and no refusal, then warns about cash at or over the Cash Limit, confirms, saves and hands on the result (lesson 4).
  • What each change makes stale is declared once, in serverState.ts: ledgerChanged for anything that can change what's owed, STALE_AFTER for the rest. Pages save through useLedgerChange, useMortgageChange or useChange. What's on screen is asked again at once; Previews and Closure quotes are only marked, because the one on screen previews the change just made (lesson 5).
