Chapter 011 · Lesson 5

Saving, and what goes stale

A save changes something on the backend, so some answers in the cache are now wrong. Which ones? This lesson shows where that is declared (once, in serverState.ts), how a page saves through it, and why the Preview the Lender just looked at is deliberately not asked for again.

By the end you can save a change and declare what it makes stale.

The problem

Meera pays ₹8,000 towards her bangles. On the backend that's one Payment row and one Allocation. In the cache, it's a lot more: the bangles' Mortgage page (Ledger, Outstanding), every list that shows an Outstanding, the Dashboard's totals, the Dormant count, Meera's Customer History (which holds her Mortgages' History), and the Receipts of her other Payments (each says what's still owed). Miss one and the Lender sees an old figure. Every figure is replayed, so a back-dated Payment can change Payments other than the one saved (trap #4).

If each page listed what its own save makes stale, the lists would drift: a new screen that shows Outstanding would have to be added to every save in the app. And there's a trap. The Payment form's Preview previews this very Payment. Ask for it again after the save, and the backend would preview the Payment on top of itself, and might refuse it.

The idea

Name the kinds of change, not the pages. There are two kinds:

  • A Ledger change: anything that can change what Mortgages owe (Payments, Voids, edits, Term Changes, Closures and Reopens). These all make the same things stale, listed once, in ledgerChanged.
  • Every other change (approving a Notice, a Call Note, a Customer's details, Gold Rates…): each has its own entry in STALE_AFTER, the list of keys it makes stale.

Save through a hook that marks them. A page saves with useLedgerChange, useMortgageChange or useChange(STALE_AFTER.…). The hook sends the change and then marks the right keys stale. TanStack Query's invalidateQueries marks a key stale and, by default, asks again at once for any of them on screen. Previews and Closure quotes are marked stale but not asked again.

The flow

The code

1. The changes, by name

Each is a plain function of the client: it sends one request and returns the data or throws. These are the save twins of lesson 4's previews. Other saves sit beside what they belong to: noticeActions, customerChanges, settings.save….

2. What a Ledger change makes stale

  1. Every key under these six prefixes is marked stale, and those on screen (TanStack Query calls them active: a mounted useQuery is watching them) are asked for again now. void says "I'm not awaiting this promise", on purpose.
  2. refetchType: 'none': mark them stale, but ask nothing now. Next time a Preview or quote is shown, it's asked for afresh.

3. What every other change makes stale

Each entry is a plain list of keys, with a comment saying why. That comment is the rule: when you add a screen that shows something, check every entry whose reason covers it. satisfies checks every entry is a list of keys while keeping the names (STALE_AFTER.notice) typed.

4. The save hooks

Each hook returns a function that takes the change as a function of the client, so the page writes changeLedger((client) => changes.recordPayment(client, asked)). (<T,> with its odd comma is how a .tsx file declares a generic arrow function: without it, <T> would be read as a JSX tag.) If the change throws, nothing is marked: a refused change changed nothing.

useMortgageChange is for changes that return the Mortgage they changed (an edit, a Term Change). It puts that answer under ['mortgage', id] before marking anything stale, so the page shows the change immediately rather than the old Mortgage while it's asked again.

Nuances

(a) The Preview on screen is not asked again

Predict: on the Redeem form, the Lender confirms. ledgerChanged runs while the form, with its Preview, is still on screen. Suppose line 157 used plain invalidateQueries({ queryKey }) like the others. What would the backend see next?

A second POST /api/closures/redeem-preview, right after POST /api/closures/redeem: a Preview of Redeeming a Mortgage that is now Redeemed. The backend refuses that, and for an instant the form would show the refusal under a change that just succeeded. closing.test.tsx's "a Waiver and a Redemption each go to their own routes" catches exactly this; the check-yourself exercise has you break it and watch.

The same goes for a Payment's Preview: after the save, asking again would preview a second ₹8,000 on top of the first. So Previews and Closure quotes are only marked stale. If the Lender comes back to the form, the Preview is asked for afresh, against the new book.

(b) Keep the answer first: a Voided Payment's Receipt

The Payment page shows the Payment and its Receipt. A Void returns the Payment, now with voided_at set, and setPayment keeps it under ['payment', id] before ledgerChanged marks ['payment'] stale. So when the Receipt (['payment', id, 'receipt'], on screen) is asked again, receiptQuery's guard (lesson 2, nuance b) finds the Voided Payment in the cache and doesn't ask the backend at all: a Voided Payment has no Receipt. Swap lines 207 and 208 and the Receipt would be asked for while the cache still held the Payment as it was before the Void.

serverState.test.tsx pins several of these by name: "new message settings reword the Receipts as well as the Notices", "a Customer's new name or number reaches everything that shows it", "marking a Mortgage called changes the Call List, its Call Notes and the Dashboard count".

(d) Almost never in a page

Search src/ for invalidateQueries outside serverState.ts and you'll find exactly one, in MortgagePage.tsx (line 46). A photo or a Collateral Value saved from the Mortgage page returns the Mortgage; the page keeps it with setQueryData and marks only that Mortgage's History stale, because the History now holds the change. Every other save goes through one of the three hooks, with a STALE_AFTER entry or ledgerChanged. A page may put an answer it got back into the cache (setQueryData, as the Settings forms and the Void do), because that's the backend's own answer, not a guess about what's stale. If you find yourself writing a second invalidateQueries in a page, it probably belongs in STALE_AFTER.

The recipe: a new route, end to end

Everything in this chapter, in the order you'd do it for a new change:

  1. Backend: the change, its Preview twin and their routes, with Pydantic models (chapter 006, lesson 5).
  2. Types: in frontend/, npm run gen:types; commit openapi.json and api.gen.ts (lesson 1, trap #10). Name the new types in api.ts if pages need them.
  3. Requests: a function in requests.ts: in changes if it can alter what Mortgages owe, otherwise beside what it belongs to; and its entry in previews (lesson 4).
  4. Stale: a Ledger change needs nothing more. Anything else: pick the STALE_AFTER entry whose reason fits, or add one with its reason, and a test in serverState.test.tsx.
  5. The page: useProposedChange with save: (c) => changeLedger((client) => changes.yourChange(client, c)), or useChange(STALE_AFTER.yourEntry); useMortgageChange if it returns the Mortgage. Never fetch (trap #11), and no invalidateQueries of your own.

Quiz

You add a "mark as sent by post" action for a Notice. It doesn't change what anybody owes. How should the page save it?

It's a Notice action: the Notices list and the Dashboard's counts are what change, which is what STALE_AFTER.notice says. useLedgerChange would ask every Mortgage, list and quote again for nothing. Invalidating in the page is exactly what serverState.ts exists to stop.

Right after a Payment is saved from the form, which of these is asked for again at once?

It's on screen and under keys.lists, so ledgerChanged asks for it again (the run-through's …&paged=false). The Preview is under keys.previews, marked with refetchType: 'none'. The Dashboard is marked stale but, not being on screen, waits until it's shown.

Why does useMortgageChange call setQueryData before marking anything stale?

The backend's answer is the Mortgage as changed, so the page can show it at once. It's still marked stale and, being on screen, asked again (a Ledger change may touch more than this one Mortgage's figures). ledgerChanged includes allMortgages.
