Chapter 011 · Lesson 4

Previews from a draft

Every form that changes what a Mortgage owes shows a Preview as the Lender types, and its Save button only works when the Preview says the change would be accepted. This lesson opens the two hooks that do that for every form, and shows when the Cash Limit's warning comes in.

By the end you can wire a form to its Preview, and say exactly when its Save button is enabled.

The problem

A Preview is what a change would do, shown before it's saved. On the backend, a Preview runs the real change and rolls it back (chapter 006, lesson 4; trap #5). That makes it exact, but not free: each one replays the Mortgage's whole Ledger.

Now picture the Lender typing ₹8,000 into the Payment form. A Preview per keystroke would ask about ₹8, ₹80, ₹800 and ₹8,000: four replays, three of them for amounts nobody meant. The answers can come back in any order, so the screen might end up showing ₹800's Preview under an ₹8,000 draft. And Save needs rules: not while the draft is incomplete, not while its Preview is still loading, and never when the Preview says the backend would refuse it. A Payment of ₹20,000 or more in cash needs a warning first.

Every form has these problems: the Payment form, Edit Mortgage, Change Terms, the Closures, a Void, a Reopen, a Collateral Value. Written into each form, they'd be written ten slightly different ways.

The idea

The form only makes a draft. From its fields, a form works out change: exactly what saving would send, or null while it can't be saved. That's all it does.

A Preview is a key and a loader. requests.ts's previews says, for each kind of change, what its Preview is called in the cache (the draft itself is in the key) and which route to ask.

Ask once the draft has settled, and only show the answer for the draft on screen. usePreview waits until the draft has stopped changing for 400 ms, then asks. An answer for an older draft stays on screen, marked as loading, until the current one arrives.

One hook owns Save. useProposedChange decides when Save is enabled and runs the steps in order: the Cash Limit's warning, the confirmation, the save, and what happens after.

The flow

Notice that the warning and the confirmation both read the Preview: the warning needs to know which sums go in cash, and the Payment form's confirmation says which Mortgages the Payment Redeems. That's why Save waits for the Preview.

The code

1. A Preview, declared once

The whole draft, payment, is part of the key. Two drafts that differ in any field are two different Previews; the same draft typed twice is the same one. There are eleven entries in previews, one per kind of change, and most of them share PreviewOfChange, the before-and-after of each Mortgage the change touches. (The new-Mortgage and Collateral Previews have their own shapes; ADR 0007 explains why each Preview route is written out by hand on the backend.)

2. Waiting for the draft to settle

A debounce. Each new value runs the effect again; React first runs the previous effect's clean-up (line 8), cancelling its timer. So the timer only fires once the value has stayed the same for ms.

  1. ['preview', 'payment', {…the draft…}]: under keys.previews, which lesson 5 treats specially.
  2. The draft's key, hashed to a string, is what's debounced. settled is true only when the debounced key has caught up with the current one: 400 ms with no change.
  3. enabled: false tells TanStack Query not to ask at all. So no Preview goes out until the draft has settled, and none for a null draft.
  4. While a new key has no answer yet, keep showing the last answer, marked as a placeholder, rather than blanking the Preview.
  5. TanStack Query normally asks again for what's on screen when the browser window regains focus (lesson 2). A Preview doesn't change while its draft doesn't, so not here.
  6. The answer is current only if the draft has settled, the answer is really for this draft (not a placeholder), and nothing is in flight. Anything else is loading, and an old answer's error is never shown under a new draft.

3. Save, and its three locks

Line 51 is the rule for Save: there is a draft, it isn't being saved already, its Preview isn't loading, and its Preview wasn't refused. The page puts disabled={!canSave} on its button. Then submit:

  1. The Cash Limit's warning, from the Preview's cash: the sums this change writes in cash (chapter 007, lesson 4). "Go back" ends here.
  2. The confirmation, worded from the draft and its Preview. A form whose own dialog has already asked passes confirm: null.
  3. The save itself, as the form supplied it. Lesson 5.
  4. A refused save: its reason is shown, saving goes back to false, and Save works again.
  5. What the form wants after a save: the Payment form goes to the new Payment's Receipt. saving stays true, so Save stays disabled while the page moves on.

Both dialogs are hooks that return a pair: a function that opens the dialog and returns a Promise<boolean>, and the dialog to render. useConfirm (line 11) stores the promise's resolve in state, renders the dialog, and calls resolve(true) or resolve(false) when a button is pressed. That's what lets submit read like a script: if (!(await confirm(…))) return.

  1. fetchQuery reads through the cache: the Cash Limit is a settings group with staleTime: Infinity (lesson 2), so it's asked for at most once.
  2. If the Cash Limit can't be read, don't block the save over a warning.
  3. A cleared Cash Limit (null) never warns; below it never warns; at it or above warns. formatINR turns the paise into "₹20,000" (trap #6).

4. A form, wired up

That's the whole wiring. Above it (lines 146–169), the form builds proposed from its fields: null while there's any problem (no Mortgage ticked, no amount, Allocations that don't add up), otherwise the exact PaymentIn body.

Nuances

(a) The same draft again, and looking away

Predict: with ₹8,000 (UPI) previewed, press Backspace (₹800), wait, then type the "0" back (₹8,000 again). The ₹8,000 Preview is in the cache. Is it asked for again? And if you switch to another window and back, is anything asked?

From scripts/network.mjs (section L4).

Coming back to a draft asks again: every answer is stale at once (lesson 2), and the key changed and changed back. The cache still helps: the ₹8,000 answer is shown immediately, marked loading, while it's asked again. What asks nothing is looking away and back, which refetchOnWindowFocus: false turns off for Previews only: the other reads on the page are asked again as usual. (This lesson's plan, issue #186, expected an unchanged draft to ask nothing again; on the real app that holds for focus, not for a draft typed again.)

(b) An old answer is never shown as the current one

Line 42's current covers a slow answer. Say the ₹800 Preview is still in flight when the Lender types the last "0". The key changes; settled becomes false for 400 ms, then a new request goes out. Meanwhile the screen shows the last answer it had, with loading: true, and Save stays disabled. When the ₹800 answer lands, it's filed under the ₹800 key, which the form is no longer asking about. It's the same trick as lesson 3's quick second click: one key per draft.

The refused Preview disables Save because a Preview is refused exactly when saving would be (trap #5). There's no point letting the Lender press a button the backend will refuse. (Lesson 1's run-through saw Save disabled with the refusal on screen.)

(d) A warning, never a refusal

The Cash Limit is the Lender's own setting, and the backend never refuses a cash Payment for it (cash_limit.py's docstring: "Only a warning: no Payment or Mortgage is refused for it"). So the check lives in the screen, after the Preview has said which sums are cash. "Record in cash anyway" goes on to the usual confirmation. "Go back" is the focused button, so pressing Enter by habit doesn't record the cash. A Lender who clears the Cash Limit in Settings is never warned (limit === null).

(e) A refused save

The Preview and the save run the same check, so a save refused after a good Preview is rare, but possible: the book can change between the two (another tab, a back-dated Payment saved in the meantime). Then save throws a BackendError, line 64 shows its message, and Save works again with the same draft. Nothing was written: the backend's transaction rolled back (chapter 006, lesson 2).

Quiz

You add a form for a new kind of change. What must it give useProposedChange to get a Preview?

change (or null) and preview: (change) => previews.yourChange(change) are all it needs; the debounce, the cache key and the locks on Save come from the hooks. An effect that posts would bypass the cache and the debounce, and break trap #11's spirit if it used fetch.

The Lender types "25000" in cash for the bangles and presses Save straight after the last key. What happens?

Until 400 ms have passed and the Preview has answered, preview.loading is true, so canSave is false and the button is disabled; submit would return at line 55 anyway. Once it's in, Save opens the warning first (line 56), then the confirmation (line 57).

The Cash Limit is ₹20,000. A cash Payment of ₹30,000 is split ₹15,000 and ₹15,000 across two of the Customer's Mortgages. Is there a warning?

The glossary's Cash Limit: "each Payment is one sum (its Final Payments included)". The backend's Preview lists the Payment's cash as one sum, ₹30,000, and warnCash compares the largest sum with the limit. Splitting a Payment across Mortgages doesn't split the cash (chapter 007, lesson 4).
