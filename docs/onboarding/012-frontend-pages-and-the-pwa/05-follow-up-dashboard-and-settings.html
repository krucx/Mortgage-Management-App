Chapter 012 · Lesson 5

Follow-up, the Dashboard and Settings

Each morning the Lender opens the Dashboard, follows its counts to the Call List and the Reminders, phones, notes what was said, and sends the day's messages on WhatsApp. Now and then they change a setting. This lesson follows that morning through the screens.

By the end you can change a follow-up screen or a setting, and say where each Dashboard figure comes from.

The problem

Follow-up is mostly backend work (chapter 009). The Call List is worked out each time it's asked for, and so is the wording of each Reminder. The screens still have real jobs. The Call List must make clear why each Mortgage is on it, in a cell a few characters wide. A Reminder has to look, before it's sent, the way WhatsApp will show it, bold and boxes included. Sending can't go through an API: the app opens WhatsApp, and the Lender presses Send. A template change has to show its effect as it's typed. And the Dashboard shows a dozen figures from several areas, each of which must agree with the screen it links to.

The idea

The screens say why, and compute nothing. Each Call List row carries its reasons; each Reminder its message, already worded; the Dashboard is one answer. The pages label, format and link.

Sending is opening WhatsApp. SendOnWhatsApp calls sender.send, which opens WhatsApp with the message filled in (ADR 0002, owned by chapter 009). Then the page tells the backend the Reminder is sent.

Settings is a page of independent sections. One component per settings group, each with its own draft, Save and status.

The flow

Reminder the two arrows out of "Send": WhatsApp is opened in the browser, and the backend is told separately. The app never sees whether the Lender actually pressed Send in WhatsApp.

The code

1. Why each row is on the Call List

The backend decided the reasons (chapter 009, lesson 1). The page only turns each into a coloured marker: the short label shows, and the full wording is its aria-label and tooltip. CallListPage (line 79) uses useListPage for the list, so it's sorted on the server and paged. CallSheet (line 154) holds the Excel and PDF export, and the import of Call Notes (chapter 009, lesson 2).

2. Marking called

  1. A Call Note can't change what anyone owes, so it uses useChange with its own list of what goes stale: the Call List and the Mortgage's Call Notes. There's no Preview to show. The same MarkCalled sits in the Call List's rows and on the Mortgage page (lesson 4's CallNotes panel).

3. A message as WhatsApp will show it

  1. split with a capturing group (the brackets in the regex) keeps the matched parts, so the list alternates: plain text at even positions, a *…* or _…_ or ~…~ at odd ones.
  2. The same trick with ```: every odd part sits between a pair of fences, and is drawn as a monospace box. That's how a Reminder's table of Mortgages looks right.
  1. sender (messaging.ts, chapter 009's) opens https://api.whatsapp.com/send/?phone=91…&text=… in a new tab or the WhatsApp app. Everything goes through sender, so the WhatsApp Business Cloud API could replace it later in one place (ADR 0002).
  2. On the Reminders page, onSent tells the backend: POST /api/reminders/{id}/sent. The Receipt panel on a Payment uses the same button, with nothing to mark.

4. Settings: one section per group

  1. Each section reads its own group (GET /api/settings/messages), cached with staleTime: Infinity (chapter 011, lesson 2).
  2. useDraft (useDraft.ts) is a useState that starts from the saved value once it arrives, and starts again when the saved value changes.
  3. New templates reword the unsent Reminders and the Receipts, so the save marks STALE_AFTER.messageSettings stale: Payments (their Receipts), the Reminders list and the Dashboard.

TemplateField (line 365) is a textarea with a WhatsAppPreview beside it, fed the draft as it's typed, and the list of placeholders the backend can fill in. To add a setting, add a section component here and a settings.… read and save in requests.ts; the backend half is chapter 010, lesson 3.

5. The Dashboard: one request, many links

  1. Every figure on the Dashboard comes from this one GET /api/dashboard. The selected dates are query parameters; reading the Dashboard also syncs Reminders on the backend (trap #8). The page adds Principal Outstanding and unpaid interest for the Owed headline.
  2. Each tile is a Figure: a Link to the list it was counted from. The Reminders tile opens the tab that has something in it.

The three activity figures below Owed on Active Mortgages use the selected period. The Dashboard defaults to the current calendar month; choose another month or set inclusive From and To dates to inspect a custom range. Principal lent counts Mortgages started in that period. Principal redeemed and Interest collected count non-Voided Payments in that period, using their applied allocations. These are activity totals, separate from the Outstanding tiles above.

The total Loan-to-Value counts only the Active Mortgages that have a Collateral Value. One whose purity has no Gold Rate, and no value set by hand, is left out of both sums (line 225), so it can't make the book look safer or riskier than it is. With none valued at all, loan_to_value is None, and the tile says "No Gold Rate or value set yet".

Nuances

(a) The Lender presses Send, not the app

Click-to-send (ADR 0002): driving WhatsApp Web from a browser robot breaks whenever WhatsApp changes its pages, and is against WhatsApp's terms, which could get the Lender's number banned. So sender.send only opens WhatsApp with the text filled in; the Business Cloud API could replace it later, behind the same sender. The page marks the Reminder sent when the button is pressed, trusting the Lender to press Send in WhatsApp. If they don't, the Reminder still says sent. The test for messaging.ts (chapter 009, lesson 5) pins why it uses api.whatsapp.com/send rather than the shorter wa.me link: the shorter one's redirect breaks emoji.

(b) What the bubble shows is what was stored

Predict: after sending Sunita's Reminder, you change the Reminder template again. You open the "Sent" tab and her Reminder's Message. Is it in the new wording?

No. A sent Reminder keeps the message stored when it was sent; only unsent ones are worded afresh from the current template (chapter 009, lesson 4). WhatsAppPreview draws whatever text it's given, so the page shows the backend's answer: the old wording for a sent Reminder, the new for an unsent one. Changing the template marks the Reminders list stale (STALE_AFTER.messageSettings), so the next look asks again.

(c) A tab is a URL

The Reminders tabs are radio buttons, but the chosen tab lives in the URL (?status=awaiting_approval, through useUrlFilters). So the Dashboard can link straight to a tab, Back returns to the last tab, and a tab can be bookmarked. Any change of tab starts again at page 1 (chapter 011, lesson 3). Without a status, the page shows "To send" (line 36).

(d) One request, so the figures agree

Why one GET /api/dashboard, not a request per tile? Because the figures have to agree with each other: the Loan-to-Value must divide the same Outstanding that "Owed on Active Mortgages" shows. One answer comes from one replay of every Mortgage at one moment. Several requests could land on either side of a Payment being saved in another tab, and disagree.

Quiz

A Mortgage of 18K gold is Active, but the 18K Gold Rate has never been set and it has no hand-set value. How does it count in the Dashboard's Loan-to-Value?

collateral_of returns None for it, and dashboard.py line 225 then adds neither its value nor its Outstanding. Only valued Mortgages are compared: "Outstanding ÷ Collateral Value, where valued". (Every purity in the sample book has a Gold Rate, so no Mortgage there is left out.)

The Lender presses Send on WhatsApp, and WhatsApp opens; they close it without pressing Send. What does the app record?

SendOnWhatsApp calls sender.send and then onSent straight away, which posts …/sent. With click-to-send, WhatsApp never reports back (ADR 0002). The Lender would have to send it from WhatsApp themselves.

You add a "WhatsApp signature" setting. Which part of the frontend do you change?

Settings is one component per group, listed in SettingsPage (lines 15–26), each with its own settings.… read and save in requests.ts. For a field of the message settings, it would go in MessageSettingsForm. The Reminders page only shows the messages.
