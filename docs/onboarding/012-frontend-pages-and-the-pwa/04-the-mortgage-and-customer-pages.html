Chapter 012 · Lesson 4

The Mortgage and Customer pages

The Mortgage page is where the Lender spends most of their time: one screen made of eight panels. The Customer form does the most awkward saving in the app: a record, then its photos one by one, with ID numbers read from those photos in the browser. This lesson opens both.

By the end you can add a panel to the Mortgage page, and follow how photos and ID numbers are saved.

The problem

A Mortgage has a lot to show: its Terms and coming Term Changes, what the jewellery is worth, who was called and what they said, photos of the jewellery, how to close it, its Ledger, where it's heading, and every change ever made to it. Several of these can be changed right on the page, and each change must show at once, without a reload, in the panel and in its History.

The Customer form has a harder job. A Customer has details, a photo and two ID Photos, and the backend takes the photos one request each, after the Customer exists. What if the third upload fails? Saving again must not create the Customer twice. And the Lender would rather not type the Aadhaar Number from the card by hand. But a photo of someone's Aadhaar card must not be sent to some service on the internet to be read.

The idea

The Mortgage page is a list of panels. Each section is an h3 and one component that takes the mortgage. A panel that changes the Mortgage calls onChange(changed) with what the backend returned, and the page puts it straight into the cache.

Photos follow the record, and a retry sends only what's left. useSaveWithPhotos saves the record once, remembers its id, then sends each photo, remembering which went.

The text on an ID Photo is read in the browser. ocr.ts runs Tesseract (an open-source text reader) inside the page, from files the app itself serves. Whatever it finds is only a suggestion, put in an empty field for the Lender to check.

The flow

Reminder that the photo is sent to the backend only once the Lender saves, and only to the app's own backend; the reading in the first half never leaves the browser.

The code

1. A saved change, straight onto the page

  1. The changed Mortgage the backend returned replaces the cached one, so every panel redraws from it at once, with no new request.
  2. The change also wrote History, which is cached separately: mark it stale so it's asked again. This is the one invalidateQueries in a page (chapter 011, lesson 5). void says "I'm not waiting for this promise" on purpose.

2. The panels

That's the recipe for a new panel: an h3, then a component in src/components/ that takes mortgage. If it shows something the Mortgage already holds, it needs nothing else. If it asks for more, it uses a read from requests.ts as CallNotes and ProjectionPanel do. If it saves a change that returns the Mortgage, it calls onChange={setMortgage} as TermsPanel, CollateralPanel and CloseMortgage do. mortgage.ledger.slice(-8) takes the last 8 steps: a negative index counts from the end.

3. History, grouped into changes

The backend writes one History row per field changed (chapter 006, lesson 3). On screen, the rows of one change belong together: same time, same record, same action. History (line 172) shows the latest 5 changes, and the rest in a ScrollPopup.

4. Reading an ID number in the browser

  1. ??= assigns only if worker is still null: the reader is set up once, on first use. import('tesseract.js') (a dynamic import) loads the library's code only when this line runs, not with the app.
  2. Every file comes from the app's own /ocr/. Lesson 6 shows these files are left out of the installed app's cache, because they're large.
  1. Reading takes a second or two. If the Lender picked another photo meanwhile, this reading is dropped. readingFor is a useRef: a box whose .current React keeps between renders without redrawing when it changes, so this line sees the latest photo, not the one from when the reading started.
  2. Only into an empty field, read from typed (another ref) as it is now, after any typing while the photo was being read.
  3. 'read' shows "Read from the photo: check it." beside the field.

findAadhaarLast4 and findPan in idNumbers.ts pick the number out of the text. They fix the letters Tesseract often confuses (O for 0, S for 5), and skip a 16-digit VID or a phone number. Only the last 4 digits of an Aadhaar Number are ever kept (chapter 008, lesson 4).

5. The record once, then each photo

  1. A new Customer is saved only the first time. After that, savedId.current holds its id, and a retry skips straight to the photos.
  2. Each upload has a key (the photo Blob itself, or a marker such as "aadhaar removed"). One already sent is skipped.

When a photo fails after a new record was saved, the error says so: "Customer saved, but a photo failed: …". The form locks its fields (they're saved already), and the button becomes "Retry photo upload". The Mortgage page uses the same hook for its photos, passing the Mortgage's id so there's no record to save.

6. Whose number is it?

A Primary Number identifies one person (chapter 008, lesson 1). normalisePhone (phone.ts) mirrors the backend's rule: "+91 98600 67890" and "09860067890" both become 9860067890, and anything that isn't 10 digits is null, so nothing is asked until the number is complete. The form shows the owner beside contact number 1. Contact number 2 may be shared (a family phone), so it is only searched when the Lender leaves the field, and only warns.

Nuances

(a) Nothing leaves the laptop, and the reader loads late

Tesseract's files are about 10 MB (dist/ocr/ in the built app). Loading them with the app would slow every start, for a feature used when a Customer's ID Photo is added. So readText loads them on first use, from the app's own /ocr/, which scripts/copy-ocr.mjs fills from node_modules before every npm run dev and npm run build. They're also kept out of the installed app's cache (globIgnores: ['ocr/**'], lesson 6). The ID Photo itself is read in the browser's memory. It reaches the backend only when the Lender saves, and only the app's own backend.

(b) A suggestion, never over what was typed

Predict: the Lender uploads a PAN card photo, and while it's being read types "ABCPS1234K" into the PAN field themselves. The photo reads as a different PAN. Which ends up in the field?

What they typed. Line 123 checks typed.current[field], the field as it is when the reading finishes, and fills only an empty one. Typing in the field also clears the "read from the photo" hint (typedOver, line 128): from then on the number is the Lender's. A wrong reading can't silently replace a right one.

(c) The whole Ledger, and the whole History, in a popup

The page shows the newest of each: the last 8 Ledger steps (LEDGER_SHOWN), the latest 5 changes (HISTORY_SHOWN). The rest open in a ScrollPopup (ScrollPopup.tsx), which the Ledger opens scrolled to the bottom (start="bottom"), at the newest steps. Every step is shown, even a ₹0 one (chapter 004): the page filters nothing.

(d) Grouping by time

Predict: the Lender edits the chain's description and its weight in one save. Then, a minute later, its description again. How many lines does History show for these?

Two. The first save wrote two rows (one per field) with the same at, record and action edited, so groupChanges joins them into one line: "Mortgage edited: Jewellery … → …; Net weight … → …". The second save has a different at: a line of its own. The grouping only joins neighbouring rows, which is enough because the backend returns History newest first, and one save's rows are written together.

Quiz

You add a "Pledge slip" panel that saves a slip number and gets the Mortgage back. What should it do with the answer?

setMortgage puts the returned Mortgage in the cache (every panel redraws from it) and marks its History stale, as TermsPanel and CollateralPanel do. A reload throws away the cache; local state would leave the other panels showing the old Mortgage.

A new Customer's details save, then the ID Photo upload fails. The Lender presses "Retry photo upload". Which requests go?

savedId.current already holds the new Customer's id, so run skips the save (line 44), and the sent set skips any photo already sent (line 51). The script saw exactly one PUT /api/customers/8/photo on the retry.

Where is the text on an Aadhaar card photo read?

ocr.ts runs Tesseract in a worker in the page, with its files at /ocr/ on the app's own address. The script saw no request to any other host. The backend is sent the photo only on Save, to keep it.
