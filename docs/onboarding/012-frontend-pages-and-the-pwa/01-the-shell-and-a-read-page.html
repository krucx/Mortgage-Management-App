Chapter 012 · Lesson 1

The shell and a read page

Someone reports "the Receipt shows the wrong date". Which file do you open? This lesson maps every URL to its page file, opens the shell drawn around every page, and reads the simplest kind of page in full: one that asks for data and shows it.

By the end you can find the file behind any screen, and read a page that loads and shows data.

The problem

A Receipt is what the Customer takes away after paying: what they paid towards each piece of jewellery, and what is still owed. The Lender prints it, or saves it as a PDF. To fix anything on it, you first need to know which file draws it. There are 21 URLs and 20 page files, and the menu shows only nine of them.

Then there's what every screen shares. Each one has the same header, menu and theme switch around it. Each one waits for an answer from the backend, and might get an error instead. Each one shows money and dates. If every page wrote these parts itself, they would drift apart: one page would say "Loading…", another would show a blank card; one would write ₹1,51,500 and another ₹151,500. The Lender reads these figures all day, and the screens must say them the same way everywhere.

The idea

One file lists every URL. App.tsx maps each path to one page component in src/pages/, and draws the shell around it once.

A read page has one shape. Ask for the data with a read from requests.ts (chapter 011, lesson 2). Until it arrives, show "Loading…", or the error in a status error paragraph. Then draw it with the shared CSS classes, and format every figure with formatINR and every date with formatDate.

Pages show figures; they never compute money. Every amount on a screen is a number the backend sent. The frontend only formats it.

The flow

Reminder that Nav and UpdateBanner are drawn on every page, so they make requests on every fresh load. You'll see them in the Network tab before the page's own request.

The code

1. Every URL, in one file

  1. StartGate wraps everything: until the backend answers, no route is drawn at all (lesson 6).
  2. The header is outside Routes, so it's drawn once and stays put while the page below it changes.
  3. Routes (React Router) draws the one Route whose path matches the URL. :id is a parameter: the page reads it with useParams(). Some pages have two routes: /customers/new and /customers/:id/edit are both CustomerFormPage, which edits when the URL has an id.

So the answer to "which file draws this screen?" is: find the URL's pattern here, and open that component in src/pages/. The frontend sheet has the whole table, with the routes each page calls.

2. The menu and its red dot

  1. GET /api/closures/dormant?page=1, keeping only its total. It's marked stale by any change to what a Mortgage owes (chapter 011, lesson 5), so the dot goes away the moment the last Dormant Mortgage is Redeemed.

A Dormant Mortgage is one that is still Active but owes nothing: its jewellery should already have gone back, and the Lender only has to Redeem it. ADR 0012 chose a quiet dot on the menu over a separate "Ready to Redeem" state, because owing nothing is usually a slip to put right, not a step in the workflow. NavLink is a Link that adds the active class when its path is the current one; end on Dashboard stops / from matching every URL.

3. A read page, whole

  1. useParams() gives the route's parameters as strings: { id: "23" }.
  2. The read, named in requests.ts and keyed ['payment', 23, 'receipt']. data is undefined until the answer comes.
  3. The shared CSS classes, from index.css: card is the white panel every page sits in, wide lets it use the page's full width, receipt adds the print layout.
  4. row lays its children out in a line (spread: at both ends). no-print hides this row on paper: index.css's @media print also hides the header and menu.
  5. receipt.paid_on is "2026-09-10", as the backend sends dates; formatDate makes it readable.

Line 14 is the whole loading and error pattern, and nearly every page has it in this form. Learn to see it at a glance: everything below it can assume the data is there.

Every figure here is a field of the answer: paid, interest_paid, principal_paid, owed_after. The page adds nothing up; even the Total row (line 79) shows receipt.total_owed from the backend. num right-aligns a figure in a table cell so the digits line up. And the jewellery is named by its description, not its Mortgage Name (line 62): see nuance (c).

4. Money and dates

Intl.NumberFormat('en-IN') is the browser's own number formatter for Indian English, which groups digits the Indian way: the last three, then pairs (lakhs, crores). Line 13 drops the paise when there are none.

Two different clocks are on this page, and nuance (d) is about the trouble that causes. formatDate reads a business date as midnight UTC and prints it in UTC, so no time zone can move it to the day before. todayIso() asks the browser what day it is.

Nuances

(a) A page that can't load

Predict: open /payments/999/receipt. There's no Payment 999. What does line 14 show, and where does its text come from?

"Payment not found", in red. The backend answered 404 {"detail": "Payment not found"}. The typed client turned it into a BackendError whose message is the detail (chapter 011, lesson 1), and line 14 shows error.message. The page wrote no error text of its own: every refusal on every screen reads as the backend worded it.

Every amount crosses the API as integer paise, and becomes rupees only in formatINR, at the last moment. If you see a figure a hundred times too big, someone skipped it; if you see ₹151,500, someone formatted it by hand. Units are trap #6 (owned by chapter 004).

(c) Descriptions, never Mortgage Names, on what the Customer sees

The Receipt says "Gold chain with Lakshmi pendant", not 2025-Meera-GoldChainPendant. A Mortgage Name is the Lender's own filing label; the Customer knows their jewellery. So anything the Customer reads (a Receipt, a Reminder) names the jewellery by its description (trap #16, owned by chapter 007). The Lender's own screens, like the Mortgage page, use the Mortgage Name.

(d) The two "todays"

The form's default and its max come from todayIso(), the browser's date. Whether a date is in the future is the backend's call, made with its own today (TodayDep, chapter 010, lesson 2). On the Lender's laptop the two agree, because the browser and the backend share one clock. On the served book, held on 19 Oct, they don't. Remember this whenever a form refuses its own default date: set it to 19 Oct 2026. (max only stops the date picker going past the browser's today; the backend is what refuses.)

(e) Dates read "Sept"

The screens write 10 Sep 2026 as "10 Sept 2026". That's not a bug in the app: it's how the browser's Intl.DateTimeFormat abbreviates September for en-IN. The course's prose writes "10 Sep"; the screens, as you'll see them, write "Sept".

Pressing back to the theme the browser would show anyway clears the choice (line 27), so the app follows the browser again. frontend/index.html applies a stored choice in a tiny inline script before the app draws, so a dark-mode Lender never sees a white flash. localStorage is kept per browser and per site, so the choice belongs to this laptop, not to the book. The CSS does the rest: index.css picks its colours from prefers-color-scheme unless data-theme says otherwise.

(g) The words on screen

Every label on a screen is UI copy, and it uses the glossary's words exactly: Customer, never "borrower"; Mortgage, never "loan"; Outstanding, never "balance". Nothing checks this (trap #19, owned by chapter 008), so when you add a label, look the word up in Documentation/GLOSSARY.md.

Quiz

A screen at /customers/7/edit shows a wrong label. Which file do you open?

App.tsx line 54 maps /customers/:id/edit to CustomerFormPage, the same component as /customers/new; it edits when the URL has an id. CustomerPage is /customers/:id, and CustomersPage is the list at /customers.

The Receipt's "Still owed" says ₹81,253. Where was that figure worked out?

The page shows formatINR(line.owed_after) and nothing else; the backend replayed the Ledger to get 8125300. Pages never compute money. formatINR only turns paise into "₹81,253".

You choose the dark theme on the Lender's laptop, then open the app on their phone. Which theme does the phone show?

The choice lives in that browser's localStorage under theme, never on the backend. A browser with no stored choice follows its own prefers-color-scheme.
