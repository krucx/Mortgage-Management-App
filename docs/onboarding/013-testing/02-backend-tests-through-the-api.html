Chapter 013 · Lesson 2

Backend tests through the API

Most backend tests in this repo talk to the app the way the frontend does: they send HTTP requests and read the JSON that comes back. This lesson takes apart the fixtures and helpers that make such a test a few lines long, then has you write one.

By the end you can write a test of a route the way the frontend calls it.

The problem

Say you want to test the Cash Limit (the amount of cash at or above which the Lender is warned on screen; chapter 007). Every test of it needs the same things before it can start: a database with the right tables, the app built on it, a way to send it requests, and a date for "today". Written out in each test, that's a dozen lines of setup before the one line that matters.

Shared setup has its own risk. If two tests share one database, the second sees what the first saved. It passes when run after the first and fails when run alone, or the other way round. Tests that depend on their order are worse than no tests: they fail at random and teach you to ignore failures.

The idea

pytest fixtures give each test a fresh app, on a fresh database, on a fixed today. A fixture is a function pytest runs for you before a test: name it as a test's parameter, and pytest calls it and passes in what it returns. conftest.py defines the fixtures all backend tests share. Then api_seed.py makes test data by sending the same requests the frontend sends, and fails the test at once if the app refuses one.

The flow

Notice that the test never builds anything itself. It names client, and pytest works backwards: client needs database_url, which needs tmp_path (a pytest built-in: a new empty folder per test). So each test gets its own database file, made fresh by the real migrations.

The code

1. The fixtures

  1. The tests' today: 20 Apr 2026, for ever. The app never reads the computer's clock; create_app takes a function that says what day it is (chapter 010, lesson 2). A test that says "Ramesh's chain owes ₹1,09,000 today" stays true next year. Lesson 3 shows what moving it does.
  2. pytest gives tmp_path to any fixture or test that names it. The database is one SQLite file inside it.
  3. TestClient, from FastAPI, sends requests straight into the app in the same process: no server, no port. Using it in a with block runs the app's start-up, which migrates the empty file (chapter 010, lesson 5).
  4. yield instead of return makes a fixture with a clean-up: the test runs at the yield, and when it's done pytest finishes the with block, which shuts the app down.
  5. conn skips the app entirely: a migrated database and a connection to it. Lesson 3.

A file called conftest.py is special to pytest: its fixtures are available to every test file in its folder without an import.

2. Test data through the API

  1. RUPEE = 100 and LAKH = 1_00_000 * RUPEE come from seed.py. Every amount the API takes or gives is in paise, whole numbers (trap #6). Tests write 9_000 * RUPEE or 20_000_00; Python ignores the underscores, so 20_000_00 is 2000000 paise, ₹20,000, grouped the Indian way.
  2. SIMPLE_3 is 3% a month, Simple, a full month charged on redemption: the Terms most tests use, because they make the figures easy to work out by hand (₹3,000 a month on ₹1,00,000). model_dump(mode="json") turns the Pydantic object into the dict the API expects.
  3. Every helper checks for 201 Created. If the app refuses, the assertion's message is response.text: the backend's own reason.
  4. The default Customer is the tests' Ramesh Kumar. Two Customers need two different Primary Numbers, or the second is refused (chapter 008).
  5. For tests that need a crowd (paging, sorting): nth_person(client, 7) is "Customer 07" on 9829000007.
  1. By default lend makes the tests' standard Mortgage: ₹1,00,000 against a 19 g chain, from 14 Jan 2026, on SIMPLE_3. On the tests' today it owes ₹1,12,000 (three months' ₹3,000, and the month under way, charged in full).
  2. Every helper ends with **fields, so a test can add or change any field of the request without a new helper.
  3. A Payment is given as its Allocations, one amount per Mortgage; pay works out the total.

3. The pattern: test_cash_limit.py

  1. The module's docstring states the rule under test in business words. Read it first: it's the spec.
  2. A small helper per request, with its status check inside, so each test reads as a sentence about the business.
  3. Test names are sentences about behaviour, in glossary words: "the Cash Limit is ₹20,000 unless changed", not test_get_settings_2. When it fails, the name says what broke. Use the glossary's words exactly, and none of its Avoid words: nothing checks this for you (trap #19).
  4. A setting is checked twice: what the save answered, and what a fresh read says. A save that answers right but stores wrong is caught.
  5. A refusal is tested by its status, with the request written out, since the helper would fail on anything but 200.

4. A test with data: test_call_list.py

  1. api_seed and seed are imported like installed packages, though they're just files in tests/. Why that works, and its catch, is nuance (c).
  2. A helper that boils the answer down to just what the tests compare: a list of (Mortgage Name, reasons). Assertions on a short tuple read better, and fail with a readable diff.
  3. A fixture of this file's own: a test that names ramesh gets a Customer already made. Fixtures can use other fixtures (client), and pytest makes each once per test.
  4. pytest.approx: a float compared within a tiny tolerance. Loan-to-Value is a ratio of two money figures, so it's a float; == on floats can fail by the last digit. Money itself is never a float (it's whole paise), so money is compared with ==.

Run-through: a test of your own

The Cash Limit's tests cover the default, a change, a clearing and a refusal. One thing is missing: once cleared, can the Lender turn the warning back on? Add this at the end of backend/tests/test_cash_limit.py:

def test_the_cash_limit_can_be_set_back_to_20000_rupees_after_being_cleared(client):
    set_cash_limit(client, None)

    assert set_cash_limit(client, 20_000_00) == {"cash_limit": 20_000_00}
    assert cash_limit(client) == {"cash_limit": 20_000_00}

Arrange (clear it), blank line, act and assert. Then run the file:

A test you've only seen pass hasn't shown you it can fail. Make it fail on purpose.

Predict: change both 20_000_00 in your test to 20_000, as if you'd written rupees. What does pytest print?

E       AssertionError: assert {'cash_limit': 2000000} == {'cash_limit': 20000}
E         Differing items:
E         {'cash_limit': 2000000} != {'cash_limit': 20000}

It fails at the first assert: the app saved ₹200 (20,000 paise) and answered so, and the test expected 2000000. pytest rewrites every plain assert to print both sides, so you see the two numbers without a debugger. A factor of 100 in a failure is almost always rupees written where paise were meant (trap #6).

From scripts/run_throughs.sh, section L2.

Put it back to 20_000_00. Keep the test or drop it (git checkout -- tests/test_cash_limit.py); it's a fine test, but this course doesn't commit it for you.

Nuances

a. No test depends on another

Each test's database is a new file in its own tmp_path, built by the migrations. Your new test cleared the Cash Limit, and the next test still saw ₹20,000. You can run any one test alone, or all of them in any order, and get the same result. Never write a test that needs another to have run first; if two tests need the same data, give them a fixture (like ramesh) or a helper.

b. A refused seed fails with the app's own reason

Predict: a test calls lend(client, {"id": 99}), lending to a Customer that was never made. Where does it fail, and with what message?

E       AssertionError: {"detail":"Customer not found"}
1 failed

It fails inside _created, before the test's own assertions, and the message is the backend's answer, word for word. A test whose setup the app refuses never gets to assert something false about an impossible state. Lesson 3 gives the layer below the API the same guarantee.

From scripts/run_throughs.sh, section L2.

c. Why it's api_seed.py and not http.py (trap #18)

backend/tests/ has no __init__.py, so it isn't a package. pytest, in its default import mode, puts the folder of such a test file at the front of Python's import path (sys.path) before importing it. That is what lets a test write import seed or from api_seed import lend.

It also means any file in tests/ wins over a module of the same name anywhere else, including Python's own. Python's standard library has a module called http, and FastAPI imports it.

Predict: copy api_seed.py to tests/http.py (a natural name for "helpers that make HTTP requests") and run uv run pytest. What happens?

ImportError while loading conftest '…/backend/tests/conftest.py'.
E   ImportError: cannot import name 'APIRouter' from partially initialized module 'fastapi'
    (most likely due to a circular import)

Not one test runs. conftest.py imports FastAPI; FastAPI's start imports http and gets your tests/http.py; that imports seed, which imports the app, which imports FastAPI, which is only half loaded. The message blames a circular import in FastAPI, and says nothing about your file. That's why api_seed.py's docstring explains its own name. Delete the file to recover.

From scripts/run_throughs.sh, section L2.

Trap #18. Never name a file in backend/tests/ after a standard-library module: http.py, json.py, types.py, email.py, calendar.py…

d. Through the API is the default

Most backend test files use client, because that's how the Lender's actions arrive: as requests from the frontend. A test through the API checks the route, the request and answer models, the status codes and the logic behind them in one go, and it keeps passing when the code behind the route is reorganised. Lesson 3 is about when to go below it.

Quiz

A new test calls pay(client, ramesh, {chain["id"]: 9_000}), meaning ₹9,000 of interest. What does the Payment really pay?

Every amount in the API and in the helpers is whole paise; nothing converts. ₹9,000 is 9_000 * RUPEE (900000). The test runs, pays ₹90, and probably fails later with a figure 100 times off (trap #6).

Your test saves a Cash Limit of ₹5,000. Another test, run right after it, reads the Cash Limit. What does it read?

database_url is built from tmp_path, a new folder for each test, and client migrates a new file in it. Nothing is shared between tests, so nothing needs cleaning up.

A test's call to person(client, "Sita Devi") fails before any of the test's own assertions. What's the likeliest reason?

person's phone defaults to 9829012345. If the test already made Ramesh with the default, Sita on the same Primary Number is refused, and _created fails with the backend's reason. Give her her own: person(client, "Sita Devi", "9829054321"), as test_call_list.py does. The address defaults to "", and client tests don't use conn.

Go deeper

Read tests/test_call_list.py whole (about 150 lines): its tests build each situation in two or three lines with person and lend, and the comments say what the figures will be. Then pytest's own guide to fixtures, for yield fixtures and how they're shared through conftest.py.
