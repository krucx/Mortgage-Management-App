Chapter 013

Testing

The problem this chapter solves

The Lender trusts the app with money. When it says Meera owes ₹83,333, they ask her for ₹83,333. If a change to the code quietly moves that figure by a rupee, nobody reminders until a Customer argues with a Receipt. There's one developer, no QA team, and the app runs on a laptop the developer never sees. So the tests are the only thing between a change and the Lender's book.

Tests only help if they are cheap to write and say something true. A test that seeds an impossible history (a Payment larger than what was owed, a Mortgage paid before it started) passes while proving nothing. A test that reads the real clock passes today and fails next month. A page test that talks to a real server is slow and breaks when the data changes. And a passing suite says nothing about a line that no test reaches.

This codebase answers each of these with a small set of tools: every check CI runs, runnable on your machine; fixtures that give each test its own fresh database and a fixed today; two seed layers that make test data through the app's own changes, so the app refuses an impossible seed; a fake backend for page tests that answers like the real one; and a habit of breaking a line to see whether any test reminders.

What you'll be able to do

  • Run locally everything CI runs (and the one check it doesn't), and run one test on its own.
  • Write a backend test of a route the way the frontend calls it, with client and api_seed.py.
  • Choose the layer for a test (pure, seed with conn, or client with api_seed) and seed a realistic history.
  • Write a frontend page test against fakeServer with showPage, and a plain unit test.
  • Check whether a line is pinned by a test, and write the missing test when it isn't.

Before you start

This chapter builds on how the code is put together, and links back rather than teaching it again:

  • Where "today" comes from. Chapter 010, lesson 2: the app never reads the clock itself; create_app(today=…) injects it, and most tests set it to 20 Apr 2026.
  • How a test's database is built. Chapter 010, lesson 5: every test's database is made by the real migrations, and the drift test.
  • Changes, refusals and History. Chapter 006: every change goes through one module that refuses, writes, checks and records History. The seeds in this chapter use those same functions.
  • The typed client and the cache. Chapter 011: pages ask the backend only through the typed client (trap #11), and the contract tests that keep both sides' types in step (trap #10).
  • Pages. Chapter 012: ChangeTermsPage (lesson 2) and StartGate (lesson 6), whose tests this chapter reads.

You need the backend's and the frontend's dependencies installed (uv sync in backend/, npm install in frontend/; chapter 002, lesson 5). You don't need the sample book or a server: no test in this repo uses either.

A different cast. Until now the course used the sample book, served on 19 Oct 2026. The tests have their own cast, and this chapter uses it: Ramesh Kumar (Primary Number 9829012345) and his gold chain, ₹1,00,000 lent on 14 Jan 2026 at 3% a month, Simple, full month (SIMPLE_3); and, in the frontend, Asha Rao's chain (Mortgage 7, owing ₹50,750). The tests' today is 20 Apr 2026. The sample book is a story for screenshots and lessons; the tests' data is made fresh in each test, as small as the test needs.

Every lesson has you change a line of code and run the tests. Each one says how to undo it (git checkout -- <file>). Run git status --short at the end of each lesson: it should print nothing.

The map

Notice that the backend has three ways in, from the outside to the inside: through HTTP like the frontend (client), through the change functions (conn), or straight into a pure function with no database at all. Choosing among them is most of lesson 3.

Lessons

  1. Every check, and how to run itThe test workflow's jobs, local tests and lint; one test on its own; and the separate CodeQL and Trivy scans.
  2. Backend tests through the APIconftest.py's fixtures, api_seed.py's helpers, test_cash_limit.py as the pattern; then write a test of your own, and make it fail.
  3. Below the API: seeds and pure testsThree layers, and how to choose; seed.py makes each change on its own date; move today one day and watch 48 tests fail.
  4. Frontend tests: fakeServer and showPageA page rendered as the app renders it, against a fake backend; ChangeTermsPage.test.tsx line by line; a test of your own; why the fake's 404 matters.
  5. Finding what no test pinsBreak a line, run the tests, look. The Loan-to-Value boundary and StartGate's 5xx: delete the real test, write your own, compare.
  6. Check yourselfWhich layer, which today, which answer? Then make seed.py record every Payment on the tests' today, and see what refuses.

Written against commit bda77f1. Every count, test name and failure message came from scripts/run_throughs.sh. It checks out the current commit into a throwaway git worktree, runs the local test and lint checks and the pages comparison, then makes each lesson's change to one line, runs the tests and undoes it, so your clone is never touched. Hosted scans and the container smoke check are separate. Run it from the repo root with sh docs/onboarding/013-testing/scripts/run_throughs.sh. Pester runs in the image scripts/pester.Dockerfile builds.

Anything unclear? Ask an agent in this repo to explain it: a fixture, why a test is written the way it is, or why a test you wrote fails. If something here looks wrong, open an issue (see Documentation/agents/issue-tracker.md).
