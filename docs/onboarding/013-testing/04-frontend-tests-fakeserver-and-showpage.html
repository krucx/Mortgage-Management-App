Chapter 013 · Lesson 4

Frontend tests: fakeServer and showPage

A frontend page test draws a real page and clicks it, the way the Lender would, with a stand-in for the backend that answers only what the test says. This lesson reads the two small files that make that work, then one real test line by line, then has you write one.

By the end you can write a page test against a fake backend, and a plain unit test.

The problem

A page is worth testing as a whole. "Type a new rate, see a Preview, press Save, confirm, end up back on the Mortgage" spans a form, the Preview hook, a dialog, a save and a navigation (chapter 012, lesson 2). Testing each piece alone misses the bugs between them.

But a page asks the backend for things, and in a test there's no backend. You could start a real one with a sample book. Then every test is slow, depends on the book's data, and breaks when a figure changes. You could replace the page's data hooks with fakes. Then the cache, the invalidation after a save and the request bodies (chapter 011) are never tested, and that's where the subtle bugs live.

The idea

Fake only the network. Everything inside the browser is real: the page, the router, the typed client, the cache. Only the last step, the HTTP request leaving the browser, is answered by fakeServer: a table of "METHOD /api/path" → answer, written by the test. showPage renders a page inside all the real wrappers, wired to that fake.

The flow

Notice the dead end at the bottom: the browser's own fetch is replaced by one that throws. A page that skips the typed client fails its test (trap #11).

The code

1. fakeServer: a table of answers

  1. The key is the method and the path, without the query string: GET /api/mortgages/7. A test that cares about ?as_of=… reads it from the request in a function answer.
  2. Every request is recorded, in order, answered or not.
  3. Not in the table: 404 {"detail": "Not Found"}, what FastAPI answers for a route it doesn't know. Nuance (b) shows why it matters.
  4. An answer can be a function of the request. It can read the body (await request.json()), count calls, or answer differently the second time.
  5. A plain object is sent as JSON with status 200. A test that needs another status returns a Response itself: new Response('Bad Gateway', { status: 502 }), or Response.json({ detail: '…' }, { status: 422 }) for a refusal.
  6. The shape every change's Preview answers with (chapter 006): the Mortgages it touches, and the cash sums it would write.

2. showPage: the page as the app draws it

  1. When the page navigates somewhere the test didn't give a page for, the screen says "Now at /mortgages/7". A test asserts where a save took the Lender by finding that text.
  2. vi.stubGlobal replaces a global for this test file (undone by vi.unstubAllGlobals()). Any fetch that doesn't go through the client throws.
  3. The app's own createServerState (chapter 011, lesson 2), given the fake's fetch. retry: false: in the app a failed read is tried again, which in a test would only slow a failure down; here it fails at once.
  4. MemoryRouter is React Router with the URL kept in memory instead of the address bar, starting at at.
  5. The state, so a test can look into the cache (state.queryClient) if it needs to.
  1. Asha Rao's gold chain: ₹50,000 at 1.5% a month, owing ₹50,750. Typed as Mortgage, the generated type, so when the backend's model changes (trap #10), npm run typecheck points at this fixture. Tests spread it and change one field: { ...mortgage, status: 'redeemed' }.
  2. The coming Accrual Dates are in 2099. The Change Terms form starts on the first of them that is after the browser's real today (free.find((day) => day > today) in ChangeTermsPage.tsx): the frontend has no injected today like the backend's. With 2099 dates that is always 10 Nov 2099, which the test below asserts. Dates in this year would pick a different default once the real calendar passed the first.

vitest runs this before every test file (setupFiles in vite.config.ts). The confirmation before every save is a <dialog> (ConfirmDialog, chapter 012), and jsdom doesn't implement showModal(). This fills the gap with the two lines a test needs. If you hit another browser feature jsdom lacks, this is where its stand-in goes.

3. A page test, line by line

  1. Lesson 1, nuance (b): page tests need jsdom.
  2. Testing Library's cleanup removes what render drew, so the next test starts on an empty screen.
  3. Undoes showPage's stubGlobal.
  4. The smallest Preview that type-checks: nothing changes. This test is about the form's flow, not the figures.
  1. The page reads the Mortgage first; Asha's chain answers.
  2. Function answers that keep every request body, so the test can check what the page sent.
  3. findBy… waits (up to 1 s by default) for the element to appear, since the page shows "Loading…" first. Elements are found the way a person finds them: by their label, role or text, never by CSS class. fireEvent.change types 2 into the field.
  4. The Preview is asked 400 ms after the last key (chapter 011, lesson 4), so this waits up to 2 s for the text BeforeAfter draws for it.
  5. The Preview was asked for the right change: 200 basis points from the first coming Accrual Date. toMatchObject checks only the fields named.
  6. Save, confirm in the dialog, and the page navigated to the Mortgage: Elsewhere says so.
  7. And what was saved is exactly what was previewed. The Lender confirms what they saw.

The second test (lines 55–92) starts on the Mortgage page with both pages routed, saves a Term Change, and checks that the Mortgage page shows it as "coming" at once. Its fake GET /api/mortgages/7 never answers after the save (new Promise(() => {})), so the only way the page can show the change is from what the save returned: it tests the cache update of chapter 011, lesson 5, through the screen. Lines 121–133 assert on server.requests, with toContain, that the removal was previewed before it was made.

4. A pure test

No page, no server, no DOM: a function in, a value out. allocateEqually suggests how the Payment form divides an amount (chapter 012, lesson 3). The two little helpers on lines 4–5 let each case be written in rupees and still pass paise to the code (trap #6). describe groups tests under a heading; it is another name for test. For any logic you can pull out of a page into a plain function in src/, test it this way.

Run-through: a page test of your own

Create frontend/tests/TryMortgagePage.test.tsx:

// @vitest-environment jsdom
import { cleanup, screen } from '@testing-library/react'
import { afterEach, expect, test, vi } from 'vitest'
import { MortgagePage } from '../src/pages/MortgagePage'
import { fakeServer } from './fakeServer'
import { mortgage, showPage } from './showPage'

afterEach(() => {
  cleanup()
  vi.unstubAllGlobals()
})

test('the Mortgage page shows whose jewellery it is and what it owes', async () => {
  const server = fakeServer({ 'GET /api/mortgages/7': mortgage })
  showPage(server, '/mortgages/7', { '/mortgages/:id': <MortgagePage /> })

  expect(await screen.findByRole('link', { name: 'Asha Rao' })).toBeTruthy()
  expect(screen.getAllByText('₹50,750').length).toBeGreaterThan(0)
})

Run it with npx vitest run tests/TryMortgagePage.test.tsx: 1 passed. (getAllByText, because ₹50,750 is on the page more than once.)

Your fake answers only one route. What else did the page ask for? Add a second test that makes the fake tell you:

test('what the Mortgage page asks for', async () => {
  const server = fakeServer({ 'GET /api/mortgages/7': mortgage })
  showPage(server, '/mortgages/7', { '/mortgages/:id': <MortgagePage /> })

  await screen.findByRole('link', { name: 'Asha Rao' })
  await new Promise((resolve) => setTimeout(resolve, 300))
  expect(server.requests).toEqual([])
})

Nuances

a. The cache is real, so it's tested too

Because showPage uses the app's own createServerState, whatever a save makes stale is asked again in the test as in the app, and shows up in server.requests. A test can check that a save didn't ask for the Mortgage again, or that it did. Chapter 011's serverState.test.tsx tests the rules themselves; page tests catch a page that forgets to use them.

b. Why an unknown request is a 404, not an empty answer

Most page tests route only what they're about, as yours did. Everything else gets the 404 the real backend would give an unknown route. What if the fake were "friendlier"?

With them, uncaught errors such as TypeError: notes.map is not a function and TypeError: rates.map is not a function. The Call Notes panel was told "here are your notes: {}", trusted its types, and called .map on an object; one panel's crash took the whole page down. A 404 is a failed request, which every panel already handles; an empty 200 is a lie in the wrong shape. The fake answers as the backend would, so pages are tested against answers they can really get.

c. Calling fetch fails the test

A page that calls fetch directly while a test draws it throws "fetch called outside the typed client: …". That's the test-time half of trap #11; the other half is npm run lint (lesson 1), which CI doesn't run.

d. Change a backend model, regenerate the types

The fixtures are typed with the types generated from the backend's OpenAPI schema. Rename a field in a backend model and forget npm run gen:types, and the backend's test_openapi.py fails (the checked-in schema is stale), and once you regenerate, npm run typecheck fails on every fixture and page that used the old name (trap #10, chapter 011, lesson 1). Both suites, on purpose.

Quiz

A page test routes only GET /api/mortgages/7. The page also asks for /api/mortgages/7/history. What does it get?

Anything not in the fake's table is answered 404 {"detail": "Not Found"} and recorded in server.requests. Only a function answer that returns a never-settling promise makes a request wait, as ChangeTermsPage.test.tsx's second test does on purpose.

After a save, the page should go back to /mortgages/7. The test routes only /mortgages/:id/terms. How does it check?

Any path the test gave no page for draws Elsewhere, which prints "Now at" and the path. MemoryRouter keeps the URL in memory, so window.location doesn't change. And a request for the Mortgage proves a read, not where the Lender ended up.

Why are the shared mortgage fixture's coming Accrual Dates in 2099?

The frontend has no injected today: it uses the browser's (chapter 012, lesson 1). The Change Terms form starts on the first coming date after it. Dates in 2099 stay after it, so the default is always 10 Nov 2099, and the test's effective_on: '2099-11-10' holds whatever day it runs. The fake backend refuses nothing it isn't told to.
