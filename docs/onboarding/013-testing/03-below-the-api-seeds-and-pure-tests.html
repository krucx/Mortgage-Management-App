Below the API: seeds and pure tests

Not every test should go through HTTP. Some code has no route of its own, some tests need a history spread over months, and the Ledger engine needs no database at all. This lesson shows the two layers below the API, the seed module that feeds the middle one, and why the tests hold "today" still.

By the end you can choose the layer for a test (pure, seed with conn, or client with api_seed) and seed a realistic history.

The problem

Notices are queued a few days before each Accrual Date by a function, notices.sync, that the daily run calls (chapter 009). There's no route that means "run sync on 12 May". To test it through the API, you'd have to build an app whose today is 12 May, and another for 13 May, and so on. And the Ledger engine is pure arithmetic: going through HTTP and a database to test that 3% of ₹1,00,000 is ₹3,000 is slow and hides the arithmetic behind a lot of machinery.

So test below the API. But then where does the test data come from? The obvious answer is to INSERT rows straight into the tables. That's fast, and dangerous: an insert happily writes a Payment larger than what was owed, or a Customer on someone else's Primary Number. The app would never allow either. A test that starts from a state the app can't reach proves nothing about the app.

The idea

Three layers, each with its own way in. Through HTTP (client and api_seed.py, lesson 2). Through the change functions, on a bare database connection (conn and seed.py). Or straight into a pure function, with no database at all.

seed.py makes data the way the app does: through the same change functions the routes call, each change made on its own date, as the Lender would have made it that day. A seed the app would refuse is refused, and History is written as usual.

The flow

Notice that seed.py and api_seed.py are not two ways of writing rows. They are two doors into the one module that changes the book (chapter 006). So both are refused by the same rules.

The code

1. seed.py: the docstring is the design

  1. The same Terms as api_seed.SIMPLE_3 (which is built from this one): 300 basis points, 3% a month, Simple, a full month charged on redemption.
  2. Every change function takes a now for History's timestamp. _at makes it 10:00 on the change's day, so a test can assert on History without the real clock making each run different.

2. Each change on its own date

  1. changes.create_mortgage is the function POST /api/mortgages calls. Same checks, same History.
  2. Names are <start year>-Ramesh-<suffix>: "2026-Ramesh-Chain", "2026-Ramesh-Ring". The name is given, even for another Customer's Mortgage, so tests can assert on it.
  3. The third argument is the change's today: the day the change is made. A Mortgage is made on its start date.

The rest of the file is the same shape. add_term_change passes on, the Accrual Date it takes effect; redeem, forfeit and waive pass the day of the Closure, and redeem and waive return the Final Payment's id (lines 118–162).

3. The tests that the seeds refuse

  1. pytest.raises passes only if the code inside the with raises that exception. Here, ₹2,00,000 on a Mortgage that owes much less.
  2. Below the API, a refusal is FastAPI's HTTPException, raised by the change function itself; the route only lets it through. So it carries the status the frontend would have got: 422 (the request can't be done), 409 (it clashes with what's saved).
  3. Both Customers default to 9829012345. The second is refused, as it would be on the Customer form.

Line 14's comment says the chain owes ₹1,09,000 on 15 Apr; by the app's own figures it owes ₹1,12,000 that day (the three months to 14 Apr, and the month from 14 Apr, charged in full: scripts/figures.py). Either way ₹2,00,000 is too much, so the test is right; a comment in a test is still just a comment.

4. A conn test, and a pure one

  1. A conn test has no app, so conftest.TODAY means nothing to it. Each call is given its date. This file works in May, when the 14 May Accrual Date is two days away.
  2. Ramesh's chain, by seed.py's defaults.
  3. The function under test, called directly with the day to run as. No route does this.
  4. [notice] = … unpacks a list that must have exactly one item: if sync queued none or two, the line raises. A short way to assert "exactly one".
  5. Customer-facing text names the jewellery, never the Mortgage Name (trap #16).
  1. compute_ledger takes facts (a start date, a Principal, Terms, a date) and returns the Ledger's steps. No database, no app: the engine of chapter 004, which ADR 0001 keeps pure on purpose.
  2. A helper that turns steps into tuples in rupees, so each test's expected Ledger is a short, readable table.

Trap #17: the tests' today is 20 Apr 2026, not the sample book's 19 Oct 2026. And below the API there is no single today: seed.py makes each change on its own date. When a test's figures look off by a month, check which today it runs on. In a client test, a Payment dated after 20 Apr is refused as "in the future".

b. Why each change gets its own date

Every change function takes a today and refuses what would be in the future: _refuse_payment starts with if payment.paid_on > today: raise unprocessable("The Payment date cannot be in the future") (lending/changes.py, line 258). seed.py could pass one date for every change. It passes each change's own date instead, because that's what really happened: the Lender recorded the 10 Mar Payment on 10 Mar. So the seed meets the checks the app would have made that day, no more and no less. The check-yourself exercise has you pass one fixed date instead, and see what breaks.

c. Seeds write History

Because seeds go through the change functions, every seeded change is in History, timed 10:00 on its day by _at. A test that reads History after seeding sees the rows the app would have written, at predictable times. A seed made by INSERT would leave History empty, and a History test would be testing a book the app never writes.

d. conn commits at the end

conn is one transaction for the whole test (engine.begin()), committed when the test ends. Everything a conn test does sees everything it did before, as one Lender's session would. Since each test has its own file, the commit never reaches another test.

Quiz

You're adding a rule to the Ledger engine: a part month at the end of a Mortgage is charged by the day. Where does its first test go?

A figure the engine computes is tested pure: facts in, steps out, in a fraction of a millisecond, with no database to get in the way. Add a test through the API too if a route's answer changes, but the rule itself belongs with the engine.

A conn test seeds a Payment with add_payment(conn, ramesh, date(2026, 6, 1), …). Is it refused as "in the future"?

add_payment passes paid_on as the change's today, and conn tests have no app, so conftest.TODAY isn't involved. Every other refusal still applies: that's the point of seeding through the change functions.

Why does seed.py call changes.record_payment instead of inserting a payment row?

The change function makes the app's checks (an overpayment is a 422) and writes History. An insert does neither, so a test could start from a book the app could never have, and pass while proving nothing. Nothing stops an insert; it's a choice.
