Chapter 013 · Lesson 1

Every check, and how to run it

Every push to main runs tests and lint on GitHub; separate hosted workflows scan the code and container for security issues. This lesson covers the local checks and what the hosted scans do.

By the end you can run the project tests and lint locally, and explain the security scans that run on GitHub.

The problem

This project has one developer, who commits straight to main. There are no pull requests and no reviewer. So when a check fails on GitHub, main is already broken: the next release would be cut from broken code, and the Lender's next update would install it.

"Run the tests before you push" sounds like enough, but "the tests" is really several different tools in two languages, plus PowerShell. Run pytest alone and you miss a type error that mypy would have caught. Run npm test alone and you miss a type error in a page, because vitest doesn't type-check. Each tool catches a different kind of mistake, so you need to know the whole list.

The idea

The test workflow is a short list of checks you can run locally. .github/workflows/test.yml covers backend types and tests, frontend types, lint and tests, plus a container smoke check, a Pages file comparison, Windows checks and tests for the security-alert automation. CodeQL and Trivy run as separate hosted workflows; they need GitHub's scanning services and don't belong in the local command list.

The flow

The release workflow runs this file before it publishes anything. A failed job stops the release (chapter 015). CodeQL and Trivy are separate scheduled and push-triggered scans; the automation records critical findings and secret-scanning alerts as issues.

The code

1. The two jobs you'll run every day

  1. workflow_call lets another workflow use this one as a step. release.yml does, so a release runs every check first.
  2. mypy checks the backend's type annotations without running anything. Note the folder: src. It checks the app's code, not the tests.
  3. pytest runs every backend test.
  4. npm run typecheck is tsc -b: the TypeScript compiler checks every type and writes nothing. It covers tests/ as well as src/.
  5. npm run lint runs oxlint, including the rule that bans direct fetch calls outside the typed client.
  6. npm test is vitest run: every frontend test, once. (Plain vitest would keep watching your files and rerun them.)

2. Where each tool is set up

  1. pytest collects every test_*.py file in backend/tests/, and every function in it whose name starts with test_.
  2. strict turns on all of mypy's optional checks: every function needs its argument and return types, and nothing may silently be Any. So src/ is fully typed. The tests aren't type-checked at all, which is why most of them have no annotations.
  3. Pydantic models (every …In body a route accepts) build their __init__ at run time. The plugin tells mypy what fields they take, so PaymentIn(amount="lots") is an error before anything runs.
  1. tsc -b is also the first step of a build. A type error that slips past you still stops npm run build, and so the Docker image.
  2. oxlint: a linter, a tool that reads code for patterns that are legal but wrong. Below.
  3. Not a check, but it decides whether two of them pass: after changing a backend model, regenerate the frontend's types (trap #10, chapter 011).

vitest's own settings are a few lines at the end of vite.config.ts: it runs tests/**/*.test.{ts,tsx}, and loads tests/setup.ts first (lesson 4).

3. The rule enforced by lint

This is trap #11, taught in chapter 011: every request goes through the typed client, so it is type-checked, cached and made stale by saves. The next rules in the file ban window.fetch, globalThis.fetch and self.fetch too. oxlint enforces the rule, and the frontend CI job runs it.

One test at a time

While you work on one thing, run only its tests. Both runners filter by name:

cd backend  && uv run pytest -k cash_limit -v
cd frontend && npx vitest run -t "Term Change"

Predict: test_cash_limit.py has four tests. How many does -k cash_limit run?

Five. -k matches any test whose name, or file name, contains the words:

FileTest
test_cash_limit.pytest_the_cash_limit_is_20000_rupees_unless_changed
test_cash_limit.pytest_the_lender_can_change_the_cash_limit
test_cash_limit.pytest_clearing_the_cash_limit_turns_the_warning_off_and_it_stays_off
test_cash_limit.pytest_a_cash_limit_of_nothing_is_refused
test_lent_through.pytest_cash_above_the_cash_limit_is_lent_all_the_same

"5 passed, 704 deselected". The fifth is a test in another file that happens to say "cash limit" in its name. That's usually what you want: everything about the Cash Limit. For exactly one file, name it: uv run pytest tests/test_cash_limit.py. For exactly one test, add :: and its name.

vitest -t "Term Change" works the same way on test names: it runs the 4 tests in ChangeTermsPage.test.tsx and skips the other 226. To run one file, give its path: npx vitest run tests/ChangeTermsPage.test.tsx.

The lint catches a request that tests miss

Now see what only the lint catches. In frontend/src/money.ts, add one line at the end:

export const sneaky = () => fetch('/api/customers')

Predict: which of npm run typecheck, npm test and npm run lint fail?

CommandResult
npm run typecheckpasses: fetch is a perfectly typed browser function
npm test230 passed: no test calls sneaky
npm run lintsrc/money.ts:27:29: error eslint(no-restricted-globals): Unexpected use of 'fetch'. Ask the backend through the typed client (src/serverState.ts, src/requests.ts), never with fetch directly.

Only the lint fails. CI runs the same command, so this mistake blocks a push check. (If a page called fetch while a test drew it, the test would fail too: showPage replaces fetch with one that throws. Lesson 4.)

Undo it with git checkout -- src/money.ts. With the code clean, npm run lint prints nothing at all.

Pester, in Docker

The Windows scripts in windows/ (Setup, Run, Uninstall) are PowerShell. Their own decisions, such as which release is newest and whether to use Docker, are tested with Pester, PowerShell's test framework, in windows/tests/. CI runs them on a Windows machine.

On a Mac, don't install PowerShell; run Pester in a small Linux container instead. The image is Debian with PowerShell's own Linux release unpacked into it, and Pester installed. scripts/pester.Dockerfile builds it. From the repo root:

docker build -t mm-pester -f docs/onboarding/013-testing/scripts/pester.Dockerfile .
docker run --rm -v "$PWD:/repo:ro" -w /repo mm-pester pwsh -NoProfile -c 'Invoke-Pester windows/tests'

It ends with Tests Passed: 65, Failed: 0, Skipped: 0: 55 tests in Launcher.Tests.ps1 and 10 in Uninstall.Tests.ps1, in under two seconds once the image is built. The repo is mounted read-only (:ro), so the tests can't change your clone.

Use this image, not another. On this project's Apple-silicon Mac, Microsoft's own mcr.microsoft.com/powershell image hung, so the Dockerfile starts from plain Debian and unpacks PowerShell's linux-arm64 release. On an Intel or AMD machine, change linux-arm64 to linux-x64 in it.

What those tests check, and the rest of the windows job, is chapter 014's.

Nuances

a. mypy doesn't read the tests; tsc does

The backend's CI command is mypy src, so a type mistake in a backend test is caught only when the test runs. The frontend's tsconfig.app.json includes "src" and "tests", so npm run typecheck checks the frontend's tests too. A test whose fake answer has the wrong shape for Mortgage fails the type check, not just the test. That is part of why the frontend fixtures are typed (export const mortgage: Mortgage = …, lesson 4).

b. vitest runs in Node unless a file asks for a browser

Vitest runs each test file in plain Node by default, where there is no document. A file that draws a page starts with the comment // @vitest-environment jsdom, which gives it jsdom: a browser's DOM, written in JavaScript. 27 of the 34 test files have it. The other 7 (allocate, format, money, sort, weight, idNumbers, api-types) test plain functions and don't need it. Forget the line in a new page test and it fails with document is not defined.

c. vitest doesn't type-check

Vitest strips the types and runs the JavaScript. A test can pass with a type error in it, so npm test green and npm run typecheck red is possible. That's why CI runs both.

Quiz

You add window.fetch('/api/backups') to a page that no test draws, then run the frontend checks. What happens?

mypy reads only the backend. tsc checks types, and window.fetch is well typed. The frontend CI job runs oxlint, whose no-restricted-properties rule rejects window.fetch. No test draws the page, so the test-time guard would not run.

You want to run only the four tests in backend/tests/test_cash_limit.py. Which command does exactly that?

A path runs that file. -k cash_limit matches by substring and also runs test_lent_through.py's test_cash_above_the_cash_limit_is_lent_all_the_same: five tests. -k takes name expressions, not paths; a dot in it is an error.

A frontend test file passes { id: 'seven' } where a Mortgage is expected. npm test passes. What does CI say?

vitest strips types without checking them, but tsc -b includes tests/ (tsconfig.app.json), so the frontend job fails at its typecheck step. oxlint runs in CI too, but checks code patterns rather than TypeScript types.
