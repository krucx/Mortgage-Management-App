Chapter 013 · Lesson 5

Finding what no test pins

709 passing tests tell you nothing about a line that none of them reaches. This lesson is a quick, honest way to find out whether a line is pinned (held in place by a test that fails if it changes): break it on purpose and see whether anything reminders. Then you write the missing test, on two real lines.

By the end you can check whether a line is pinned by a test, and write the missing test.

The problem

The Call List puts a Mortgage on it when its Loan-to-Value is above 85% (chapter 009, lesson 1). Above, not at. Someone tidying the code changes > to >=, believing it's the same thing. Every test passes. Now a Mortgage at exactly 85% is listed, and the Lender phones a Customer who has done nothing wrong.

That's the trouble with a green suite: it proves the tests pass, not that the code is covered. A coverage tool would report the line as run, because many tests run it. Running a line isn't pinning it: no test cared which side of 85% it chose.

The idea

Break the line, run the tests, look. If something fails, the line is pinned, and the failure tells you by what. If nothing fails, no test cares what that line does. Write a test that fails on the broken line and passes on the real one. Then put the line back.

This is a hand-made version of what mutation testing tools do automatically to every line (mutation testing). By hand, you do it to the lines that matter: the boundaries, the filters, the rules.

The flow

Notice the middle loop. A test written after the code tends to pass first time, which feels good and proves nothing: it might pass whatever the line says. Seeing it fail on the broken line is what makes it a test of that line.

Nuances

a. A filter every caller repeats

Some lines are unpinned for a subtler reason. Replay.dormant() says a Mortgage is Dormant if it is Active and owes nothing (chapter 005, lesson 5):

But every caller (the Dormant list in closing.py, the Call List, the Reminders) only ever passes it Active Mortgages: closing.py line 64 selects .where(mortgage_table.c.status == MortgageStatus.ACTIVE) before it asks. So deleting line 184 changed no answer any route gave, and no test failed. That was #113.

It's a conn test (lesson 3) that seeds a Redeemed, a Waived off and a Forfeited Mortgage and calls replay(conn, mortgage).dormant(TODAY) on each directly. From scripts/run_throughs.sh, section L5.

The lesson: passing tests don't prove a line is pinned, even when the line is run. If its callers already guarantee what it checks, it's dead weight to them and a trap for the next caller. Pin it where it is, at the lowest layer that can reach it.

b. Which lines to try it on

Every line is too many. Try it on the lines where a small slip changes what the Lender sees: comparisons with a limit (> against >=, < against <=), status checks, filters on Active, the rounding of a rupee, the order of steps inside a day (trap #7). And on any line you just changed: before you push, break your own new line and check that your new test fails.

c. Another kind of gap: tests that compare two lists

#115 was a gap of a third kind: nothing compared db.py's Tables with the schema the migrations build, so a column declared in one and not the other slipped through. It's closed by the drift test (chapter 010, lesson 6). When two things must agree and are written by hand in two places, look for a test that compares them.

d. When you find a gap and can't fix it now

File it, as #113–#116 were, with the line, the break that nothing caught, and the test that would. Use the issue tracker (Documentation/agents/issue-tracker.md). A known gap is better than a forgotten one.

Quiz

You change a < to <= and all 709 tests pass. What does that tell you?

The two differ only exactly at the boundary, so a pass means no test sits there. The line may well be run (the Call List's line runs in every Call List test). Whether the boundary can occur in the app is a separate question, and for money it usually can.

You write a test for a line, and it passes first time. What should you do next?

A test that passes whatever the line says pins nothing. Seeing it fail on the broken line, for the reason you expected, is what makes it a test of that line. Then undo the break and see it pass.

Every caller of dormant() passes only Active Mortgages. Which test pins its status check?

The route filters to Active first, so through the API a closed Mortgage never reaches the line. test_a_closed_mortgage_owing_nothing_is_never_dormant seeds closed Mortgages with seed.py and calls dormant() on each. compute_ledger knows nothing about status.
