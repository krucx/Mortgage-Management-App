Settings in the config table

The Lender's Default Terms, the Call List limits, the message templates, the Gold Rates, and the little the app records for itself (the last Backup, the last daily run) all live in one two-column table. This lesson shows how a group of them is read and written as one typed object, and how saving one can set off something else.

By the end you can read and add a group of settings, and make something react when it is saved.

The problem

The app has a few dozen single values to remember. The Default Terms are three: a monthly rate, an Interest Mode and a Part-Month Rule. The Call List has two limits. Messages have two templates, a number of days and a yes/no. Each Gold Rate has a price and the date it was set.

A table per group would mean a new migration every time a setting is added, for tables that only ever hold one row. So they all share one key–value table, config: a text key and a text value. That's simple to store, but awkward to use. Code that reads "true" must remember to turn it into True; code that reads "2" must remember int; a key nobody has set yet must fall back to a sensible default; and every reader of the message settings must agree what the keys are called.

The idea

Declare each group of settings once: a Pydantic model (the fields, their types and defaults) plus the config key each field is stored under. That declaration, a ConfigGroup, does the rest. get reads the keys and gives back a validated model, with defaults for anything missing. set writes every field as text and then calls whatever should react to the change.

Pydantic, if you haven't met it, is the library FastAPI uses for request and response bodies: a class whose fields have types, which checks and converts data into those types ("2" → 2, "true" → True, "2026-10-19" → a date).

The flow

The code

1. The table and its two helpers

on_conflict_do_update is SQLite's upsert: "insert this row; if a row with that key already exists, update its value instead". It's SQLite-specific, which is why it comes from sqlalchemy.dialects.sqlite.

2. ConfigGroup

class ConfigGroup[M: BaseModel] is Python 3.12's syntax for a generic class: M stands for whichever model the group holds, so MESSAGE_SETTINGS.get(conn) is typed as a MessageSettings.

  1. Most groups use prefixed: each field is stored under the prefix plus its name. MessageSettings.reminder_days_before becomes the key message_reminder_days_before.
  2. Only the keys that exist are passed to the model. A key that was never set is simply absent, so Pydantic fills in the field's default.
  3. model_dump(mode="json") turns the model into plain JSON-style values: dates become "2026-10-19", enums their string values.
  4. A field set to None deletes its row, rather than storing the text "None". Read back, the field gets its default again.
  5. Then each reaction is called with the same connection.

3. A reaction: saving message settings syncs the Reminders

You met _sync_reminders in chapter 009, lesson 3: it calls reminders.sync. Because it runs on the connection the PUT route opened with engine.begin(), the new settings and the re-synced Reminders are committed together, or not at all. If the sync raised an error, the settings wouldn't be saved either.

4. The exception: the Cash Limit

The Cash Limit needs three states: never set (warn at ₹20,000), set to an amount, and cleared on purpose (never warn). A ConfigGroup has only two, because None means "forget it". So the Cash Limit stores an empty string for "cleared", by hand. Chapter 007, lesson 4 showed the rest of it.

Nuances

(a) Setting a field to None

Predict: the 22K Gold Rate's group is set with rate_per_gram=None, updated_on=None. What's in config for it afterwards, and what does get return?

From scripts/run_throughs.py (section L3), on a copy, calling the group directly.

Here the default is None, so forgetting is exactly right: the 22K rate is back to "not set". But if a field's default were something else, setting it to None would bring that default back. That's the Cash Limit's problem: if its key were deleted, get_cash_limit would read cash_limit=2000000, and the Lender's "never warn me" would quietly turn into "warn at ₹20,000". Pinned by test_setting_nothing_forgets_the_value in tests/test_settings.py.

(b) A model's default isn't the book's value

MessageSettings declares reminder_approve_first: bool = False, but the book's row says true, because book.py saved it. The default only applies while a key has never been written. The same goes for Default Terms in the other direction: Terms has no defaults at all, which is safe only because migration 0001 writes all three rows when the database is created (the comment at default_terms.py line 10 says so). A fresh database's Default Terms are therefore 3%, Compounded Yearly, full month, the values in that migration.

(c) Adding a group of your own

The tests show the whole recipe in a few lines. A model with defaults, a prefix, and optionally a reaction:

No migration is needed: the config table already exists, and a missing key reads as the default. Give every field a default (or seed it in a migration, as 0001 does for Default Terms), pick a prefix nobody else uses, and expose it through a GET/PUT pair like default_terms.py's, whose PUT opens engine.begin() and passes the today that after_set reactions receive.

Quiz

The Lender has never opened Backup settings. The backup_keep row doesn't exist. What does GET /api/backups report for keep?

get passes only the keys it found; Pydantic fills keep from _StoredBackupSettings' default=DEFAULT_KEEP, which is 4. (From scripts/run_throughs.py, section L3.)

How is reminder_approve_first = True stored in config?

_as_text writes booleans as "true"/"false", the way the app always stored them, and everything else with str(). The value column is text, so everything is a string.

A PUT /api/settings/messages saves the new days ahead, then its after_set sync raises an error. What's saved?

set calls each reaction with the same connection, and the route opened it with engine.begin(). An exception rolls the whole transaction back, the settings rows included.
