Chapter 010

Platform, database and migrations

The problem this chapter solves

Every chapter so far has been about the Lender's business: Mortgages, Payments, Closures, Reminders. Underneath all of it sits a small amount of plumbing that every feature leans on. Something has to build the app and plug its parts together. Something has to say what day it is. Something has to run the once-a-day jobs on a laptop that has no scheduler and may be shut all weekend. Something has to keep the Lender's settings, talk to the database, and hand out long lists a page at a time.

And the database has to change shape as the app grows, on a laptop nobody else can reach. When version 3.2.0 added a Customer's PAN, every Lender's existing database needed a new column, added safely, with a way back if it went wrong. There is no database administrator to run the change by hand. The app has to do it to itself, every time it starts, without ever losing a rupee of the Lender's records.

Get this plumbing wrong and the damage is quiet and wide. A wrong "today" moves every interest figure. A daily job that silently stops means no Backups. A migration run against the wrong folder changes a real lending book for good. This chapter opens each piece, shows you where its rules live, and ends with you adding a migration safely.

What you'll be able to do

  • Say what create_app builds, in what order the app starts, and how to start it differently (as the tests and the sample book do).
  • Say what date the app thinks it is, where that comes from, and whether a given request runs the daily jobs.
  • Read and add a group of settings in the config table, and make something react when it's saved.
  • Write a query against db.py's Tables inside a transaction, and page and sort a list.
  • Say what happens to the database on every start, and add a migration with its db.py mirror, tested, without ever editing a released one.

Before you start

You need these ideas from earlier chapters:

  • Where things live. Chapter 002, lesson 2 pointed at main.py and called create_app the backend's composition root. Lesson 1 here opens it properly.
  • Two warnings from chapter 002. Lesson 5 warned that the daily jobs run on the first request of the day (trap #8) and that migrations run on every start (trap #9). Its check-yourself had you edit migration 0001 and promised that this chapter would explain why you must never do that for real. Lesson 6 keeps the promise.
  • Transactions and refusals. Chapter 006 showed every change running inside engine.begin(), so a refused change leaves nothing behind. Lesson 4 shows where engine comes from.
  • The Reminder queue. Chapter 009, lesson 3 showed that sync is one of the two daily jobs and runs when the message settings are saved. Lessons 2 and 3 here show the machinery that calls it.

Keep the sample book served from chapter 002, lesson 4 (http://127.0.0.1:8765, held on 19 Oct 2026). Build it fresh into a new, empty folder and set $BOOK to that folder, because chapter 009 saved changes on the old one. In this chapter you mostly read the served book: its config rows, its alembic_version, its Backup folder. Lesson 3 saves one setting through the API and puts it back. Lessons 5 and 6 start the app on copies of the book (cp -R "$BOOK" …), never on the book you keep served, and never on real data.

The map

Notice the two arrows into create_app. The real app (main.py's last lines) builds it from environment variables. The tests and the sample book's serve.py call it themselves, with their own clock and folders. That one seam is why the whole course can hold the book on 19 Oct 2026.
