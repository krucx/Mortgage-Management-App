Chapter 010 · Lesson 6

Adding a migration safely

Suppose the Lender asks to note a Customer's nickname, the name everyone at the shop actually calls them. That's a new column on every Lender's existing database. This lesson walks through adding it: the two files you edit, how you test it, what you watch happen on a copy of the book, and the one rule you never break.

By the end you can add a migration and its db.py mirror, test it, and say why released ones are never edited.

The problem

From lessons 4 and 5 you know the two halves. The migrations change the Lender's real database, on their laptop, the next time the app starts. db.py's Tables are what the code queries. A new column needs both, and both have to agree.

A column added to a table that already has rows also has to say what those old rows hold. Meera has been a Customer since 2025: what's her nickname? And whatever you write will run exactly once on each Lender's database, with no developer watching, so it has to be right the first time.

The idea

Add the change as a new revision at the end of the chain, copying the last one's shape, and mirror it in db.py. A column for old rows is either nullable (old rows hold NULL, "not known") or has a default the database fills in. The test suite then checks three things for you: the chain runs, the code's queries work, and the two halves describe the same tables.

And never edit a revision that has been released. Lenders' databases have already run it, and their alembic_version says so. Alembic won't run it again for them, so your edit would reach new installs only, and the two would quietly differ. A fix is always one more revision.

Nuances

(a) A column old rows can't fill

Predict: 0016 says nullable=False, with no default. The copy of the book has 7 Customers. What happens when it starts?

WhatResult
Backup…-before-update.zip is taken first (the database is about to change)
0016's upgrade()OperationalError: Cannot add a NOT NULL column with default value NULL; the app doesn't start
alembic_versionstill 0015: the migration's transaction rolled back

From scripts/run_throughs.py (section L6).

Note that the test suite would not catch this: every test database starts empty, and an empty customer table has no rows to fill. Only a start on a database with Customers shows it, which is why you try every migration on a copy of the book. The fix is either nullable=True (0014, 0015) or a default the database fills in, like 0012's sa.Column("approved", sa.Boolean(), nullable=False, server_default=sa.false()). A server_default is a default written into the table itself, so SQLite fills it into existing rows. 0012 then goes one step further and sets the right value for old rows with an UPDATE: a migration can move data as well as schema.

The second row is the dangerous one, and it's why #115's test exists. A migration without its mirror would ship a column the code can't see. "remove_column" is Alembic's view: to make the database match db.py, it would remove the column.

(c) Why a released migration is never edited

This is chapter 002's promise. In its check-yourself you changed 0001's seeded rate from "300" to "200", watched tests fail, and undid it. Here is why you must never make that kind of edit for real:

Databasealembic_versionDoes the edited 0001 run?Default Terms afterwards
a Lender who installed last year0015no: 0001 is long behind them3% (or whatever they've set)
a fresh installnoneyes2%

Alembic decides what to run from alembic_version, never from the files' contents. So an edit to a released revision reaches only new databases, and from then on two databases at the same revision can hold different schemas or data. Nobody can tell which by looking at alembic_version. To change something a released revision did, add a new revision that changes it, so every database, old or new, goes through the same steps. "Released" means it has reached any Lender; a revision that only exists on your branch can still be edited.

(d) Testing a migration against old rows

The tests show two ways to check what an old database looks like after your migration:

Upgrade to the revision before yours, write the rows an old database would have, then start the app or call migrate, and check what the old rows hold. The other way is cheaper when the column is nullable: test_a_mortgage_made_before_shows_none_until_an_edit_sets_it in test_lent_through.py (line 68) makes a Mortgage normally, then sets lent_through to None "as every Mortgage made before Lent Through was asked", and checks the screens cope.

(e) Tell the Lender

Every release note in CHANGELOG.md says whether it changes the database. 3.2.0, which shipped 0015: "Updates the database (the new Customer details): the app takes a Backup marked -before-update first, and 3.1.1 does not start on the updated database." A release without a migration says "No database changes: updating keeps all data and Backups". Adding 0016 means the next release note uses the first form. Cutting a release is chapter 015's.

Quiz

0015 shipped in 3.2.0 with a bug: the PAN index should not be unique. How do you fix it?

Every 3.2.0 database is at 0015 already; an edited 0015 would never run for them, only for new installs. A new revision runs for everyone. Lenders never run downgrade(); their way back is the -before-update Backup.

You add a column to customer_table in db.py and nowhere else. What breaks?

Queries select every column the Table declares, and the migrated test databases don't have it: 422 tests fail or error (179 failed, 243 errors at b34526a). The reverse mistake, a migration without its mirror, is the one only the drift test catches.

Your new NOT NULL column has no default. All 607 tests pass. Is it safe to release?

Tests start from empty databases, so they can't see a migration that fails on existing rows. Start it on a copy of the book, or write a test that upgrades to the revision before and adds rows. The Backup helps the Lender recover, but the app still won't start for them.
