Chapter 010 · Lesson 5

How the app migrates on every start

When the Lender updates from 3.1.1 to 3.2.0, their database gains five Customer columns. Nobody runs a command for it. This lesson shows what the app does to its database every time it starts, when it takes a Backup first, and when it refuses to start at all.

By the end you can say what happens to the database on every start: when it is migrated, when a -before-update Backup is taken first, and when the app refuses to start.

The problem

The database's shape (its schema: tables, columns, indexes) changes as the app grows. Release 3.1.0 added mortgage.lent_through; 3.2.0 added the Customer's email, Aadhaar Number, PAN and ID Photos. The new code expects those columns. The Lender's database, full of real records, doesn't have them yet.

On a company server, someone would run a migration script by hand during a maintenance window. Here there's one Lender, on one laptop, who isn't a developer. And three things can go wrong:

  • The change fails halfway, or turns out to be wrong. The Lender needs a way back to exactly what they had.
  • The Lender goes back to the older version (ADR 0009 keeps it installed). The older code doesn't know the new columns, and might misread the database.
  • A developer starts unreleased code with DATA_DIR pointing at real data, by accident. That changes the real database too (trap #9).

The idea

Each schema change is a small Python file, a revision, with an upgrade() function. The revisions form one chain: 0001, then 0002, … up to 0015, each naming the one before it. The database itself records how far along the chain it is, in a one-row table called alembic_version. The newest revision is called the head.

On every start, migrate() reads that row and walks the database forward to the head, running each missing upgrade() in order. If the database is about to change, it takes a Backup marked before-update first. If the database is at a revision this code has never heard of, a newer version must have migrated it, and the app refuses to start.

Think of a building with a logbook of renovations, each numbered. A new contractor reads the last entry in the log, does every renovation after it in order, and writes each one in the log. If the log mentions a renovation the contractor has no plans for, they don't touch anything: someone with newer plans has been here.

The tool doing the walking is Alembic, SQLAlchemy's migration library.

The flow

The code

1. Alembic's settings, built in code

  1. The data folder is made if it isn't there. SQLite then creates an empty database file on first connect. That's how a fresh install starts.
  2. Most Alembic projects keep their settings in an alembic.ini file and run alembic upgrade head on the command line. This one has no alembic.ini: the two settings it needs (where the revisions are, which database) are set here, in code, so the app can migrate itself.
  3. The ScriptDirectory is Alembic's view of the revision files in migrations/versions/.
  4. The database's current revision: the value in alembic_version, or None for a database with no tables yet.

2. Refuse, back up, migrate

  1. A revision this code doesn't have can only come from a newer version. The check happens before anything else runs, Backups included.
  2. Updating means "there is a database, and it isn't at the head yet". A fresh install (current is None) isn't updating: there's nothing to back up.
  3. The lifespan passes lambda: backup.make("before-update") (lesson 1). make writes the Backup synchronously and raises if it fails. A raise here means line 316 never runs.
  4. Alembic runs every upgrade() from the current revision to the head, in chain order, and updates alembic_version.

3. How each revision runs

Alembic runs env.py each time it migrates. It connects to the URL migrate() set, then runs the revisions inside one transaction. render_as_batch is about SQLite's limits: its ALTER TABLE can add, rename or drop a column, but it can't change one (its type, whether it may be NULL) or add most constraints. Alembic's "batch" mode works around that by building a new table with the new shape, copying the rows across, and swapping it in. Lesson 6 shows the batch_alter_table blocks that use it.

4. The chain

Each revision names itself (revision) and the one it comes after (down_revision). 0001's down_revision is None: it's the start. Alembic follows these links to put the files in order; the file names' numbers are for people.

5. Every test's database is built by this chain

Tests that use the conn fixture call migrate directly; tests that use client get it through the lifespan. Either way, there's no separate "create the test tables" step. Each test's database is built by running 0001 to 0015, so a broken migration breaks the whole suite at once.

Run-through: three databases, three starts

First, your served book. Read its revision:

sqlite3 "$BOOK/data/mortgage.db" "SELECT * FROM alembic_version"

It says 0015: the head. Stop serve.py (Ctrl-C) and start it again. Nothing to migrate, so no before-update Backup; ls "$BOOK/backups" still shows only the start-up Backup from lesson 1.

Now try the other two cases on copies, never on $BOOK itself, and on another port so your served book can keep running. From backend/:

export NEWER=$(mktemp -d) && cp -R "$BOOK/data" "$NEWER/"
sqlite3 "$NEWER/data/mortgage.db" "UPDATE alembic_version SET version_num = '0016'"
uv run python ../docs/sample-book/serve.py "$NEWER" 8766      # fails at once
ls "$NEWER"                                                       # data only: no backups folder

export OLDER=$(mktemp -d) && cp -R "$BOOK/data" "$OLDER/"
uv run python - "$OLDER" <<'EOF'
import sys
from alembic import command
from alembic.config import Config
from mortgage_backend.platform.db import MIGRATIONS_DIR
config = Config()
config.set_main_option("script_location", str(MIGRATIONS_DIR))
config.set_main_option("sqlalchemy.url", f"sqlite:///{sys.argv[1]}/data/mortgage.db")
command.downgrade(config, "0014")     # as if from the version before 3.2.0
EOF
uv run python ../docs/sample-book/serve.py "$OLDER" 8766      # Ctrl-C once it's up
ls "$OLDER/backups"; sqlite3 "$OLDER/data/mortgage.db" "SELECT * FROM alembic_version"

The second script builds Alembic's settings the same way migrate() does (there's no alembic.ini to use), then runs 0015's downgrade(), which drops the five new Customer columns. It's only for making an old-looking database on a copy.

The refusal is the point of known_revisions. Docker restarts a crashed backend over and over (restart: unless-stopped). If the older version took a Backup each time before failing, it would fill the Backup folder with copies of a database it can't even read, and push out the older Backups the Lender needs to go back. test_an_older_version_takes_no_backup_of_a_newer_database_and_does_not_start (test_backups.py line 247) starts it five times and checks.

Nuances

(a) Only one Backup on an update morning

Predict: $OLDER has never had a Backup. The lifespan migrates (with a before-update Backup), then calls start_if_due, which backs up when the last Backup is a week old. How many Backups does the start leave?

One, mortgage-backup-2026-10-19-1100-before-update.zip. make records every Backup it writes in backup_last_at, labelled or not. By the time start_if_due looks, the last Backup is from this minute, so no weekly one is due. (From scripts/run_throughs.py, section L5.)

(b) The Backup fails

Predict: the Backup folder is full, and before_update raises. What revision is the database at afterwards?

Still 0014. The script calls migrate(url, before_update=…) with a function that raises OSError("the backup folder is full"): the error comes straight out of migrate, and command.upgrade never runs. The app doesn't start, and the database is exactly as it was. No migration ever runs without its Backup. (From scripts/run_throughs.py, section L5.)

(c) A fresh install takes no before-update Backup

Started on an empty folder, the app builds the database from 0001 to 0015 with no before-update Backup (current is None, so updating is false). The lifespan's weekly check then takes an ordinary one, mortgage-backup-2026-10-19-1100.zip, because none was ever taken. Pinned by test_a_fresh_install_takes_no_backup_before_update.

(d) Trap #9: migrations don't care whose data it is

Trap #9. Migrations run on every start, against whatever database DATA_DIR points at. Start a branch with a new migration while DATA_DIR points at a real lending book, and that book is migrated, for good. The released app it belongs to will then refuse to start on it, exactly like $NEWER above. Getting back means restoring the before-update Backup (chapter 015). That's why every command in the course, and every QA run in this repo, passes a scratch DATA_DIR and a scratch BACKUP_DIR on every command, and why the course only ever starts the app on mktemp -d folders.

(e) The Lender's way back

Every revision has a downgrade(), and you just used one. The Lender never does. Going back to the older version (which ADR 0009 keeps installed) doesn't undo the migration: the old version sees a revision it doesn't know and refuses, as in the run-through. So "A database update cannot be undone this way", in the ADR's words, and Setup instead tells the Lender which -before-update Backup to restore. That Backup lives in the Lender's synced folder outside the app (ADR 0003). How a Backup is made and restored is chapter 015's.

Quiz

The Lender's database is at 0013. They install a version whose head is 0015. What happens on its first start?

0013 is known and isn't the head, so updating is true: before_update runs first, then upgrade walks 0014 and 0015. The refusal is only for revisions this code doesn't know. The weekly check after it finds the fresh Backup and takes none.

Which start takes a before-update Backup?

Only an existing database that is about to change. An empty folder has nothing to back up; a database from a newer version is refused before any Backup.

A developer's new migration has a typo that raises inside upgrade(). What does uv run pytest show?

Every test database is built by migrate, through the conn fixture or the lifespan. If the chain can't reach the head, no test gets a database. That's a feature: a broken migration can't slip through.
