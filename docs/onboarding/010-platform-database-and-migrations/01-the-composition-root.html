Chapter 010 · Lesson 1

The composition root: how the app is put together

The same backend runs in Docker on the Lender's laptop, in hundreds of tests, and as the sample book frozen on 19 Oct 2026. Each time it needs a different database, a different clock and different folders. This lesson shows the one function that builds it, and what happens, in order, when it starts.

By the end you can say what create_app builds, in what order the app starts, and how to start it differently.

The problem

A backend needs a few shared things: a connection to the database, a way to know today's date, a place to put Backups, the once-a-day jobs. The easy way is to create each one wherever it's needed: create_engine("sqlite:///data/mortgage.db") at the top of each module, date.today() inside each route.

That fails the moment you want the app to behave differently. A test needs a throwaway database, not data/, which may hold the Lender's real lending book. A test about interest needs "today" to be a fixed date, or its figures change every night. The sample book needs to stay on 19 Oct 2026 forever. With the shared things created all over the code, you'd have to patch every module to change any of them.

The idea

Create every shared thing in one place, a function called create_app, and pass in the things that vary as arguments. That one place is called the composition root: where the app's parts are composed into a whole. Everything else in the backend receives what it needs rather than creating it.

Think of a theatre's stage manager. The actors don't each fetch their own props and lights; the stage manager sets the stage once before the curtain goes up, and each actor finds what they need in its place. A different production (a test, the sample book) just has a different stage manager's list.

The flow

Notice the gap between "app" and "start the server". create_app returns without opening the database once. Migrations and the start-up Backup wait for the lifespan, the code FastAPI runs as the server starts and stops.

The code

1. What can vary: the arguments

  1. today is a function that returns a date, not a date. Callable[[], date] means "something you can call with no arguments that gives back a date". The default is date.today itself (no brackets: the function, not its result). Lesson 2 is about why.
  2. Each optional argument switches a feature on. Leave backup_dir out and the app takes no Backups; leave out screens_dir and it serves no screens; leave out latest_release and it never looks for an update.
  3. One engine for the whole app. An engine is SQLAlchemy's object that hands out database connections (lesson 4).
  4. The two daily jobs, built from the pieces just made. Lesson 2 opens DailyRun.

2. The start sequence: the lifespan

A lifespan is a FastAPI hook for "on start" and "on stop" work. It's written as an async generator: everything before yield runs as the server starts, everything after it runs as the server stops. @asynccontextmanager is the standard-library decorator that turns such a generator into something FastAPI can enter and leave.

  1. A Backup that was interrupted (the laptop shut mid-write) can leave a half-written .partial file and a .backup-work folder. They're removed first.
  2. The database is brought up to date, every start. If it's about to change, a Backup marked before-update is taken first, but only if there's a Backup folder. Lessons 5 and 6 are all about this line.
  3. The weekly Backup, if one is due. This is the same function the daily run calls; running it here as well means a Backup that a shutdown cut short is retried at the next start.
  4. The server answers requests while the generator is paused here.
  5. At shutdown, a Backup that is still being written gets up to 8 seconds to finish.

3. Putting the shared things where routes can find them

app.state is a plain bag of attributes that FastAPI keeps for you on the app. Routes never import the engine. They ask for it through a dependency, a function FastAPI calls for each request and whose result it passes in as an argument:

Annotated[Engine, Depends(get_engine)] is FastAPI's way of saying "this argument is an Engine, and you get it by calling get_engine". So a route written def read_default_terms(engine: EngineDep) receives whichever engine this app was built with. TodayDep and NowDep work the same way (lesson 2).

4. The routes, and the screens last

Each feature module (customers.py, notices.py, …) declares its routes on its own APIRouter, all under /api. include_router adds them to the app. serve_screens adds one catch-all route, /{path:path}, that answers any path with a screen. FastAPI tries routes in the order they were added, so it must come last, or it would swallow /api/customers too. It also refuses any path starting api/ itself, so a mistyped API path is a JSON 404, not a web page.

5. The real app: built from the environment

This is what uvicorn mortgage_backend.main:app loads: the module-level app. It's built the moment main.py is imported, from environment variables. With no DATA_DIR set, it's data, relative to wherever you started it. Run from the repo root, that's the folder that may hold the Lender's real book. today and now aren't passed, so the real clock is used.

Importing main.py builds an app. Any script that does from mortgage_backend.main import create_app also runs line 138, building an app from the environment. It's harmless, because building touches nothing (the database is first opened when a server starts). But it's why the tests and serve.py import create_app and call it themselves, rather than using main.app.

Nuances

(a) Leave out an argument, lose a feature

Predict: the same copy is started without a backup_dir. What does GET /api/backups say, and what does pressing "Back up now" (POST /api/backups) do?

RequestAnswer
GET /api/backups200, enabled: false, no last Backup

From scripts/run_throughs.py (section L1).

The app still starts and works; it just has no Backups. That's why most tests can call create_app(database_url, today=…) with two arguments: everything they leave out is simply off. It's also why lifespan passes before_update=None when there's no Backup folder: a test database is migrated without being backed up.

/customers is a screen's address: the browser loads index.html and the frontend picks the page from the path. An unknown /api/ path stays a JSON 404 either way, so the frontend never mistakes a web page for an API answer. The real app always has a screens_dir: in Docker the image sets SCREENS_DIR to the screens built into it, and without Docker it points at the release's frontend/dist (chapter 014, lesson 2; ADRs 0010 and 0013). Only the tests and the Vite dev set-up run without one.

(c) The tests are a third caller

tests/conftest.py builds the app for most tests: create_app(database_url, today=lambda: TODAY), a fresh database in pytest's tmp_path, and TODAY = date(2026, 4, 20). TestClient used as with TestClient(app) as client: runs the lifespan on entry, so every test's database is migrated before its first request. Chapter 013, lesson 2 covers the fixtures.

Quiz

You run uv run uvicorn mortgage_backend.main:app from backend/, with no environment variables set. Which database does it open?

data_dir() falls back to the relative path data, so it depends on where you start it: from backend/, that's backend/data/. migrate creates the folder and a fresh database if they're missing. Started from the repo root, it would be the root data/, which may hold real data. That's why the commands sheet always sets DATA_DIR.

In which order does the app start?

Lines 78, 80 and 87. Leftovers go first so a half-written file can't be mistaken for a Backup. Migration comes before the weekly Backup so that Backup is of the database the app will actually use.

A new route needs today's date. How should it get it?

TodayDep reads app.state.today, so the route gets 19 Oct 2026 in the sample book and 20 Apr 2026 in tests. date.today() would ignore both. main.py exports no today; and importing from it would tie the route to the environment-built app.
