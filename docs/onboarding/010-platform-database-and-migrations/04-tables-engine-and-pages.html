Chapter 010 · Lesson 4

Tables, the engine and lists a page at a time

Every route you've read so far opens engine.begin() or engine.connect() and queries something called customer_table or payment_table. This lesson shows where those come from, what the database enforces and what it doesn't, and how a long list comes back 20 rows at a time.

By the end you can write a query against db.py's Tables in a transaction, and page and sort a list.

The problem

The code needs to talk to SQLite without hand-writing SQL strings everywhere. Strings can't be checked by the type checker, are easy to get subtly wrong, and invite SQL injection when a value is pasted in. It also needs a few rules to hold every time: a Payment can't point at a Customer who doesn't exist, and a change that is refused halfway must leave no rows behind.

Lists bring their own problem. The Lender's Customers and Payments grow every month. Sending the whole list on every page load gets slower each year, so a list comes a page at a time. But paging only works if the order is stable: if two Customers sort equally and the database is free to return them either way round, one of them can appear on both page 1 and page 2, and another on neither.

The idea

Declare each table once, in Python. platform/db.py describes all 12 tables with SQLAlchemy Core: Table objects whose columns you query with Python expressions (customer_table.c.name), which SQLAlchemy turns into SQL with the values safely bound. "Core" is SQLAlchemy's query-builder layer, without its ORM: rows come back as plain tuples or dicts, not objects.

One engine, with the rules switched on. make_engine turns on SQLite's foreign-key checks for every connection. Every change runs inside engine.begin(), a transaction.

One paging helper for every list. A list declares its sort keys once, plus a unique column to break ties. query_page then sorts, counts and cuts the page in SQL.

The flow

The code

1. A Table

  1. metadata collects every Table declared against it. Lesson 6 shows a test that compares it with the real database.
  2. A ForeignKey: the value must be the id of an existing customer row (or NULL), but only if SQLite is told to check (below).

The 12 Tables are config, standalone_referrer, customer, mortgage, mortgage_photo, payment, term_change, audit_entry (History), call_note, allocation, reminder and reminder_mortgage. Read mortgage_table (lines 81–109) and you'll see the units again (trap #6): Meera's chain is stored as amount_lent = 8000000 (paise, so ₹80,000) and monthly_rate_bps = 200 (basis points, so 2% a month).

There is no ledger table, and no column for Outstanding, interest or Months Unpaid. Every money figure is worked out by replaying the stored facts (chapter 004, ADR 0001). If you catch yourself adding an outstanding column, stop and reread that ADR.

2. The engine and foreign keys

  1. An event listener: SQLAlchemy calls this function every time the engine opens a new database connection.
  2. SQLite has foreign keys switched off by default, for backward compatibility, and the setting lasts only for one connection. Without this line, every ForeignKey above would be decoration.

3. Transactions and refusals

You've seen the two ways to get a connection in every chapter since 005:

CodeWhat it isUsed for
with engine.connect() as conn:a connection; nothing is committedreads
with engine.begin() as conn:a transaction: committed when the block ends normally, rolled back if an exception escapes itevery change (and the reads that write, like GET /api/reminders)

A change refuses with raise unprocessable("…"). The exception leaves the engine.begin() block, which rolls back anything the change had written, and FastAPI turns it into a 422 whose detail the screen shows the Lender. That's the whole of chapter 006's "refuse, write, check" safety net, at the database level. The other small helper here, exists(conn, table, row_id) (line 242), answers "is there a row with this id?", which many changes ask before writing.

4. Sort keys, declared once

The key line is 46: the tie-breaking columns are sorted in the same direction as the chosen key. A unique column (an id) as the last sort key means no two rows ever compare equal, so the order is fully decided, and reversing the direction reverses every row.

5. A page, in SQL

  1. The total counts every matching row, not just this page's, so the screen can say "7 Customers" and how many pages there are.
  2. The order from Sorting.
  3. Page 1 skips 0 rows, page 2 skips 20, and so on. .mappings() gives each row as a dict-like mapping (row["name"]), which to_items turns into the response model.

The Customers route (customers.py line 451) is a typical caller: query_page(conn, select(customer_table).where(match), _SORTING, page, …, sort=sort, descending=descending), inside engine.connect().

Run-through: the book's Customers, a page at a time

Ask your served book for its Customers list four ways:

curl -s 'http://127.0.0.1:8765/api/customers' | jq '{total, page, page_size, names: [.items[].name]}'
curl -s 'http://127.0.0.1:8765/api/customers?sort=referrer' | jq '[.items[] | "\(.id) \(.name)"]'
curl -s 'http://127.0.0.1:8765/api/customers?sort=referrer&descending=true' | jq '[.items[] | "\(.id) \(.name)"]'
curl -s 'http://127.0.0.1:8765/api/customers?page=2' | jq '{total, page, items}'

By name, ascending, this is the SQL query_page sends (the script compiled it from the real _SORTING; the column list is shortened here):

SELECT customer.id, customer.name, … FROM customer WHERE 1 = 1
ORDER BY lower(customer.name) ASC, customer.id ASC
LIMIT 20 OFFSET 0

WHERE 1 = 1 is the "no filter" case: match is true() when there's no search text. With descending=true, the order becomes lower(customer.name) DESC, customer.id DESC.

The Referrer rows are where ties earns its place. Four Customers have no Referrer and two share one, so the Referrer name alone can't order them. The id does: 3, 4, 5, 6 ascending; 6, 5, 4, 3 descending. Without ties, SQLite could return those four in any order, and could choose differently for page 1 and page 2 of a longer list.

Nuances

(a) Foreign keys only bite through make_engine

Predict: on a copy of the book, insert a Call Note for Mortgage 999, which doesn't exist. Once with Python's plain sqlite3 module, once through make_engine. What happens each time?

ConnectionPRAGMA foreign_keysINSERT INTO call_note (mortgage_id, …) VALUES (999, …)
plain sqlite3.connect0accepted
make_engine(url).begin()1IntegrityError: FOREIGN KEY constraint failed

From scripts/run_throughs.py (section L4), both rolled back.

The same goes for the sqlite3 command-line tool you've been using to read the book. That's one reason the course only ever reads with it: a hand-typed INSERT or DELETE there skips the checks the app relies on. Write through the API, or through make_engine.

(b) A refused change leaves no rows

Predict: on a copy, POST /api/payments pays ₹90,000 to Meera's chain on 19 Oct, when it owes ₹83,333. How many rows are in payment afterwards? (There are 33 before.)

Still 33. The response is a 422: "2025-Meera-GoldChainPendant: the Payment on 19 Oct 2026 would be more than the ₹83,333 owed then". The Payment and its Allocation were inserted, then check_replays refused (chapter 006), and the exception rolled the transaction back. (From scripts/run_throughs.py, section L4.)

(c) rows_page: lists worked out in Python

The Call List can't be sorted by SQL: Months Unpaid and Loan-to-Value aren't columns, they come from replaying each Mortgage. So the route works out every row, then rows_page sorts them with Python's sorted (which keeps equal rows in their original order) and slices out the page with page_of. On the book, GET /api/call-list has total 1 (Arjun), page_size 20, and mortgages 2. The Reminders and Closures lists work the same way. rows_page also accepts page=None, meaning "every row on one page".

(d) The schema is declared twice

The Tables in db.py are what the code queries. But they don't create the database: the migrations do (lessons 5 and 6). So every column exists in two places, and a new column means editing both. If they disagree, the code asks for a column the database doesn't have, or the reverse. Until recently nothing caught that. Now one test does, test_the_migrations_build_the_tables_the_app_declares, added for #115. Lesson 6 has you watch it fail, and this chapter's check-yourself has you break it on purpose.

Quiz

A list of Payments is sorted by amount, with ties=[payment_table.c.id]. Two Payments are both ₹5,000, ids 12 and 30. With descending=true, which comes first?

order() applies _ordered(column, descending) to every tie column, so descending sorts the ids descending too. That's what makes descending the exact reverse of ascending.

A list has 45 rows. What does page 3 hold?

Page 3 skips 40 rows and takes up to 20, so 5 come back. total counts every row, on every page (Page's comment says so).

A route reads the Customers and also writes nothing. Which should it open?

Reads use engine.connect(). engine.begin() is for changes, and for the few reads that write, like the Reminders list. Plain sqlite3 skips the engine, and with it the foreign-key PRAGMA.
