Chapter 003 · Lesson 3

Saving it

The Lender presses Record Payment of ₹6,600, then Confirm and save. One POST /api/payments later, Meera's Payment is in the book for good. What does the backend check, what does it write, and what happens if a check fails halfway?

By the end you can follow POST /api/payments from validation to the committed rows.

The problem

A Payment must never be half-saved. Picture the naive version: insert the payment row, insert the first Allocation, then discover the second Mortgage was closed last week. Now the book has a Payment of ₹6,600 that only paid ₹5,000 to anything. Or the checks run first and pass, but the Payment turns out to pay more than the chain owed once the replay sees it. Every figure after it would be nonsense.

And the Lender can back-date a Payment, so "does it pay too much?" can't be answered by looking at today's figures alone. It depends on every Payment before and after it.

The idea

Do the whole save inside one database transaction, in four steps: refuse what can be refused up front, write the rows, check by replaying every Mortgage the Payment touched, then record it in History. If any step raises, the transaction rolls back and nothing was saved. The same four steps shape every change in the app (chapter 006).

The flow

Notice that the check runs after the write. The replay needs the new rows in the database to see the Payment in its place among the others.

The code

Where is it? Not where you'd look

Newcomer trap #1: Payment writes live in payments/recording.py and payments/writes.py, not in payments/payments.py. payments/payments.py only reads Payments, and payments/ also holds Receipts and the Cash Limit. Every change that moves a Ledger, whichever package it lives in, shares the refusals in lending/refusals.py, so they all refuse, write, check and record the same way. Find a route by searching for its path string, as chapter 002 showed. See the traps sheet.

1. The route

  1. engine.begin() opens a connection with a transaction. Leaving the with block normally commits; leaving it by an exception rolls back.
  2. The route only parses, calls and answers. All the rules are in record_payment, which is why the Preview (lesson 2) can call the very same function.

2. Validation, before any code of ours runs

PaymentIn is a Pydantic model: a class that describes the JSON body. FastAPI parses the request into it and answers 422 by itself if the body doesn't fit: a missing field, a negative amount, Allocations that don't add up. It's also the model the frontend's PaymentIn type is generated from.

3. record_payment: refuse, write, check, record

Meera's Payment pays neither Mortgage in full, so both Allocations are ordinary and the Redemption branch (lines 56–70) does nothing. Chapters 005 and 007 cover that branch.

  1. Refuse what's wrong on its face (below).
  2. Write one payment row and one allocation row per Mortgage.
  3. Check by replaying each Mortgage, now with the new rows in it.
  4. Record the new Payment in History.

replays and Overpayment come from the Ledger engine, lesson 4's black box. All you need now: rebuilding a Mortgage's Ledger raises Overpayment if any Payment in it, old or new, is larger than what was owed on its date.

4. The tables it writes

Look at what's not there: no "interest paid", no "Principal paid", no "still owed". Lesson 4 is about why.

Nuances

(a) A refusal saves nothing

Predict: after saving, try a second Payment of ₹81,734 to the chain alone, ₹1 more than it now owes. write_payment inserts its rows before check_replays notices. Are the rows still there afterwards?

No. check_replays raises a 422:

2025-Meera-GoldChainPendant: the Payment on 19 Oct 2026 would be more than the ₹81,733 owed then

From scripts/run_throughs.py (step 6), sent both as a Preview and as a save.

The exception leaves the with engine.begin() block, so the transaction rolls back, taking the inserted rows with it. In the app you won't even get that far: the Preview runs the same check, shows this message, and Save stays disabled. A 422 means "understood, but not allowed", and the frontend shows the backend's message to the Lender (BackendError in serverState.ts). (A closed Mortgage is refused with 409, "conflict", instead.)

(b) The daily jobs ride on this request

If this happens to be the first /api/ request of the day, the run_daily_jobs middleware in main.py (line 104) runs first: a Backup if one is due, and the day's Reminders. There's no scheduler. You met this in chapter 002; chapter 010, lesson 2 explains it.

Quiz

You need to change what happens when a Payment is recorded. Which file?

record_payment and post_payment are in payments/recording.py (trap #1). payments/payments.py reads Payments; previews.py only wraps record_payment in a rollback.

Why does check_replays run after write_payment, not before?

The replay rebuilds each Ledger from the stored Allocations, so the new Payment has to be in the tables, in its date order among the others, to be checked. The transaction makes that safe: a failed check rolls the write back.

A Payment's body has Allocations of ₹5,000 and ₹1,600 but amount 650000. Who refuses it?

allocations_add_up on PaymentIn raises while the body is parsed, so FastAPI answers 422 before record_payment runs at all.
