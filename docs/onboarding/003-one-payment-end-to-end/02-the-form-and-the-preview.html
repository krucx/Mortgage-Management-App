Chapter 003 · Lesson 2

The form and the Preview

The Lender types ₹6,600, picks UPI and divides it between two Mortgages. Before they press Save, the screen already shows what each Mortgage will owe afterwards. Where is that draft built, and who works out the "afterwards"?

By the end you can say where the draft is built and how the Preview reaches the backend and returns.

The problem

Money mistakes are expensive to undo. If the Lender types ₹50,000 instead of ₹5,000, or puts the money on the wrong Mortgage, they want to see it before it's saved, in figures they recognise: "the bangles will owe ₹1,46,500".

The obvious design is for the screen to work those figures out itself. But the rules for what a Payment pays first are subtle (chapter 004 needs a whole chapter for them), and a second copy of them in TypeScript would drift from the Python one. Then the Preview would say one thing and the save would do another, which is worse than no Preview at all.

The idea

The form only describes the Payment it would save, as the exact JSON body the save would send. It hands that body to the backend's Preview route, which makes the real change inside a database transaction, reads every figure, and rolls the transaction back. One set of rules, used twice.

The flow

Notice that record_payment, the very function the save calls (lesson 3), runs inside the Preview. The only difference is the rollback at the end.

The code

1. The list: what each Mortgage owes on the Payment's date

That's request 1, GET /api/mortgages?…&as_of=2026-10-19. asOf: paidOn asks for each Outstanding on the Payment's date, not today, because a Payment can be back-dated. placeholderData keeps the old list on screen while a new date loads.

2. The draft: exactly what saving would send

  1. The Lender types rupees; everything below works in paise (₹1 = 100 paise), as integers. See nuance (a).
  2. proposed is either a complete request body or null. The form checks only what it can see by itself: something chosen, an amount, Allocations that add up. Whether the Payment is allowed (too large? before the Mortgage started?) is for the backend to say, in the Preview.

3. From draft to Preview

useProposedChange is a custom React hook: a function, named use… by React's convention, that bundles state and behaviour a component can reuse. Every form that changes a Ledger uses this one hook, so they all behave alike: preview, confirm, save, go somewhere. Inside it:

The Preview's cache key is the draft itself, so an unchanged draft is never asked for twice.

4. The backend makes it, reads it, undoes it

Nuances

(a) Paise on the wire, rupees on the screen

Every amount in the API and the database is an integer number of paise, so ₹6,600 travels as 660000. Integers never pick up floating-point dust like 0.1 + 0.2 = 0.30000000000000004. When you read a request or a test, divide by 100 in your head. The app has other units of this kind (milligrams for weight, basis points a month for rates); chapter 004 lists them.

(b) One Preview, however fast you type

Predict: you type 5000 and 1600, nine keystrokes in two boxes. How many POST /api/payments/preview requests appear?

One, if you type briskly. A draft that's incomplete (the Allocations don't add up to ₹6,600 yet) is null and asks for nothing. And usePreview waits until the draft has stopped changing for 400 ms before it asks:

Debouncing means waiting for a pause before acting. Without it, every keystroke would make the backend write and roll back a Payment.

Paying a Mortgage's whole Outstanding Redeems it, in the same request (ADR 0011). The form doesn't decide that: it reads after.closure?.kind === 'redeemed' from the Preview and words the dialog to match, with buttons Redeem and Go back, because the Lender must now hand the jewellery back. Don't save this one; leave the chain at ₹1,600 for the rest of the chapter. Chapter 005 covers Redemption.

(d) Two warnings for later

A bug in a change shows up in its Preview too. Because the Preview runs record_payment for real, a bug there breaks the Preview as well as the save. That's by design: they can never disagree. Each change's Preview route is written out by hand beside its save route (ADR 0007). Chapter 006 explains both.

PaymentIn is generated, not written. The TypeScript type PaymentIn comes from the backend's Pydantic model of the same name, through openapi.json and api.gen.ts. Change the model and run npm run gen:types, or tests fail in both languages. Chapter 011, lesson 1 covers it.

Quiz

Who works out the "Owed today ₹1,51,500 → ₹1,46,500" figures?

_preview replays each Mortgage, runs record_payment, replays again, and rolls back. The frontend has no copy of the money rules, so the Preview can't drift from the save.

The Allocations add up to ₹6,500 but the total says ₹6,600. What happens?

The form can check this itself: problems gets "The Allocations add up to…", so proposed is null, no Preview is asked for, and Save stays disabled. (The backend would refuse it too, in PaymentIn's validator.)

Why is the Record Payment button disabled while the Preview is loading?

canSave waits for the Preview because the confirmation (Redeem or not) and the Cash Limit warning are worded from it, and a Preview error means saving would be refused. The save sends proposed, not the Preview.
