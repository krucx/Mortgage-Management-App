Architecture review · pass 5

Mortgage-Management-App · 21 Oct 2026 · scope: what changed since pass 3 (Waive off, Closures, Call List, the server-state module, the propose-a-change hook, Windows scripts)

Every pass-3 candidate has landed. The server-state module and the Notice queue are deep and well tested. The newest friction is around Closure: Waive off arrived as a third way to close a Mortgage, and the frontend now writes closing three times and repeats the backend's rules.

Problem

A Closure is made three ways. The bulk ways skip the Preview and commit one Mortgage at a time, so a failure halfway through leaves the Lender's selection half-closed. "Can it be Waived?" is written in 3 places and "not a future date" in 4; the frontend uses the browser's date while the backend uses its own clock.

Solution

The backend closes a set of Mortgages in one transaction, so a Preview of a bulk Closure comes for free. The frontend has one closing module used by all three pages, which shows the backend's refusal and holds none of its rules.

Wins

  • locality: Closure rules in one module
  • leverage: one interface, three pages
  • bulk Closures get a Preview
  • no half-closed selections
  • delete closeEach and its copy
  • bulk Forfeit and Redeem testable (none today)

Tests today: only bulk Waive has page tests (2, in ClosuresPage.test.tsx). Bulk Forfeit, RedeemPaidOff and a partial failure have none.

Problem

The Closure figures each reader needs are worked out by that reader, from the Ledger's last step or from the frontend's arithmetic, so the Waived Amount and profit/loss each have more than one definition.

Solution

The Mortgage replay works out the whole Closure once; every reader takes it from there. It is still derived on demand, so ADR-0001 holds.

Wins

  • locality: one definition of each figure
  • tests hit the replay, not each reader
  • frontend does no Closure arithmetic
  • pairs with 01: the Preview shows the Closure
03

Problem

Reopen, Void and removing a Term Change show a Preview inside ReasonDialog, but the Lender can still confirm while that Preview shows a refusal. The rule the hook holds for four changes doesn't hold for these three.

Solution

The hook takes an optional reason; ReasonDialog shrinks to a form field inside it.

Wins

  • leverage: one interface, 7 changes
  • Preview rule holds everywhere
  • proposedChange tests cover Reopen, Void
  • delete ReasonDialog's own saving state

Each change declares what it makes stale, beside its request

Speculative in-process
  • frontend/src/requests.ts ~190–245: changes.* say nothing about what they make stale
  • 22 call sites choose useLedgerChange, useMortgageChange or useChange(STALE_AFTER.x)
  • pages/MortgagePage.tsx 41–44 and SettingsPage (setQueryData ×5) write the cache by hand

Before · the call site picks

page B → useMortgageChange
page C → useChange(STALE_AFTER.x)
Settings → setQueryData ×5

22 sites · each right today

After · the change knows

changes.recordPayment · makes stale: Ledger
changes.setGoldRate · makes stale: Collateral
…one line each
pages: save(change)

Problem

What a change makes stale is decided at each call site, so a new page using an old change can pick the wrong list.

Solution

Move the choice onto the change's request entry; pages only save.

Honest rating: no bug today. It protects the next change, so do it only while touching requests.ts for 01 or 03.

A Payment says which Mortgages it cleared; New Payment gets a page test

Speculative local-substitutable (fake server)
  • frontend/src/pages/NewPaymentPage.tsx 205–219: a second fetch after saving, to find Mortgages with nothing Outstanding
  • NewPaymentPage.tsx 106–121, 169–179: re-ticking on a date change; switching between amount and percent modes

Before · tested at the edge, not where it's called

NewPaymentPage · 0 tests

After · tested through the page

NewPaymentPage behind fakeServer / showPage
Payment answer lists the Mortgages it cleared · no second fetch

Problem

The riskiest form in the app is tested only through allocate.ts. The bugs would be in how the page calls it, and in the page asking a second time what the Payment just did.

Solution

The backend's Payment answer names the Mortgages it left with nothing Outstanding; add a page test on the existing harness.

Looked at, not worth it now

  • Notice actions decided in both tiers (notices.py _ACTIONS; NoticesPage 5 status checks). Real but small; the queue module is deep with 28 tests.
  • Status and step label maps in BeforeAfter, History, MortgagePage, MortgagesPage. Typed over generated unions, so the compiler catches a missing kind.
  • Call List. The backend owns the reasons; the frontend only labels them. 11 + 3 tests.
  • requests.ts (634 lines of thin entries). Shallow one by one, but pairing a typed key with its load is the point. Merging twin routes is ADR-0007.
  • useReadyToRedeem (12 lines). Shallow, but deleting it only moves one line into its callers.
  • windows/*.ps1. Assert-Success is duplicated because setup.ps1 runs before common.ps1 is downloaded. The parts worth testing are already pure and covered by Pester.
  • suggestEqually's split by Infinity in New Payment. Deliberate and commented: whether a Payment is too large is for the Preview to say.

Top recommendation

01 · One closing module

It's the only candidate with a real way for the Lender to lose: a bulk Closure that fails halfway is left half-closed, with no Preview beforehand. It removes three copies of the Closure rules, and 02 slots into it.
