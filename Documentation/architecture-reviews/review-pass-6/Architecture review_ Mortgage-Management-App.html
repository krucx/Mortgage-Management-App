Problem
"Paying the whole Outstanding Redeems" (ADR 0011) is worked out by the page from N extra quote requests, sent as redeeming, and then checked again by the backend in both directions. Save is blocked with "Checking whether they can be Redeemed…" until the quotes come back. The caps come from outstanding_total while the quote comes from outstanding_on_closure, so the page has two sources for the same number.
Solution
The Payment changes module decides the Redemptions itself: an Allocation of the whole Outstanding on paid_on Redeems. The page reads the Redeem confirmation and the Interest to Date wording from the Payment Preview, which already returns each Mortgage's Closure. redeeming and useQuotes are deleted.
Wins
  • locality: the paid-in-full rule in one module
  • interface shrinks: redeeming field deleted
  • N quote requests and one blocking state gone
  • page tests fake only the Preview
  • no two refusals to keep consistent
Tests
test_redeeming_payments.py (14) stops passing redeeming= and asserts the outcome. NewPaymentPage tests (11) stop faking /outstanding-on-closure.

Problem
Storage is shared, but every caller writes its own save-and-attach sequence, and the copies have different bugs. On a new Mortgage, the catch reads the createdId from that render, so a failed photo shows the raw error, not "Mortgage saved, but a photo failed". On the Customer form, a retry uploads the photo and ID Photos again, which adds a file and a History entry each time.
Solution
In the backend, one photos.replace owns the file's whole lifecycle, including the rollback. In the frontend, one save-with-photos hook keeps track of what has already uploaded and marks caches stale in one way.
Wins
  • locality: a retry bug fixed once
  • leverage: 3 pages, 6 backend sequences
  • no orphan files after a rollback
  • no duplicate History rows
Tests
One backend file for the photo lifecycle (failed transaction leaves no file; replace deletes the old one) instead of checks scattered over three files. One hook test: "a retry uploads only what failed".

Problem
useCashWarning is shallow. The Cash Limit rule is really decided by its 4 callers, and they disagree about what counts as one cash sum. The ₹20,000 figure is written in both tiers.
Solution
Each Preview returns cash, worked out by one backend rule. useProposedChange warns from it, and pages pass nothing.
Wins
  • locality: one definition of a cash sum
  • 4 page tests become 1 hook test
  • New Mortgage joins the shared hook

ADR 0007: Preview routes stay hand-written. This adds a field to what they return; it doesn't generate them.
