Architecture review, pass 7

Mortgage-Management-App · 9 Nov 2026 · scope: 477c6f0..d68b5df, 115 commits, 3.2.1 → 3.4.6. That covers Discounts, correcting starting Terms, Reminders, Dashboard timeframe, the Calculator, the one image, and the new security, review and release pipeline.

All five pass-6 candidates landed, with small leftovers. The new friction sits in two places. In the product, the rules that came with the newest features (Discounts, Reminders, Terms correction) are decided by callers instead of by the module that owns the concept. In CI/CD, the release flow's logic lives in shell inside YAML, and that is where every recent release fix landed.

Decisions taken since pass 6

These are settled. The candidates below build on them and don't reopen them. Items marked no ADR are only in commits and docs. A future review could re-suggest them, so they're worth recording.

Architecture
  • ADR 0013: one image; the backend serves the screens in Docker too. The backend-*/ui-* tags stay on Docker Hub for rollback (ADR 0009).
  • ADR 0014: a Discount is a non-cash Payment reduction. It pays unpaid → Interest to Date → Principal and is left out of the cash KPIs.
  • ADR 0015: starting Terms can be corrected. The Ledger replays from them.
  • ADR 0017: Notices are renamed Reminders, with no compatibility period. An unsent Reminder holds only Mortgages that are Active and accruing. The Dashboard's activity timeframe has inclusive dates.
  • The Calculator's Simulation runs on the real Ledger engine (simulation.py → compute_ledger, project). The frontend has no interest math. no ADR
  • The Discount confirmation threshold is a setting, like the Cash Limit. no ADR
  • A newer database is refused in migrate, before the pre-update Backup.
Security
  • ADR 0016: each Secret scanning alert gets one labelled issue, synced daily. It uses a separate fine-grained token (alerts: read, issues: write) and never copies the secret field.
  • CodeQL runs security-and-quality on actions, JS/TS and Python: on push, on PR, and weekly. no ADR
  • Trivy scans the one image on push, on PR, and daily, then uploads SARIF.
  • Critical CodeQL, Dependabot and Trivy findings become fingerprinted issues, reconciled on every run. no ADR
  • Workflows default to permissions: {} and grant per job.
  • A 20 MB upload cap is enforced in middleware, for both a stated length and a streamed body.
  • Compose binds 127.0.0.1 only.
CI / CD & process
  • Changes are PR-only (rulesets/main.json). That means 1 human approval, approval of the last push, threads resolved, and the backend, frontend and CodeRabbit checks. The maintain role can bypass on PRs only. no ADR
  • CodeRabbit is the automated reviewer. It is advisory and never counts as approval.
  • A release candidate is a dispatched workflow. It promotes Unreleased, syncs VERSION, runs the full Tests preflight, then opens the PR.
  • Merging the release PR publishes it. The tag is created at the merge commit with RELEASE_WORKFLOW_TOKEN, then release.yml is dispatched and re-verifies the approved PR. Tags are never pushed by hand. no ADR
  • After publishing, the workflow checks the notes, the ZIP and the image manifest. latest only moves forward.
  • Coverage is reported against the PR base and is non-blocking. check-version.mjs enforces one canonical VERSION.

Problem. Only the pure checks are tested. The orchestration is shell, and it is copied. "Latest published version" appears 3 times, the reviews-and-checks jq glue twice, the dispatch-and-poll loop twice.   • two adapters justify the seam
  • YAML shrinks to wiring

Tests. test-publish-release.mjs grows from pure checks to whole scenarios: "tag already at another commit → refuse", "release PR not approved after last push → refuse", "dispatch run never appears → time out with the recovery summary". Today these are only exercised by doing a real release.

Problem. The page works out the Discount cap itself, as outstanding − cash. That restates ADR 0014's payment order, which already lives in ledger.pay. The threshold check exists only in the page. Against the real backend, an over-balance Discount makes the Preview raise Overpayment, canSave goes false, and handleSubmit returns before the "Reduce Discount to the remaining balance?" dialog. The tests stub the Preview to accept anything, so they don't see this.

Solution. This is pass 6's cash move, applied to Discounts. The Preview returns, per Allocation, the room left for a Discount and whether it is over the threshold. The page only shows dialogs. In ledger.pay, cash and Discount go through one _apply instead of two copied blocks (:238-250).

Wins
  • the cap dialog becomes reachable
  • locality: the payment order once
  • the re-submit effect is deleted
  • page tests fake only the Preview

Tests. Add a backend Preview test for an over-balance Discount and one for over the threshold. Drop the page's cap arithmetic tests. Add one page test where the fake Preview refuses with an Overpayment; it fails today.

ADR 0007: Preview routes stay hand-written. This adds fields to what they return; it doesn't generate them. ADR 0014 is untouched; this puts its order in one place.

Security and CI gaps (no redesign needed)

  • Third-party actions are pinned by tag, not commit SHA. This includes trivy-action@v0.36.0, setup-uv@v7 and docker/*, and some of those jobs hold Docker Hub credentials, RELEASE_WORKFLOW_TOKEN or issues: write. Pin by SHA and let Dependabot bump them.
  • release.yml has no top-level permissions: {}. Its publish job, which holds the Docker Hub token, runs with the default token scope, unlike the other workflows.
  • The one image runs as root, with no USER in the Dockerfile. It is only bound to 127.0.0.1, but a non-root user is cheap.
  • The ruleset requires only backend, frontend and CodeRabbit. image, windows, pages and CodeQL can be red at merge on ordinary PRs. They are caught only when a release revalidates the checks.
  • The coverage-vs-base glue is ~60 lines of inline Python and Node in test.yml, with no tests. It's non-blocking, so this is low risk.
  • release-candidate.yml defaults its version input to 3.4.6, which is already released.

Checked and fine

  • The pass-6 candidates landed: the Payment decides its Redemptions, photo_change + useSaveWithPhotos, the Preview returns cash, Call Note rules are shared, and rupees and grams have toDraft/fromDraft. Leftovers: the Call Sheet import still has its own insert and same-note check (call_sheets.py:369,439), replace_photo and replace_id_photo are twins, and calculator.ts:105 skips formatRate.
  • One image: the screens are built on the build platform and served by screens.py in both modes, with an image smoke test in CI.
  • Refusing a newer database lives in one place (db.migrate) and is tested.
  • The upload cap middleware handles both a stated length and a streamed body, with tests. The 20 MB figure is repeated in requests.ts on purpose.
  • The shared ChartFrame/Gridlines are reused correctly.
  • Release gates: the PR author can't approve their own release, an approval is required after the last push, and the tag must sit at the merge commit. These pure checks are tested.
