1. The licence in plain English

The repository ships a single LICENSE file: the unmodified Apache License, Version 2.0. GitHub detects it as apache-2.0. Apache 2.0 is a permissive open-source licence: it gives away broad rights and asks for very little in return.

What it lets anyone do

PermissionWhat it means here
UseRun the app for yourself, in a business, at any scale. No fee, no seat count, no registration.
Copy & redistributeHand the code, or a built Docker image, to anyone — including on a paid basis.
ModifyChange anything, fork it, rip out parts, build a different product on it.
Commercial useRun it as a paid service, sell support, sell a hosted version, bundle it into a product.
SublicenseDistribute a modified version under different terms — including closed-source terms.
Patent licenceContributors grant a royalty-free patent licence for their contributions. This is the main practical difference from MIT.

What it requires in return

  • Keep the licence. Anyone redistributing the code or a derivative must include a copy of the Apache 2.0 licence.
  • Keep notices. Copyright, patent, trademark and attribution notices must stay. If a NOTICE file exists, its contents must be carried forward (this repo has none).
  • Mark changes. Modified files must carry a prominent notice saying they were changed.
  • No trademark grant. Section 6 explicitly withholds rights to the project’s name, logo or branding. A fork cannot market itself as “Mortgage Management by krucx” or imply endorsement.
  • No warranty. The code is provided “AS IS”. Nobody can sue the author because the app miscalculated a loan.
  • Patent peace. If someone sues claiming the software infringes their patent, their own patent licence under this project terminates (the “retaliation” clause).

The one-sentence version: Apache 2.0 is “do almost anything, but don’t pretend you wrote it, don’t use my name to sell it, and don’t blame me if it breaks.”

2. “Can someone steal it?”

Short answer: they cannot legally steal the authorship, but they can absolutely take the code and make money from it. That is not a loophole — it is what this licence is designed to allow. The useful question is which specific scenario you care about.

Someone copies it for their own shop
Allowed
permitted

No obligation to publish anything. They can even keep their changes private because they are not distributing the software.

Someone forks it, rebrands it and sells it as their product
Allowed, with conditions
permitted license + notices kept

They must keep the Apache licence text, retain copyright/attribution notices, and state that they changed the files. They may not use your name or logo to promote it, or imply you endorse them.

Someone turns it into a closed-source paid app
Allowed
permitted

Apache 2.0 is not copyleft. A derivative can be distributed under other terms, provided the Apache conditions are still met for the Apache-licensed parts.

Someone claims they wrote it, or strips your name
Not allowed
infringement

Removing copyright notices or misrepresenting authorship breaches the licence and copyright law. In practice, enforcing this costs time and money, so it is a deterrent rather than a guarantee.

Someone patents a feature and sues you
Weaker position for them
patent grant

Contributors granted a patent licence; a contributor who attacks the project patent-wise loses that licence. This is a real advantage over MIT, which is silent on patents.

Someone clones the public repo on GitHub
Allowed by GitHub’s terms
public repo

Public repositories can be viewed and forked by anyone with an account. The only way to prevent that on GitHub is a private repository.

What Apache 2.0 does not protect: exclusivity. It does not stop a competitor from taking this code, changing the name, and selling it — as long as they comply with the notice requirements. If the goal is “nobody may commercialise this without my permission”, Apache 2.0 is the wrong licence (see §4).

For a jewellery-lending app the realistic risk is not a giant competitor cloning it. It is a local software vendor or an ex-employee taking the code, adding a logo and selling it to nearby shops. Apache 2.0 permits that. What it prevents is them passing it off as entirely their own work or using your branding.

4. If you want more control than Apache 2.0

Licences are a dial, not a switch. From “anyone can do anything” to “nobody can touch it”:

LicenceCan others sell a fork?Must their changes be published?Open source?Good fit when…
Apache-2.0 (current)YesNoYesYou want adoption, contributions, and no legal friction.
MITYesNoYesSame as Apache but simpler; gives up the patent clause.
GPL-3.0Yes, but…If they distribute itYesYou want forks to stay open, but hosting it as a service is still allowed.
AGPL-3.0Yes, but…Even for network useYesYou want to stop a closed-source paid hosted clone.
BUSL-1.1Not for production useDependsNoYou want to sell commercially later, with a timed conversion to open source.
PolyForm NoncommercialNoDependsNoPersonal/educational use only; no commercial use at all.
Private repo / proprietaryNoN/ANoYou want maximum control and do not need public adoption.

Practical warning: changing licence later is painful. Apache 2.0 is irrevocable for code already published, and contributions already merged came in under Apache 2.0. You can relicense future versions, but not retroactively strip rights from existing copies. Decide the strategy now, before more contributors arrive.

For this project specifically, Apache 2.0 is a reasonable default: it is a single-lender niche app, the value is in the domain logic and the trust of the lender, and broad permission helps adoption. If the commercial plan is to sell it to many shops, the more common pattern is open core: keep the core Apache-2.0, and put multi-branch, statutory forms or hosted sync in a separately licensed add-on.

6. Your app: pros & cons

Strengths

  • Free and genuinely open. Apache-2.0 means no seats, no per-loan fee, no vendor lock-in. Any developer can read, audit or extend it.
  • Data never leaves the laptop. No vendor cloud, no third-party processor, no subscription that can be switched off. This is a real advantage under India’s DPDP Act for Aadhaar/PAN photos.
  • Works offline once installed; only update checks and WhatsApp links need the internet.
  • Correct-by-construction ledger. Outstanding is derived from terms and payments every time, never stored. Money-affecting changes show a preview first. Payments are voided, closures reopened — never deleted. That is better audit behaviour than most competitors.
  • Purpose-built domain model. Pledged packets, weights, purity, gold rates, LTV, part payments, split payments across mortgages, redeem/waive/forfeit closures, reminders and a daily call list.
  • On-device OCR for Aadhaar/PAN, with only the last four Aadhaar digits stored. Nothing is uploaded to an OCR service.
  • Backup discipline. Weekly zip backups (password-protected where the platform allows it), a pre-migration backup that blocks the update if it fails, and a documented restore path. This is stronger than many paid products.
  • Engineering quality. Typed API with generated frontend types, migrations, 90% backend / 80% frontend coverage gates, CI, CodeQL, release automation, Pester tests for the Windows installer.
  • Two deployment paths. Double-click Windows setup, or Docker on Intel and Apple silicon. PWA install gives it an app icon and window.
  • No sign-in to lose. Bound to loopback, single user, no password reset flow to attack.

Weaknesses

  • Single user, no authentication or roles. No staff accounts, no per-clerk permissions, no concurrent use from two devices. Fine for one lender; a blocker for a counter with employees.
  • No multi-branch or consolidation. One book, one machine.
  • Compliance gaps. No state pawnbroking registers or statutory forms (e.g. Tamil Nadu Form E/G/H/M), no auction notice or RDO paperwork, no police/pawn-act reporting.
  • Messaging is manual. WhatsApp opens with a prefilled message; the lender presses Send. No bulk sends, delivery tracking, SMS gateway or two-way inbox.
  • No accounting layer. No double-entry, day book, GST invoices, Tally export, trial balance or P&L. The accountant will keep a separate book.
  • Narrow interest engine. Simple, compounded yearly, compounded monthly, plus a part-month rule — but no slab rates, multiple named schemes, daily interest, minimum-interest slabs, renewals or top-ups.
  • No repledge / bank funding module to track gold sent to a bank for liquidity.
  • Gold rates are entered by hand. No live rate feed, no rate history automation.
  • No nominee or guarantor fields (it models Referrers instead), which some state rules and many shops expect.
  • No payment integration. No UPI reconciliation or gateway; only a cash-limit warning.
  • PWA, not a native app. Figures require the laptop/server to be running; there is no phone-first workflow.
  • Windows-first installer. Linux needs manual chown; no macOS installer.
  • Bus factor of one. 1 star, 0 forks, essentially one maintainer. No support SLA, no community, no security certification or independent pen test.
  • Backup encryption caveat. On Windows the README says backups are plain zips because Windows lacks built-in zip encryption — and they contain ID photos.
  • Limited export. Excel/PDF export exists for the call sheet only; there is no one-click full-book Excel/CSV export for an accountant or a migration.

Net: this is a high-quality, narrowly scoped ledger for one lender. It wins on correctness, privacy, cost and offline operation. It loses on everything a growing shop needs: staff, branches, compliance paperwork, messaging automation and accounting.

A practical hybrid: keep your app as the pledge book — it is the strongest part — and add the two things that actually block growth: (1) a one-click full-book Excel export and (2) a printable statutory/auction pack. Both are small features relative to rebuilding the ledger, and they remove the main reasons a shop would be forced onto paid software.

On the licence decision: if you want the code to stay open but stop a paid closed-source clone, AGPL-3.0 is the standard tool. If you might sell it commercially later, keep Apache-2.0 and plan an open-core split. Either way, add the copyright/NOTICE line first — it costs nothing and makes attribution enforceable.
