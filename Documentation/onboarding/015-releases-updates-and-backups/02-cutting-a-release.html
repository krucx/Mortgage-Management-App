Cutting a release

A release starts when a version tag is pushed. How does that one event safely produce an image for Docker and an installer download for Windows?

By the end you can trace the release workflow and explain why the GitHub Release waits for the image.

The problem

Docker installations pull a versioned image. Windows Setup needs the repository files plus already-built browser screens in a zip. If either artifact claims a version different from the code, a Lender may install mismatched pieces.

The idea

A numeric version tag is the release request. The workflow checks the tag against both package versions and runs the reusable test workflow. It publishes one multi-platform Docker image first, tagged with the version and, for the highest version, latest. The old backend-* and ui-* images remain available for older installs to roll back. Then it builds the screens and publishes a Windows zip with the version's CHANGELOG.md section as release notes.

Run-through: run the release preparation steps locally

Run these preparation steps from the repository root. They compare files and build a zip in a temporary folder. They do not push a tag, publish an image or create a GitHub Release. Use the current version, 3.4.1; then try the deliberately wrong 3.4.2 for the version and notes checks.

TAG=3.4.1
BACKEND=$(sed -n 's/^version = "\(.*\)"/\1/p' backend/pyproject.toml)
FRONTEND=$(node -p "require('./frontend/package.json').version")
test "$TAG" = "$BACKEND" && test "$TAG" = "$FRONTEND"
STAGE=$(mktemp -d)
awk -v tag="$TAG" '/^## \[/{if(found) exit; if(index($0,"## [" tag "]")==1){found=1;next}} found{print}' CHANGELOG.md > "$STAGE/notes.md"
test -s "$STAGE/notes.md"
git archive --format=tar --prefix="mortgage-management-$TAG/" HEAD | tar -x -C "$STAGE"
cp -r frontend/dist "$STAGE/mortgage-management-$TAG/frontend/dist"
(cd "$STAGE" && zip -qr "mortgage-management-$TAG.zip" "mortgage-management-$TAG")
unzip -l "$STAGE/mortgage-management-$TAG.zip" | grep "frontend/dist/index.html"

If frontend/dist is absent, run cd frontend && npm run build first. The version check must be repeated after changing TAG to 3.4.2; that check and test -s both fail because the version fields and CHANGELOG are still 3.4.1. The workflow's notes step fails for TAG=3.4.2 because that CHANGELOG heading does not exist. Remove the temporary stage and zip after inspecting them.

The workflow in .github/workflows/release.yml encodes each step; the artifact is made from the tagged source.

Nuances

A valid release tag is exactly x.y.z, with no leading v. The two independently maintained version fields are backend pyproject.toml and frontend package.json; frontend/src/version.ts receives its build version from that package field. The CHANGELOG section starts with a plain summary that says whether the database changes, and an ### Upgrading section. Those notes appear in the banner, so write them for the Lender with the glossary terms.

Predict: If the GitHub Release job ran before Docker image publication, what user-facing failure could follow?

The banner could offer a version whose image Docker cannot yet pull. The workflow explicitly makes the GitHub Release depend on the published image.

Quiz

A release tag disagrees with the frontend package version. What happens?

The workflow tests the tag against both backend and frontend versions before the publish job runs.
