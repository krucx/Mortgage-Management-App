One tag, two distributions

A release starts when a version tag is pushed. How does that one event safely produce an image for Docker and an installer download for Windows?

By the end you can trace the release workflow and explain why the GitHub Release waits for the image.

The problem

Docker installations pull a versioned image. Windows Setup needs the repository files plus already-built browser screens in a zip. If either artifact claims a version different from the code, a Lender may install mismatched pieces.

The idea

A numeric version tag is the release request. The workflow checks the tag against both package versions and runs the reusable test workflow. It publishes the multi-platform Docker image first, then builds the screens and publishes a Windows zip with the version's CHANGELOG.md section as release notes.

Nuance

Predict: If the GitHub Release job ran before Docker image publication, what user-facing failure could follow?

The banner could offer a version whose image Docker cannot yet pull. The workflow explicitly makes the GitHub Release depend on the published image.
