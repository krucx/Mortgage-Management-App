Chapter 015 · Lesson 4

When an update changes the database

A new version can fail before it starts, or it can change the database and then fail. Those failures have different ways back.

By the end you can explain which rollback is safe by switching app versions, and when restoring a -before-update Backup is necessary.

The problem

Each release has its own code and may introduce a database migration. Switching back to old code is safe only while the database is still in a format that code understands. Once the new code migrates the database, the old version may refuse to start.

The idea

Windows Setup installs each version into its own folder, starts it, then points the stable app junction at it only once it answers. The prior version stays available. Before any schema migration, app startup creates a specially named Backup. If the new app cannot run on its migrated database, Setup identifies that Backup; a person restores it deliberately.

ADR 0009 avoids automatic restore because Setup should not silently replace the Lender's data. A code rollback and a data restore are separate decisions. Chapter 010 taught the migration runner; here we focus on the Backup hook and what Setup locates. This chapter also warns traps #8 (the daily run has no scheduler) and #9 (unreleased code can migrate the database).

The flow

The code

The migration code invokes the callback immediately before applying the migration. If a Backup destination is not configured, this callback is absent. A Backup failure prevents the migration from proceeding.

Nuances

When BACKUP_DIR is configured, a pre-update Backup is made only for an existing database whose schema is behind this version; a fresh install takes none. If making that Backup fails, migration does not run and the app does not start. Without a Backup folder, the callback is absent, so migration has no pre-update archive. The CHANGELOG tells the Lender whether the release changed the database and whether the previous version still starts on it.

Predict: An older version starts on a database from a newer version whose migration is unknown to it. Will it make a Backup and then fail?

Current code refuses the unknown revision before calling the Backup hook. This protects the real pre-update Backup from being pruned by repeated failed starts; issue #118 described the earlier failure mode, now fixed in platform/db.py.

Quiz

Why does the app take a Backup before a migration?

A code folder rollback cannot reverse a database schema change; the pre-update Backup preserves the earlier database.
