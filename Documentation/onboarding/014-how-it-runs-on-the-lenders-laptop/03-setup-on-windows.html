Setup on Windows

On Windows the Lender double-clicks Setup.bat, answers two questions, and gets a Desktop shortcut. Behind it are six PowerShell scripts in windows/. You won't read them whole, and you don't need a Windows PC: you'll follow CI's windows job as the story of one install, read the few functions that decide things, and run their Pester tests in Docker.

By the end you can explain what Setup does on a PC, and run and read the scripts' Pester tests.

The problem

The Lender's PC is a stranger's machine. It runs Windows PowerShell 5.1, the version built into Windows, not the modern PowerShell 7 you'd install. It may have Docker or not, git or not, internet or not, admin rights or not. The Lender will run Setup once to install and again, months later, to update, and both must leave their records exactly where they were. Nobody will be there to read an error.

And you can't test it by hand: you probably don't have a Windows PC, and if you did, "install it on my machine" proves nothing about theirs.

The idea

Keep the scripts' decisions in small functions with no side effects, test those with Pester anywhere, and test the whole install end to end on a real Windows machine in CI. The decisions ("which release is newest?", "Docker or not?", "where does the data go?") are pure: they take values and return values. The actions (download, install, start) are thin wrappers around programs. Pester (PowerShell's test framework, chapter 013, lesson 1) can call any function and replace any other with a Mock, so a test can say "pretend Docker is installed" without Docker.

The flow

Notice that setup.ps1 runs the new version's install.ps1, not its own. Setup only fetches code; the code installs itself. So a release can change how it installs without the Lender ever getting a new Setup.bat.

The install folder, %USERPROFILE%\MortgageManagement by default, ends up like this:

MortgageManagement\
├── app\              a junction (a Windows folder link) to the version that runs
├── versions\
│   └── 3.4.1\        that version's code, its .env, backend\.venv, frontend\dist
├── data\             DATA_DIR: mortgage.db and photos (unless the Lender chose elsewhere)
└── backups\          BACKUP_DIR (or a Google Drive / OneDrive folder)

The code

Each of these functions is a few lines. Read them in this order.

  1. Out of its own folder first: an update moves the app junction, and Windows won't change a folder a window is sitting in.
  2. Downloaded on its own (from the docs site), there's no setup.ps1 beside it, so it fetches the newest from GitHub. If GitHub can't be reached, it repeats setup.ps1's offline path inline (start the version installed, or say the first setup needs internet), because there's no setup.ps1 to run. Its comment says: keep the two in step.

Three ways to get a version's code. A release number (3.4.1) gets the ready-built download, mortgage-management-3.4.1.zip from the GitHub Release, which has frontend\dist already built, so the PC needs no Node.js (chapter 015 shows the release workflow that makes it). A release from before that zip existed answers 404, and so does a branch or commit: then the code itself, through git if it's installed, else GitHub's source zip. -Ref main or -Ref <commit> is how CI installs the commit under test.

A pure decision, called by install, run and the version switch. -Mode auto (the default) means Docker if the docker command exists. The choice is saved as RUN_WITH in .env, so run.ps1 later starts the app the same way. Its Pester tests are the three lines of "Docker or local".

  1. An update already has a .env (copied forward from the version before, lesson 4): only RUN_WITH is set, every other line and comment kept (Set-EnvValue; Pester's "changes one value and leaves the rest, comments included").
  2. Without Docker there's no zip program (lesson 1), so Backups are plain zips and a password is cleared, with a yellow warning.

New-EnvText writes the same names as .env.example plus RUN_WITH, and Write-EnvFile writes UTF-8 without a byte-order mark, which Docker Compose would read as part of the first variable's name.

This is ADR 0010's payoff on the PC. A release came built, so Node is never installed and nothing is built: just uv sync for the backend's packages. Only code from a branch or commit needs Node. Pester's "installing without Docker" pins both cases: "needs no Node, and builds nothing, when the screens come built" (uv once, npm and winget never), and "installs Node and builds the screens from the code otherwise" (winget once, npm twice).

  1. The same three variables as the image's line 33 (lesson 1), from .env. With SCREENS_DIR set, the backend serves the screens (lesson 2).
  2. The venv's own python.exe -m uvicorn, not uv run. When the window closes, the finally below stops the process it started. Started through uv run, that process would be uv, and uvicorn under it could keep running. This way the window is the app: close it and the app stops.
  3. Ready means /api/backups answers. Up to five minutes: a start that migrates the database takes a Backup first (chapter 010, lesson 5).

With Docker, run.ps1 instead starts Docker Desktop if needed, runs docker compose up -d --remove-orphans (lesson 4 says why --remove-orphans), and waits for the app. The window can close; the container keeps running.

Now open windows/tests/Launcher.Tests.ps1 and read these Describe blocks. Each It is one sentence of what Setup promises:

DescribeWhat to notice
"Docker or local"Pure: values in, a value out. No mocks needed
"the .env file"A password with spaces and # survives; one with a ' is refused (.env single-quotes it, leaving no way to write one)
"first setup folder selection"Mock Read-Host answers the prompts, so an interactive function runs unattended
"Setup without internet"Tells "can't reach GitHub" (start what's installed) from "GitHub said no", for example a 403 rate limit (don't pretend to be offline, stop)

Then Uninstall.Tests.ps1: which Backup is kept (never a half-written .partial), that it never overwrites a file of the same name, which processes are stopped (Run.bat's window and everything it started, never the uninstaller's own), and which Docker images go (every published version, old backend-/ui- names included, and the :dev builds).

Optional, with a Windows PC or VM. Run what CI runs, into a scratch folder: powershell -ExecutionPolicy Bypass -File windows\setup.ps1 -NonInteractive -Mode local -Ref main -InstallDir C:\scratch\mm, then C:\scratch\mm\app\windows\Run.bat. Remove it with C:\scratch\mm\app\windows\Uninstall.bat. Never leave out -InstallDir on a PC where the app is installed for real.

Nuances

Trap #14: the scripts' rules

Trap #14. Windows PowerShell 5.1 reads a script without a byte-order mark as the PC's old code page, so an em dash or a curly quote in a .ps1 becomes garbage, and inside a string can break the parse. Every file in windows/ is ASCII only and says so in its header. Check before you commit: LC_ALL=C grep -c "$(printf '[\200-\377]')" windows/*.ps1 windows/*.bat windows/tests/*.ps1 prints 0 for each file. Pester in Docker runs PowerShell 7, which reads UTF-8 happily, so it won't catch this; CI's Windows runner will.
  • docs/Setup.bat must stay byte-identical to windows/Setup.bat. The docs site offers it for download, and CI's pages job runs cmp windows/Setup.bat docs/Setup.bat. Change one, copy it to the other.
  • The dot-source guard. setup.ps1, install.ps1, link.ps1 and uninstall.ps1 end like link.ps1's lines 49–50: if ($MyInvocation.InvocationName -ne '.') { Open-Link $Arguments }. Run normally, it does its job. Dot-sourced (. .\link.ps1, which runs a script in the caller's scope), it only defines its functions. That's how Launcher.Tests.ps1's BeforeAll loads common.ps1, setup.ps1, install.ps1 and link.ps1 without installing anything. (common.ps1 only defines functions anyway; run.ps1 isn't loaded by the tests.)
  • Uninstall runs from %TEMP%. Windows won't delete a folder that a window is in, and Uninstall.bat sits inside the folder being deleted. So it changes to %TEMP% first, keeps the latest Backup in Documents (copied, not moved, if the Backup folder is a synced one that stays), and only then removes the Docker images, the shortcut, the link, the data folder and the install folder. Its last line does the rest, because cmd reads a .bat a line at a time and this one is deleted while it runs. With no Backup to keep, it asks again (or, non-interactive, removes nothing).
  • No admin rights anywhere. The install folder is under the user's profile, the shortcut on their Desktop, the link under HKCU (lesson 5). Only Node's winget install may ask, and a release never needs it.

Quiz

Why does setup.ps1 run the new version's install.ps1 instead of its own?

Setup only fetches the code; the code installs itself, so a release can change its own install steps (a new dependency, a new folder) and still be set up by any Setup.bat. Downloading is Get-AppCode's job in either case, and nothing stops 5.1 running several scripts.

Setup installs release 3.4.1 on a PC without Docker or Node. What does Install-Local run?

The ready-built zip has frontend\dist\index.html, so $built is true: no Node, no build. The backend's packages still need installing into backend\.venv (plus uv itself, if missing). Node is only for a branch or commit.

You add a helpful "→" to a Write-Host in install.ps1. Pester passes in Docker. What happens?

Windows PowerShell 5.1 reads a BOM-less script in the PC's code page, so the arrow's UTF-8 bytes become other characters (trap #14). Docker's Pester runs PowerShell 7, which reads UTF-8, so it can't catch it. The pages job compares only Setup.bat.
