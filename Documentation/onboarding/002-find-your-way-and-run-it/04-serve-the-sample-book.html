Chapter 002 · Lesson 4

Serve the sample book

Time to run the app. Not on an empty database, where every screen is blank, and never on a real one: on the course's own invented lending book, frozen on 19 Oct 2026, so the figures you see are the ones chapter 001 taught.

By the end you can build and serve the sample book on scratch data and check a figure on it.

The problem

A fresh app has nothing in it. To see a Ledger, a Call List or a Dormant Mortgage you'd have to type in Customers and Mortgages by hand, and wait months for interest to build up. Worse, the obvious shortcut, opening the app on a copy of the Lender's database, puts real people's names, phone numbers and ID photos on your screen, and one wrong command could migrate or change it.

What you want is a book full of realistic history, made safely, that looks the same on every developer's laptop and every day you open it.

The idea

The sample book, docs/sample-book/book.py, builds the Gold Chain Story's whole year through the app's own API, one dated change at a time, into a folder you choose. Then serve.py runs the real app on that folder with its clock held on 19 Oct 2026. Same code as the Lender's, invented data, and figures that never drift.

The flow

Notice that nothing touches the repo's data/ or backups/. Both scripts write only under the folder you give them.

The code

  1. The book is made the way the Lender would make it: by HTTP requests, each on its date. If a rule in the app would refuse a step, book.py fails at once. So the sample book is also a test that the whole year is still possible.
  2. Clock is the "today" handed to create_app (lesson 2's today parameter). The book moves it forward day by day until THE_DAY.
  1. Port 8765 unless you give another.
  2. lambda: THE_DAY is a function that always returns 19 Oct 2026. Every figure is worked out "as of" that day, every time.
  3. Backups go inside your scratch folder, never to the real BACKUP_DIR.
  4. The screens are the built ones in frontend/dist, served by the backend itself, as on a Windows laptop without Docker (lesson 1's third front door, ADR 0010).

Run-through: serve it, then recheck Meera's chain

You need uv and Node.js installed. From the repo root:

# 1. A fresh, empty scratch folder for the book
export BOOK=$(mktemp -d)

# 2. Build the book into it (a few seconds)
cd backend
uv run python ../docs/sample-book/book.py "$BOOK"

# 3. Build the screens (once, and after every frontend change)
cd ../frontend
npm install
npm run build

# 4. Serve it on http://127.0.0.1:8765
cd ../backend
uv run python ../docs/sample-book/serve.py "$BOOK"

mktemp -d makes a new empty folder under your system's temporary area and prints its path; $(…) captures that path into BOOK. Keep the terminal open: serve.py runs until you press Ctrl-C.

Nuances

(a) A fresh database is not the book

Predict: serve an empty folder (serve.py "$(mktemp -d)" 8766), which gives a brand-new database, and ask both apps for their Default Terms with curl -s http://127.0.0.1:<port>/api/settings/default-terms. Will the two answers match?

Databasemonthly_rate_bpsinterest_modepart_month_rule
Fresh (port 8766)300compounded_yearlyfull_month
Sample book (port 8765)200compounded_yearlypro_rata

From scripts/run_throughs.py.

No. A fresh database starts with Default Terms of 3% a month (bps is basis points: 300 = 3.00%), Compounded Yearly, full month. Those come from the very first database migration, 0001_config_table.py. The sample book changes them to 2% pro-rata as one of its first steps, through PUT /api/settings/default-terms. So when you see "2%" in this course, it's the sample book's Default Terms, not the app's. Serving an empty folder is also the quickest way to get a blank app on scratch data.

(b) The clock is held

Predict: you serve the same book again next week. Is the chain's Interest to Date still ₹533?

Yes, ₹533, next week and next year. serve.py passes today=lambda: THE_DAY, so the app always believes it's 19 Oct 2026. That's what makes the course's figures checkable. The backend you run while coding (lesson 5) uses the real today, so on any Mortgage there, Interest to Date grows a little every day you look.

(c) serve.py shows the built screens

Predict: with serve.py running, you change a heading in MortgagePage.tsx and reload the page. Do you see it?

No. serve.py serves frontend/dist, the output of the last npm run build. Your edit is in src/ and isn't in dist until you build again. The installed app's service worker can also keep the old screens cached until the update is picked up. For live edits, use Vite's dev server instead (lesson 5).

(d) Rebuilding needs a fresh, empty folder

Predict: you run book.py "$BOOK" a second time into the same folder. What happens?

It stops early with an AssertionError:

AssertionError: POST /api/customers: {"detail":"Contact number 1 9810012345 already belongs to Customer Meera Sharma"}

From scripts/run_throughs.py.

The book adds Meera again through the API, and the app refuses: a Primary Number belongs to one person only (ADR 0005). The app is protecting the data, just as it would for the Lender. Make a new folder with mktemp -d each time you rebuild.

Quiz

Why does book.py make the book through the API, not by inserting rows?

Through the API, each change is refused if the app would refuse it, and every check runs, on the date it happened. Rows inserted directly would skip all of that and could make a book the app itself could never produce. Speed and locking aren't the reason.

On the served book, "total": 8333300. What does Meera owe?

The API works in paise, so divide by 100: ₹83,333. The screens show it with Indian grouping.

A course page says the chain's rate is 2% a month. A fresh database says 3%. Which is a bug?

Neither. A fresh database starts at 3% (migration 0001), and book.py sets the sample book's Default Terms to 2% pro-rata before making any Mortgage.
