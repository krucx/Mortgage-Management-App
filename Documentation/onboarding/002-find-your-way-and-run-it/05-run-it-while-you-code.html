Chapter 002 · Lesson 5

Run it while you code

The served book is perfect for looking, but every frontend edit needs a rebuild and every backend edit a restart. How do you get both halves reloading as you type, still on scratch data, and how do you run the checks before you commit?

By the end you can run the backend and frontend with hot reload on scratch data, and run the test and type-check commands.

The problem

A developer's loop is edit, look, edit, look. If each "look" means npm run build and restarting serve.py, that loop takes a minute instead of a second. The README's two hot-reload commands fix that, but run as written they quietly pick a database for you, and it may not be the one you think.

The idea

Run each half in its own development server. Vite serves the frontend straight from src/ and updates the page the moment you save. Uvicorn with --reload restarts the backend whenever a Python file changes. Vite passes /api to port 8000, so whatever backend listens on 8000 is the one your screens talk to. Always tell that backend which folder to use.

The flow

The code

The port is fixed: 8000. That's the whole trick of option 1 below.

Both defaults are relative paths: data and backups, relative to the folder you start uvicorn in. main.py calls these two functions when it builds the module-level app that uvicorn imports. This is what the Lender's installed app relies on; for you it's a trap (nuance a).

Run-through

Option 1: hot-reload screens on the frozen sample book

When you're working on a screen, you want the familiar figures from lesson 4. Serve the book on port 8000 instead of 8765, and Vite will use it:

# terminal 1: the sample book, as the backend on :8000 (BOOK from lesson 4)
cd backend
uv run python ../docs/sample-book/serve.py "$BOOK" 8000

# terminal 2: the screens, hot reloading
cd frontend
npm run dev

Option 2: the general case, both halves reloading on scratch data

When you change backend code, run uvicorn with --reload and give it its own scratch folders:

# terminal 1: the backend on :8000, on scratch data
export DEV=$(mktemp -d)
cd backend
DATA_DIR="$DEV/data" BACKUP_DIR="$DEV/backups" \
  uv run uvicorn mortgage_backend.main:app --reload

# terminal 2: the screens
cd frontend
npm run dev

NAME=value command sets an environment variable for that one command only. The backslash continues the command on the next line.

Nuances

(a) Forgetting DATA_DIR

Predict: you run the README's line as written, cd backend && uv run uvicorn mortgage_backend.main:app --reload, with no DATA_DIR. Where is the database, and does anything warn you?

It's backend/data/mortgage.db, created silently, with Backups in backend/backups/. Nothing warns you: both folders match the data/ and backups/ lines of .gitignore, so git status stays clean too. It's harmless as long as nothing real is in there, but it's easy to forget it exists, and easy to start uvicorn from another folder one day and get a different database. Always pass both variables, pointing at a scratch folder.

(b) The serve.py-on-8000 trick

That's option 1 above: because Vite's proxy only knows "port 8000", any backend you put there becomes the screens' backend, including the frozen sample book. Two warnings: only one process can hold port 8000, so stop uvicorn first; and remember the clock is held, so anything dated "today" is 19 Oct 2026.

(c) The first request of the day does work

Predict: the app has no scheduler. So when does the weekly Backup happen, and when are the day's Notices queued?

On the first /api/ request of each day. A middleware is a function FastAPI runs around every request; this one runs the daily jobs first if they haven't run today. The jobs are: take a Backup into BACKUP_DIR if the last is a week old, and queue Notices. The app also tries a Backup when it starts. So simply opening your dev app writes a Backup zip into BACKUP_DIR, which is one more reason that must be a scratch folder, not the Lender's synced folder. Chapter 010, lesson 2 explains the daily run.

(d) Docker, in one box

Plain docker compose up runs the published image, not your code. docker-compose.yml pulls the release from Docker Hub. To run this folder's code, add the dev file, which builds the image locally:

export DEV=$(mktemp -d)
DATA_DIR="$DEV/data" BACKUP_DIR="$DEV/backups" APP_PORT=8081 \
  docker compose -p mortgage-dev -f docker-compose.yml -f docker-compose.dev.yml up -d --build
# … try it on http://localhost:8081 …
DATA_DIR="$DEV/data" BACKUP_DIR="$DEV/backups" \
  docker compose -p mortgage-dev -f docker-compose.yml -f docker-compose.dev.yml down
  • Scratch DATA_DIR and BACKUP_DIR on every docker compose command, including down. Compose otherwise reads them from a .env file in the repo root. If you've set the app up for real from this clone, that .env points at the real data.
  • Migrations run on every start, against whatever DATA_DIR they get, and there is no way back to the old schema. Unreleased code started on real data migrates it for good (chapter 010, lesson 5).
  • -p mortgage-dev gives your containers their own project name, and APP_PORT=8081 their own port, so they never replace or collide with a copy of the app already running from this folder on 8080.

Nothing in this chapter needs Docker. Chapter 014 covers it properly.

Quiz

Vite is running. You start serve.py "$BOOK" 8765. What does localhost:5173 show?

Vite proxies /api to port 8000 only. With the book on 8765, every request fails. Vite holds no database of its own.

You start uvicorn from the repo root instead of backend/, without DATA_DIR. Which database does it open?

The default is the relative path data, so from the repo root it's the root's data/, which may hold a real book. That's exactly why you always pass DATA_DIR.

Why do you pass scratch DATA_DIR/BACKUP_DIR to docker compose down too?

Every docker compose command reads the same configuration. Leave the variables out and Compose fills them from .env, so the command you think is about scratch data may be about the real stack. down doesn't delete data or take a Backup.
