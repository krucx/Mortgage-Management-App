Chapter 002 · Lesson 1

The repo at a glance

You've cloned the repo and see a dozen folders and files at the top. Which ones hold the app, which hold its documents, and which ones you'll never touch in your first month?

By the end you can say which top-level folder a piece of work belongs in.

The problem

Suppose your first ticket says: "Meera's Receipt should show the jewellery's weight." Where do you start? The Receipt is a screen, so maybe the frontend. But its words come from the backend. And the screenshots on the project's website show Receipts too, and there's a folder of Windows scripts that installs the app. A newcomer who guesses opens the wrong folder, reads a hundred lines, and still isn't sure.

The fix is a mental map: every top-level folder has one job. Learn the jobs once and most tickets tell you where they live.

The idea

The repo is one app in two halves, a backend (Python) that owns the data and every rule, and a frontend (TypeScript) that draws the screens. Around them sit the ways the app gets onto the Lender's laptop, and the documents that explain it.

The map

Notice that docs/ and Documentation/ are different things. docs/ is the public website (GitHub Pages: the install guide, the walkthrough, The Gold Chain Story). Documentation/ is for developers: the ADRs, the agents' instructions and this course.

The code: how the two halves meet

The README's Development section gives the shortest possible picture of the app: two processes, one per half.

  1. uv is the Python package manager this repo uses; uv run runs a command inside the backend's own virtual environment, installing what's missing first. uvicorn is the web server that runs the FastAPI app, here the object app in mortgage_backend/main.py.
  2. Vite is the frontend's build tool. npm run dev starts its development server, which serves the screens and passes every request under /api on to the backend.

That one fact, "the screens call /api/… and something passes it to the backend", is how the app is wired everywhere. What changes is who serves the screens.

Three ways the screens are served

The same backend and the same screens run in three different set-ups. You'll meet all three, so here they are as a picture. How each one works inside is chapter 014's subject.

Two ADRs explain the Lender's two set-ups. ADR 0004 ships the app as a Docker Compose stack, so nobody installs Python or Node on the Lender's laptop. ADR 0010 is for laptops without Docker: the backend serves the built screens itself, so there's one process and no Node.js. You only need their names for now.

Quiz

Where does the GitHub Pages install guide live?

docs/ is the GitHub Pages site (docs/install.html). Documentation/ is for developers only, and windows/ holds the installer scripts, not the page about them.

You run npm run dev. A page asks for /api/mortgages/2. Who answers?

Vite serves the screens and proxies /api to the backend on :8000. Vite holds no data, and nginx only runs in Docker.

What is in Requirements/?

It holds the original spec and the owner's lists of enhancements to pick up later. Today's rules are in the code, its tests, the glossary and the ADRs. Versions live in backend/pyproject.toml and frontend/package.json.
