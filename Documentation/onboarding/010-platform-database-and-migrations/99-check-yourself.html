Chapter 010 · Check yourself

Check yourself: Platform, database and migrations

Questions from all six lessons, mixed up. Then add one column three ways, and see which of them the tests catch.

Quiz

1. You build a fresh sample book and serve it. Its first /api/ request arrives. Do the daily jobs run?

book.py builds the book through the API up to 19 Oct, so the daily run already ran that day and wrote last_daily_run. The check reads the database, not anything about this server. The start-up Backup came from the lifespan, not the daily run. (Lesson 2; scripts/run_throughs.py, section L2.)

2. A test builds its app with conftest.py's client fixture and reads Meera's Outstanding. Which day is "today" in that test?

The fixture calls create_app(database_url, today=lambda: TODAY) with TODAY = date(2026, 4, 20). 19 Oct 2026 is serve.py's. The real date is only the default, used when no today is passed. (Lessons 1 and 2.)

3. The Customers list on the book, sorted by Referrer, descending. Who comes straight after Meera (id 1)?

Arjun and Sunita are both referred by Meera Sharma, a tie. ties=[customer_table.c.id] is sorted in the same direction as the key, so descending puts id 7 before 2. Customers with no Referrer sort as "", last when descending. (Lesson 4; section L4: 1, 7, 2, 6, 5, 4, 3.)

4. Suppose the Cash Limit were stored as a ConfigGroup with cash_limit: int | None = 20_000_00. The Lender clears it (None). What would it read back as?

set deletes the key of a field set to None, and get fills a missing key from the model's default. That's exactly why the Cash Limit isn't a ConfigGroup and stores an empty string by hand. (Lesson 3; section L3: with its key deleted, get_cash_limit reads 2000000.)

5. A test upgrades a database to 0013 by hand, then builds the app with no backup_dir and starts it. What happens?

With no Backup folder, the lifespan passes before_update=None, so migrate skips the Backup and upgrades. Leaving out an argument switches a feature off; it never stops the app starting. (Lessons 1 and 5.)

6. On 26 Oct the Lender opens the laptop. The last Backup was 19 Oct. The screen loads, then calls GET /api/dashboard. Which code takes the week's Backup?

If the app started that morning, the lifespan checks first and takes it (7 days are up). When the daily run gets to it on the first /api/ request, the last Backup is from that morning. If the app had been running since before, the daily run would take it instead. (Lesson 2, nuance (a); section L2.)

7. You need a Customer nickname column. Which files do you edit?

The migrations build the database; db.py's Tables are what the code queries. Neither is made from the other, so both change, and test_the_migrations_build_the_tables_the_app_declares checks they agree. (Lessons 4 and 6.)

8. Why can't you fix a bug in released migration 0015 by editing 0015?

Alembic decides what to run from alembic_version alone. Every 3.2.0 database already says 0015, so the edit only reaches new installs, and two databases at "0015" would differ. A fix goes in a new revision. Alembic keeps no hash of the files. (Lesson 6.)

Hands-on: one column, three ways

  1. Run the suite to see it's green: uv run pytest -q. 607 passed.
  2. In src/mortgage_backend/platform/db.py, add one line to customer_table, right after Column("pan_photo", String), (line 69): 
        Column("nickname", String),
    Change nothing else. Predict, then run uv run pytest -q. It takes a minute or so longer than usual: failing tests are slow.

Check: how many broke, and with what error?

179 failed, 243 errors, 185 passed (at commit b34526a): 422 of 607 broken, all the same way:

sqlite3.OperationalError: no such column: customer.nickname

An error is a test whose fixture failed before the test body ran (usually a seed that creates a Customer); a failure is a test whose own code hit it. Every select(customer_table) asks for every column the Table declares, and the migrated test databases don't have nickname. The 185 that pass never read a Customer: the pure Ledger tests, the settings tests, and so on.

  1. Remove that line again (git checkout -- src/mortgage_backend/platform/db.py). Instead, create src/mortgage_backend/migrations/versions/0016_customer_nickname.py exactly as in lesson 6 (copy 0015, change the numbers to 0016/0015, add only nickname). Predict, then run uv run pytest -q.

Recap

  • create_app is the composition root: it builds the engine, Backups and the daily run, puts them on app.state, adds the routers and the screens last. The real app builds it from the environment (DATA_DIR, the Backup and screens folders); tests and serve.py call it with their own clock and folders. Leave out an argument and that feature is off. Starting runs the lifespan: clean leftovers, migrate, the weekly Backup if due (lesson 1).
  • "Today" is whatever today function the app was built with, read through TodayDep; nothing else calls date.today(). Business dates follow TZ. There is no scheduler: the first /api/ request of each day runs the Backup check and the Notice sync, under a lock, with the date in config so a restart doesn't repeat them. A failing job is logged and the next still runs (lesson 2, trap #8).
  • Settings are text rows in config. A ConfigGroup declares a model and its keys once: get fills missing keys from defaults, set stores text (true/false), deletes fields set to None, and runs after_set on the same transaction. The Cash Limit isn't one, because cleared must differ from never set (lesson 3).
  • db.py declares 12 Tables, with no ledger table (ADR 0001). make_engine switches on foreign keys; engine.begin() rolls a refused change back. query_page sorts and pages in SQL; rows_page pages lists worked out in Python. 20 rows a page, total on every page, and ties make descending the exact reverse (lesson 4).
  • Every start runs migrate: a revision this code doesn't know is refused before anything runs; an existing database that isn't at the head gets a -before-update Backup first, and if that fails nothing is migrated; a fresh install gets none. Every test database is built by the chain, so migrations run on whatever DATA_DIR they're given (lesson 5, trap #9, ADRs 0003 and 0009).
  • A new column is a new revision (copy the last, next number) plus its db.py mirror, nullable or with a server_default for old rows. The drift test checks the two agree; a start on a copy of the book checks it works on real rows. A released revision is never edited; a fix is another revision. The CHANGELOG says "Updates the database" (lesson 6).
