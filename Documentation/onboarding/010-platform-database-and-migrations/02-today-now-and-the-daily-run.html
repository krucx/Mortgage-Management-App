Chapter 010 · Lesson 2

Today, now and the daily run

Almost every figure in this app depends on what day it is: the Interest to Date, Months Unpaid, the Call List, which Notices exist. This lesson shows where the app's "today" comes from, and how the once-a-day jobs run on a laptop with no scheduler.

By the end you can say which date the app thinks it is, and what runs on the first request of each day.

The problem

Two problems, both about time.

Which day is it? Meera's chain owes ₹83,333 on 19 Oct and more on 20 Oct, because the Interest to Date grows every day. A test that checks that figure must get the same answer tonight and next year. The sample book must stay on 19 Oct 2026 forever. And on the Lender's laptop, "today" must be the Lender's today in India, not the server's idea of it in some other time zone: at 2 a.m. on 20 Oct in Delhi, it is still 19 Oct in London.

Who runs the daily jobs? Two things should happen once a day: a Backup when the last one is a week old, and the Notice queue brought up to date. A server would use a scheduler (cron, or a timer thread) set for, say, 6 a.m. But this app runs on the Lender's laptop, which may be asleep at 6 a.m., shut for the weekend, or left running for weeks (trap #8). A job that fires at a set time misses every day the laptop was off, and nobody notices.

The idea

Today is an argument. The app never asks the computer for the date directly. It calls whatever today function it was built with (lesson 1). Nothing outside create_app's defaults calls date.today() or datetime.now().

The day's first request runs the jobs. If the Lender is using the app, a request will come. So the first /api/ request of each calendar day runs the daily jobs, then carries on. The date of the last run is written in the database, so a restart on the same day doesn't run them again.

Think of the first person into an office each morning: they switch on the lights and the kettle. Nobody has to arrive at 6 a.m. to do it, and the second person in doesn't do it again. A note on the door ("lights on: 20 Oct") stops someone who pops out and back from doing it twice.

The flow

Notice that the date is written before the jobs run. If a job fails, the day still counts as done. The jobs aren't retried on the next request; they run again tomorrow.

The code

1. Today and now, as dependencies

The same pattern as EngineDep in lesson 1: read what create_app put on app.state. today is the business date: the day used for interest, Accrual Dates and Notices. now is a full date and time, used where the minute matters: History entries (chapter 006) and Backup file names.

The rest of clock.py is two small helpers for lists filtered by month: MonthQuery accepts a query parameter like 2026-04 (a regular expression rejects 2026-13), and month_span("2026-04") gives its first and last days. The Payments list (?month=) and the Closures list (?closed_in=) use them.

2. The middleware

A middleware is a function FastAPI runs around every request, before the route.

  1. Only API requests count. Loading a screen, a picture or /docs never runs the jobs.
  2. run_if_due is ordinary (blocking) code that talks to the database. run_in_threadpool runs it on a worker thread, so the server's async loop isn't stuck while it does. The request still waits for it (await).
  3. Then the request carries on to its route as usual.

3. The daily run

  1. The last run's date is one row in the config table, key last_daily_run. ConfigGroup reads and writes it as a small model; lesson 3 opens it.
  2. The server answers several requests at once, each on its own thread. Without a lock, two requests arriving together could both read "not run today" and both run the jobs. threading.Lock lets one thread in at a time.
  3. The check and the write happen in one transaction, inside the lock, and the transaction commits when the with block ends, before any job runs.
  4. Each job gets the business date. One failing is logged, and the next still runs.

The two jobs are the ones you saw in lesson 1 (main.py lines 72–74): backup.start_if_due, which only starts a Backup on a background thread when the last one is 7 or more days old, and sync_notices (chapter 009, lesson 3). Both return quickly, which matters: the day's first request waits for them.

Nuances

(a) Two places start a Backup

Predict: look at the 26 Oct rows. The last Backup is 7 days old. Which code took the new one: the daily run on the first request, or something else?

The lifespan (main.py line 87), before any request. It calls the same start_if_due as the daily run. By the time the first request runs the daily jobs, the last Backup is from that morning, so the daily run doesn't take another. Starting a Backup at start-up means a Backup that a shutdown interrupted is retried the next time the app starts. So "the weekly Backup runs on the first request" is only half true: on a laptop that is switched on each morning, it usually runs at start-up. test_backups.py line 278 pins the retry.

(b) A job that fails

Predict: the first job raises an error. Does the request fail? Does the second job run? Does the next request try again?

The request gets its normal 200, and the second job runs (the script swaps in a job that raises ValueError("boom"), then one that records the date: it recorded 20 Oct). The error goes to the log as "Daily job … failed". The next request does not try again, because last_daily_run was already written. A failing Backup also records backup_last_error, which the Settings screen shows, so the Lender finds out (chapter 015).

From scripts/run_throughs.py (section L2).

(c) Whose midnight?

date.today() gives the date in the time zone of the process it runs in. In Docker that would be UTC unless told otherwise, so docker-compose.yml sets TZ: ${TZ:-Asia/Kolkata} for the backend: India, unless the Lender's .env says otherwise. Without it, from 00:00 to 05:30 in India the app would still think it was yesterday, and a Payment typed at 1 a.m. would be refused as dated "in the future". Business dates follow TZ; that's what clock.py's first line means.

Quiz

On 20 Oct the Lender opens the app. The browser loads the Dashboard screen (/), its JavaScript and its icons. Then it calls GET /api/dashboard. Which of these runs the daily jobs?

Only paths starting /api/ run the middleware's check (line 107). The screen, scripts and icons don't. There is no 6 a.m. run: there's no scheduler at all.

The app was restarted at noon on 20 Oct after running the daily jobs at 9 a.m. What happens on the first request after the restart?

The check reads the date from config, which survived the restart. count is only an in-memory counter for tests. (The lifespan's own start_if_due still checks the Backup at the restart, but a Backup taken that morning means none is due.)

A test calls create_app(database_url) with no today, and checks an Interest to Date figure. What's wrong with it?

today defaults to date.today, the real clock. The test would pass today and fail tomorrow. 20 Apr 2026 only applies to apps built through conftest's client fixture, which passes today=lambda: TODAY.
