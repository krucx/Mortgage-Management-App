Chapter 006 · Lesson 1

One door for every change

Every change to a Mortgage or Payment goes through one function in lending/changes.py, and every one of those functions takes the same four steps. This lesson walks one change through them: the 1.5% rate the Lender gave Meera's bangles on 12 Oct.

By the end you can name every change in changes.py, find its route, and walk one through refuse → write → check → History.

The problem

On 12 Oct Meera asked for a lower rate on her bangles. The Lender agreed to 1.5% a month instead of 2%, from the bangles' next Accrual Date, 25 Oct. In the app, that's a Term Change: a dated change to some of a Mortgage's Terms (its rate, Interest Mode and Part-Month Rule), applying to the months from then on. Chapter 004, lesson 5 showed how the engine uses one. This lesson is about how one gets saved.

Saving it isn't just an INSERT. Several things could be wrong:

  • The date might not be an Accrual Date, or might be in the past, which would rewrite interest already charged.
  • There might already be a Term Change on that date.
  • The Mortgage might be closed.
  • The "change" might change nothing.

And once it's saved, every Ledger it touches has to still make sense, and the change has to appear in the Mortgage's History. The same is true of a Payment, a Void, an edit, a Closure. If each route handled those concerns its own way, one of them would eventually forget one.

The idea

Each change is one plain Python function in changes.py that takes a database connection and does four things in order:

  1. Refuse if the change isn't allowed, by raising an HTTPException.
  2. Write the new facts.
  3. Check by replaying every Mortgage it touches (lesson 2).
  4. Record it in History (lesson 3).

The route around it does nothing but parse the request, call the function inside a transaction, and send back the result. The rules stay out of the route on purpose: then a Preview (lesson 4) can run exactly the same function.

The flow

Notice that the route reads the Mortgage back inside the same transaction, so the answer shows exactly what was just saved.

2. The route: parse, call, answer

  1. FastAPI turns the JSON body into a TermChangeIn (a Pydantic model, lines 96–102) before your code runs. A body that doesn't fit it, such as a rate of 0, is refused with a 422 right here, and the change function never runs.
  2. engine.begin() opens a transaction and commits it when the with block ends normally. If anything inside raises, it rolls back instead. Everything the change writes, History included, is saved together or not at all.
  3. The only line that does anything. today and now come from the app's clock (held on 19 Oct 2026 for the sample book), never from date.today(), so tests and the sample book can choose the day.
  4. Read back inside the transaction, so the page gets the Mortgage as just saved, with its new Term Change.

Every save route in lines 905–1090 has this shape. Open the file and skim them: post_payment, put_mortgage, post_redeem, … each is a few lines long.

3. The change function, part 1: refuse

  1. A closed Mortgage takes no changes until it's Reopened. The helper is shown below.
  2. Leave the date out and you get the next Accrual Date after today. next(generator) returns the first value the generator yields.
  3. Not an Accrual Date, or in the past: the request can't stand. unprocessable makes the 422.
  4. A Term Change already on that date: the request is fine in itself, but the Mortgage is already in a state that blocks it. That's a 409.
  5. The Terms that would be in force for the month starting that day, earlier Term Changes included.
  6. audit.changes (lesson 3) lists the fields whose values differ. model_dump(exclude_none=True) leaves out the fields the request didn't give, so they carry over from before. If nothing differs, there's nothing to change.

4. The change function, part 2: write, check, History

  1. Only the fields in changed get a value. The others stay NULL, meaning "carry over whatever is in force then". The comment at line 390 says why: "so a later Term Change keeps its own effect". If this one stored the Interest Mode too, a different mode set by an earlier Term Change would be overwritten from here on.
  2. Replay the Mortgage with the new row in place (lesson 2).
  3. One History row for the date, and one for each changed field (lesson 3).

5. Two kinds of refusal

Note that unprocessable returns the exception and the caller writes raise unprocessable(…). That way a type checker sees the raise and knows the code after it can't run. The message in both cases is shown to the Lender as it is, so it's written for them: plain words, the Mortgage Name, a date.

StatusMeansExamples in changes.py
409 ConflictThe request makes sense, but the thing isn't in a state that allows itA closed Mortgage ("reopen it first"); a Term Change already on that date; a Payment already Voided; a Mortgage Name already used; Reopening an Active Mortgage
422 UnprocessableThe request can't stand as asked, whatever the stateA date in the future or not an Accrual Date; a change that changes nothing; a Payment larger than what was owed (lesson 2); a body FastAPI can't parse
404 Not FoundNo such Mortgage, Payment, Term Change or photomortgage_row; void_payment; remove_term_change

The frontend shows the message whatever the status (chapter 011). The status mostly tells you, reading a test or a log, which kind of refusal it was.

Nuances

(a) A change that changes nothing

Predict: you ask for 1.5% from 25 Nov. 25 Nov is an Accrual Date and has no Term Change. What happens?

422  The Term Change must change the rate, mode or rule

From 25 Oct the bangles are already at 1.5%. terms_on(25 Nov) includes the 25 Oct Term Change, so changed comes out empty and line 397 refuses. A Term Change is compared with the Terms in force then, not with the Terms the Mortgage started with.

From scripts/run_throughs.py (section L1).

(b) A closed Mortgage

Predict: POST /api/mortgages/3/term-changes with {"monthly_rate_bps": 100}. Mortgage 3 is Kavita's coin, Redeemed on 5 Oct. 409 or 422, and from which line?

409  2026-Kavita-GoldCoin is redeemed: reopen it first

Line 374, the first check. A closed Mortgage is refused for being closed before anything else is looked at, the same rule chapter 005 met in closable. It's a 409 because the request would be fine on an Active Mortgage.

From scripts/run_throughs.py (section L1).

(c) A refusal before your code runs

Send {"effective_on": "2026-11-25", "monthly_rate_bps": 0} and you get a 422 whose detail is a list, not a sentence: [{"type": "greater_than", "loc": ["body", "monthly_rate_bps"], "msg": "Input should be greater than 0", …}]. That comes from FastAPI checking the body against TermChangeIn's Field(gt=0, le=10_000), before post_term_change runs. Rules about the shape of one field go on the request model. Rules that need the database (Is it an Accrual Date? Is it taken?) go in the change function.

(d) The whole change is one transaction

Every step writes through the same conn, inside the route's engine.begin(). If check_replays refuses at step 3, the row written at step 2 is rolled back with it. If anything after History raised, the History would be rolled back too. That's why the change functions don't need any clean-up code: they just raise. It's also why a refused change never leaves History behind (lesson 3).

Quiz

Where is the rule "a Term Change starts on an Accrual Date" written?

It needs the Mortgage's start date, so it can't be on the request model. Routes only parse, call and answer. It's in the change function (line 379), which is also what the Preview runs.

Voiding a Payment that is already Voided. Which status?

void_payment raises 409 "Already voided". The request is fine; the Payment's state blocks it. A Voided Payment still exists (it's kept, marked voided_at), so it isn't 404.

The bangles' Term Change row has interest_mode NULL. What does that mean?

Only what differs is stored (line 402). NULL means "whatever is in force then", so a later Term Change that sets the Interest Mode keeps its effect.
