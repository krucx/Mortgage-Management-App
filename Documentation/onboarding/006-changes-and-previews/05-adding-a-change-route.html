Chapter 006 · Lesson 5

Adding a change route

You now know every piece of a change. This lesson puts them together as a checklist, walks it against the smallest complete change in the app, the Collateral Value set by hand, and has you sketch a change of your own on paper.

By the end you can list everything a new change needs: change function, save route, Preview route, History Action, tests.

The problem

Sooner or later the Lender will ask for something new: "let me move a Term Change to a later month", say. The code for it is small. The risk is in what you forget: a Preview that doesn't refuse what the save refuses, a change that isn't in History, a check that should have run, or frontend types that no longer match the API. Each of those passes a quick manual test and then bites in use.

The idea

Copy the shape of a change that already works, and tick off the same pieces every time. The smallest change that has all of them is set_collateral. The Collateral Value is what the jewellery is worth today: its net weight at the Gold Rate for its purity, unless the Lender sets a value by hand. Chapter 008 owns how it's valued. Here we only need the change that sets it.

The flow

The code: Collateral Value, piece by piece

1 and 4. The request model and the save route

  1. Field-level rules go on the model: a value, if given, must be above 0. None means "clear it". Money is always paise (trap #6).
  2. The lesson 1 shape: engine.begin(), call, read back.

2. The change function

  1. Refuse: no such Mortgage, a closed one (the jewellery isn't held any more), a value of ₹0 or less. Line 525 repeats CollateralIn's rule, because the function can be called without the route: from a test, or from another change. Don't rely on the route alone.
  2. Write two columns: the value, and the day it was set.
  3. There's no step 3. A Collateral Value isn't one of the facts a Ledger is replayed from, so nothing could become too large. If your change touches anything replays() reads (the mortgage row's Principal, start date or Terms, Payments, Allocations, Term Changes, the Closure), call check_replays.
  4. An existing Action, edited, fits, so no new literal is needed. Note the guard: setting the same value again records nothing.

5. The Preview route

  1. Never engine.begin() in a Preview (lesson 4).
  2. The real change, between two reads.
  3. This is one of the two Previews with its own shape, so it does its own try … finally: conn.rollback() instead of calling _preview. A Ledger-changing change would just call _preview with a lambda.
  4. What the Lender needs to decide: would the Loan-to-Value (the Outstanding as a share of the Collateral Value) put the Mortgage on the Call List? Chapters 008 and 009 own those two.

6. The tests

Each change is tested at two levels, in two files:

7. The generated types

Trap #10. The frontend's API types are generated from the backend. A new or changed request model, response model or Action literal means running npm run gen:types in frontend/ and committing both frontend/openapi.json and frontend/src/api.gen.ts. Forget, and tests fail in both languages. Chapter 011, lesson 1 owns this trap.

Your turn, on paper

The Lender asks: "Meera's bangles go to 1.5% from 25 Oct. She's now asked to wait a month. Let me move that Term Change to 25 Nov, instead of removing it and adding it again." Sketch the pieces on paper: names, routes, every refusal with its status, whether it calls check_replays, its History, and its tests. Don't write the code. Chapter 016 is where you make a real change, test-first, through every layer.

Did you reuse the refusals of add_term_change and remove_term_change rather than inventing new ones? Did you put every rule in the change function, so the Preview gets them for free? Those are the two habits this chapter is about.

Nuances

(a) The same pattern for Customers

Changes to a Customer live in people/customer_changes.py, not changes.py, and follow the same pattern: a change function that refuses, writes and records History (entity "customer"), and routes that only parse, call and answer. Customers have no Ledger, so there's no check_replays. Chapter 008, lesson 3 owns it.

(b) Changes with a file

A photo is a file on disk as well as a row. A database transaction can roll back a row, but not a file. The photo routes wrap their change in photos.photo_change (in platform/photos.py), which writes the new file first, deletes it if the change is refused, and deletes a replaced file only once the change is saved. That's why post_photo (changes.py line 1064) doesn't use engine.begin() itself. Chapter 008, lesson 4 owns it.

Quiz

Your new change edits a Mortgage's start date by a new route. Which piece must you not leave out?

The start date is read by replays(), so a Payment could become too large. An existing Action (edited) may fit. The Preview must never copy the rules: it calls the same change function.

You added a field to a request model and all backend tests pass. What's left before committing?

Trap #10: the frontend's types are generated into openapi.json and api.gen.ts, and tests in both languages compare against them. A request model isn't a table, so it needs no migration.
