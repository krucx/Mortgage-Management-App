Chapter 012 · Lesson 6

The installed app (PWA)

The Lender doesn't open a browser and type an address. They click the app's icon, like any other program. This lesson is about what makes that work: the service worker that caches the screens (and never the figures), the screen shown while the server is stopped, and the banner that offers an update.

By the end you can say what the service worker caches and why, and what the Lender sees when the server is stopped or an update is out.

The problem

The app runs on the Lender's own laptop: a backend serving the API and the built screens on one port. Chrome lets a website be installed as a Progressive Web App (PWA): it gets an icon and opens in its own window. But an installed website is still a website. Click the icon while the server isn't running, and the Lender gets Chrome's "This site can't be reached" page.

A cache seems to be the fix: keep a copy of the screens, so the app opens either way. But cache the wrong things and it goes wrong. Cache the API's answers, and the app could show what Meera owed last week. Cache the pages too eagerly, and after an update the Lender keeps getting the old app. Even once the app opens without a server, it can't start that server itself: a web page can't run programs on the laptop.

The idea

Cache the app, never the figures. A service worker is a script the browser keeps installed for a site. It sits between the page and the network and can answer requests from its own cache. This one keeps the built screens, and fetches every page from the server first whenever the server answers. It never caches /api.

A gate in front of the app. StartGate pings the backend before drawing anything. If it doesn't answer, it says so (on Windows, with a Start button: ADR 0008). It keeps checking, and reloads the app the moment the backend answers.

A banner for updates. UpdateBanner asks the backend whether a newer release is out, and offers it with its notes: Install now, or Later.

The flow

Notice that the gate runs after the cached app has loaded. The service worker's job is only to get the app's own code onto the screen. Whether there's a server to talk to is the gate's question, asked through the same typed client as everything else.

The code

1. What the service worker keeps

  1. vite-plugin-pwa writes the service worker (sw.js, made with Google's Workbox library) when you npm run build. autoUpdate: a new service worker takes over as soon as it's installed, with no "reload to update" prompt.
  2. The precache: every built file that matches, fetched and stored when the service worker installs. That's the whole app, so it can open offline.
  3. Except Tesseract's 10 MB (lesson 4): they'd slow every install, for a feature used now and then.
  4. By default a Workbox app answers every page from the precached index.html, without asking the server at all. That would keep the Lender on the old app after an update until a second start. null turns that off; the rule below fetches pages instead.
  1. A navigation is the browser loading a page (a URL typed, a reload, the icon), not a fetch from the page's code. /api requests are never navigations, and would be refused here anyway.
  2. NetworkFirst: ask the server first and keep the answer in the pages cache; use the cache only if the server fails or takes more than 5 seconds.
  3. Offline, and asked for a page that was never cached: answer with the precached index.html anyway. The app finds its page from the URL (lesson 1), so any URL works offline.
  4. The version in the top bar ("v3.4.1") is written into the build from package.json. src/version.ts names it APP_VERSION.

2. The gate

  1. Any answer below 500 means a backend is there. A 5xx means something answered for it: Vite's dev server answers 502 when the backend behind its proxy is down (checked: the script got 502 from /api/payment-methods with no backend on port 8000), and so did nginx in Docker before ADR 0013.
  2. With no server at all, fetch throws: stopped.
  3. Once it answers, reload the whole page rather than just drawing the app. The server may now be a newer version than the cached screens, and a reload is a navigation: NetworkFirst fetches the new app.

The rest of StartGate is the screen itself. On Windows (navigator.userAgent includes "Windows") it shows Start Mortgage Management, which opens mortgage-management://start: a link Setup registered with Windows that runs the app's launcher (ADR 0008; chapter 014, lesson 5). Elsewhere there's no such link, so it says "The app isn't running. Start its server: this page loads the app as soon as it is running." After five minutes of Starting… it says to use the Desktop shortcut to see what went wrong.

3. The update banner

  1. The version the Lender last put off with Later, kept in this browser's localStorage under mortgage-management.update-put-off.
  2. While installing (after Install now opened mortgage-management://update and Setup began), ask every 3 seconds which version runs. Any version other than the one running before means the update worked: reload into it.
  3. The app went away and came back as the same version: Setup put the old one back, so the update failed. "Update failed; still on 3.4.1. The Setup window says why."
  4. Nothing to offer, or this version (or a newer one) was put off.

What's "available" is the backend's answer from GET /api/update, which compares the running version with the latest release (chapter 015). The banner only shows it, renders its release notes from Markdown (ReleaseNotes, line 46), and watches the install.

Run-through: build it, install it, stop the server

The service worker exists only in a built app (npm run dev has none). Build the screens, and serve a fresh book with them on serve.py's own port:

# from frontend/
npm run build

# from backend/, a new book in a new folder
export PWA=$(mktemp -d)
uv run python ../docs/sample-book/book.py "$PWA"
uv run python ../docs/sample-book/serve.py "$PWA"      # http://127.0.0.1:8765

Open 127.0.0.1:8765 in Chrome. The top bar says v3.4.1. Install it with Chrome's install icon at the right of the address bar (or the Install item in Chrome's ⋮ menu; its place varies between Chrome versions). It opens in its own window, named "Mortgage Management".

Nuances

(a) No figure is ever stale

Predict: the Lender opens Meera's chain in the installed app on Monday. On Tuesday they open it with the server stopped. Do they see Monday's ₹83,333?

No: they see "The app isn't running…". The page and its code are cached, but /api/mortgages/2 never is (neither cache has any /api/ entry), and StartGate draws nothing until the backend answers. The app is either live or not shown. Every figure on screen came from the backend just now. (Chapter 011's in-memory cache lasts only while the page is open; a reload empties it.)

(b) The first start after an update runs the new app

The cached screens are an old version once the Lender updates. With NetworkFirst and navigateFallback: null, the first page load after the update asks the server, which now serves the new index.html; it names new hashed assets/ files, which the browser fetches. Meanwhile the new sw.js installs and, with autoUpdate, takes over and replaces the precache. cleanupOutdatedCaches deletes the old one. The 5-second timeout only matters when the server is slow to answer: then the cached app opens, and StartGate takes it from there.

(c) The server's cache headers must agree

The service worker isn't the only cache. The browser's own HTTP cache follows the server's Cache-Control headers, and sw.js itself is fetched through it. If sw.js or index.html were kept for an hour, the Lender could stay on the old app for that hour, whatever the service worker says. The backend sends:

These come from platform/screens.py. The service worker's caching in vite.config.ts and the server's headers in screens.py are separate rules that both affect updates. Change either one, then check the installed app's behavior. Chapter 014, lesson 2 explains how one backend now serves screens in both modes.

(d) Later is per device

Later is remembered in the browser's localStorage, not on the backend. The Lender's laptop and phone each decide for themselves, and a private window forgets it once closed. And Later only means "not this version": a newer release than the one put off shows the banner again (line 159; the test at line 56).

(e) Reloading for the version that runs

Predict: the banner offers 1.6.0. While the Lender is installing, 1.6.1 is released, and Setup installs the newest. If line 137 were data.running === available.version ("reload once 1.6.0 runs"), what would the Lender see?

"Updating to version 1.6.0…" forever, then, after 20 minutes, "The update hasn't finished…": 1.6.1 is never 1.6.0. Comparing with the version that ran before catches any successful update. This is the check-yourself exercise: make the change, and exactly one test fails.

Quiz

The server is stopped. Which cache does a reload of the installed app use for the page?

Pages are NetworkFirst: the server is asked first, and when that fails the pages cache answers. For a page never visited, handlerDidError falls back to the precached /index.html. The precache alone answers only the app's files.

Why does StartGate count a 502 from /api/payment-methods as stopped?

A 5xx means something answered for the backend: Vite's dev server answers 502 when nothing listens on 8000, as nginx did before ADR 0013. Pinned by StartGate.test.tsx's "a 502 from a proxy in front of a stopped backend counts as stopped".

The Lender presses Later on 1.6.0. What does the app remember, and where?

writePutOff(available.version) stores the version under mortgage-management.update-put-off. The banner hides while the offered version isn't newer than it. Nothing is sent to the backend.
