Reading through one cache

No page calls the client directly to read something. It asks the cache, by key, and the cache decides whether to ask the backend. This lesson shows the keys, where the cache is made, and when an answer is shown from the cache and when it is asked for again.

By the end you can write a read in requests.ts with the right key, and say when it will be asked for again.

The problem

Go from Meera's Customer page to her chain and back. If each page fetched its data in a useEffect and kept it in its own state, every visit would start with a blank page and a spinner, and the same answer would be fetched over and over. Keep answers forever instead, and after a Payment her page still shows the old Outstanding.

There's a second, subtler problem: finding what to refresh. A Payment to the chain changes the chain, Meera's Customer History, every list, the Dashboard. If each screen kept its data its own way, the code that saves a Payment would need to know about every one of them.

The idea

One cache for the whole app, with answers filed under keys. The app uses TanStack Query (often called React Query). It keeps every answer from the backend in one QueryClient, filed under a query key: an array such as ['mortgage', 2]. A page says "I need the answer for this key, and here's how to get it", and TanStack Query shows what it has, asks the backend if what it has is stale, and re-renders the page when the answer arrives.

Keys are paths. Keys are built like folder paths, so a prefix names a whole branch: ['customer'] matches ['customer', 1], ['customer', 1, 'history'] and ['customer', 'search', 'Meera']. Lesson 5 makes whole branches stale with one prefix.

Shown at once, asked again behind the scenes. By default, TanStack Query treats every answer as stale the moment it arrives (its staleTime is 0). A page that needs a cached key shows the cached answer immediately and asks the backend again, then swaps in the new answer. Things that can't change while the app runs say so with staleTime: Infinity, and are asked for once.

The flow

Notice that the page never decides any of this. It names a key and a function, and the cache's rules do the rest.

The code

1. One client, one cache, given to every page

createServerState() (lesson 1) runs once, when the app starts, and makes the typed client and the QueryClient. Reload the browser tab and you get a fresh, empty cache.

Two React contexts: a way to hand a value to every component below, without passing it through each one's props. QueryClientProvider is TanStack Query's own; ClientContext is the app's, for the typed client.

Every page and hook gets both from here. Tests wrap a page in the same provider with a fake fetch (chapter 013, lesson 4), which is why nothing else may make its own client.

2. The keys

as const tells TypeScript to type ['mortgage', id] as a fixed, read-only pair (readonly ['mortgage', number]) rather than a loose (string | number)[]. The all… keys are the prefixes; the functions make one entry under them. Every key the app uses starts with one of these.

3. A read, with its key

  1. select picks what the page gets out of the cached answer. The cache keeps the whole first page of Dormant Mortgages; the menu only gets the number, total.
  2. queryOptions is TanStack Query's helper that ties a key to its function's answer type, so useQuery(mortgageQuery(client, 2)).data is typed Mortgage. It returns the plain options object; the page passes it to useQuery.
  3. The key comes from keys, never typed out by hand in a page. One spelling, one place.

A page then reads it in one line, as MortgagePage does (line 40): const loaded = useQuery(mortgageQuery(client, id)). loaded.data is the Mortgage, or undefined until it arrives; loaded.error is the BackendError from lesson 1, if any.

4. Read once

Each settings group (default-terms, gold-rates, call-list, cash-limit, messages, placeholders) gets this. paymentMethodsQuery (line 681) and updateStatusQuery (line 691) set staleTime: Infinity too: the payment methods are fixed while the app runs, and the backend asks GitHub about updates at most once a day anyway.

Nuances

(a) A key is a path, on purpose

Predict: the Lender saves a Customer, and the save makes the prefix ['customer'] stale. Which of these cached answers become stale: ['customer', 1]; ['customer', 1, 'history']; ['customer', 'search', 'Meera']; ['customer', 'referrer', 1]; ['mortgage', 2]?

The first four, not the Mortgage. TanStack Query matches a key by its start, element by element. That's why keys.search, keys.numberOwner and keys.referrer are filed under 'customer' even though they aren't one Customer: a saved Customer can change who matches a search, who owns a Primary Number, and whom a Standalone Referrer has referred. (['mortgage', 2] is made stale by the same save for a different reason: STALE_AFTER.customer names allMortgages too, because a Mortgage shows its Customer's name. Lesson 5.)

(b) A Receipt sits under its Payment

  1. ['payment', 23, 'receipt']: anything that makes Payments stale reaches their Receipts too. New message settings reword every Receipt, and STALE_AFTER.messageSettings only has to name allPayments. (... is JavaScript's spread: it copies the elements of keys.payment(paymentId) into the new array.)
  2. A query function gets a context object; client in it is the QueryClient (renamed cache here, to tell it apart from the typed client). It looks up the Payment already in the cache, without asking. A Voided Payment has no Receipt, so asking would only earn a refusal. Lesson 5 shows the save that makes this work. projectionQuery (line 430) does the same for a closed Mortgage, which has no Projection.

(c) Read once, then known from what saving returns

If the settings groups are never asked again, how does the page see a change? The save route answers with what it stored, and the page puts that answer straight into the cache. In SettingsPage.tsx, saving the message settings ends with queryClient.setQueryData(settings.messages(client).queryKey, messages) (line 415). setQueryData writes an answer under a key as if the backend had just sent it. The default Terms, Gold Rates, Call List thresholds and Cash Limit forms do the same.

(d) A picker must never leave a Mortgage out

  1. Filed under the Mortgages list, so anything that makes lists stale reaches it. The filters object is part of the key, so each Customer, status and date has its own entry. TanStack Query compares keys by value, not by object identity, so a new { customerId: 1, … } with the same contents finds the same entry.
  2. The Payment form passes its date: the backend works out each Mortgage's Outstanding on that date. The frontend never does; it has no Ledger code.
  3. Lists come 20 to a page (chapter 010, lesson 4). A Customer with 21 Active Mortgages would lose one from the Payment form's table. paged: false asks for all of them on one page.

On the Payment form, this is GET /api/mortgages?page=1&customer_id=1&status=active&as_of=2026-10-19&paged=false. That as_of is why the form's date matters: leave it at your browser's real today and the backend refuses the date as in the future.

Quiz

You add a read of a Customer's Call Notes across all their Mortgages. Which key lets a saved Customer make it stale with no other change?

Under ['customer', id], so STALE_AFTER.customer's allCustomers prefix reaches it. The first sits under ['call-notes'], which a Call Note makes stale but a saved Customer doesn't. The second is under nothing at all: you'd have to add it to every STALE_AFTER entry by hand.

You open Meera's chain, go to the Dashboard, then come back to the chain. What happens?

The cached answer is shown immediately, and, being stale (staleTime 0), asked again in the background. "Loading…" is only for a key that was never answered. Asking nothing is for staleTime: Infinity, which a Mortgage doesn't have.

Why does everyMortgageQuery pass paged: false?

The Payment form and other pickers must show every one of the Customer's Mortgages, or the Lender can't choose the one that's missing. Lists come 20 to a page, so a Customer with 21 would lose one. as_of works with or without paging.
