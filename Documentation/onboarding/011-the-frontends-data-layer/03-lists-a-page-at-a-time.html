Chapter 011 · Lesson 3

Lists a page at a time

The Customers, Mortgages, Payments, Notices, Call List and Dormant lists all work the same way: sorted by the backend, 20 rows a page, the sort kept in the URL. This lesson shows the one hook behind all six, and the small rules that keep a list from showing the wrong page.

By the end you can add a sortable, paged list.

The problem

Chapter 010, lesson 4 showed the backend's half: query_page sorts across every row in SQL and hands back one page of 20, with total. The screen can't sort what it has, because it only has 20 rows. So clicking a column heading has to become a new request.

Around that request sit a handful of things that are easy to get wrong:

  • The Lender sorts the Payments by amount, opens one, and presses Back. Is the list still sorted?
  • The Lender is on page 2 and types a filter that matches 11 Payments. Page 2 of 11 rows is empty.
  • The Lender approves the last Notice on page 2. Page 2 is now empty, and the pager would say "Showing 21–20 of 20".
  • The Lender clicks a heading, then clicks it again before the first answer arrives. If the first answer lands last, the screen shows the wrong order under the right arrow.

Six lists, each solving these on its own, would solve them six slightly different ways.

The idea

A list is a key and a loader. requests.ts declares each list once, in lists: which list it is (with its filters), and how to ask for page n in a given order.

One hook does the rest. useListPage keeps the page number, reads the sort from the URL, asks the cache for that page in that order, steps back when a page comes back empty, and hands the page a pager. Changing the sort or a filter starts again at page 1. The sort and the page are part of the query key, so each page in each order is its own cache entry.

The flow

The code

1. A sort, and the URL

  1. Clicking the column already sorted reverses it.
  2. A new column starts ascending, unless it says otherwise. Amounts and dates set firstDescending (largest or newest first), as the Payments list's Date and Amount headings do.
  3. A URL can say anything; the Lender might have an old bookmark. Only a column in the list's own columns (lesson 1's CUSTOMER_SORTS) is believed. Anything else means "the list's own order", null.
  1. useMemo remembers a value between renders and works it out again only when something in its list ([raw, columns]) changes. So sort stays the same object until the URL parameter changes. That's why the hook's comment asks for columns to be a constant: a new array every render would make a new sort every render.
  2. Clicking writes the new sort into the URL. useUrlFilters (React Router's useSearchParams) replaces the current history entry rather than adding one, so Back leaves the list instead of undoing a click.
  3. Whatever the list wants done on every sort change; useListPage passes "go to page 1".

2. A list, declared once

  1. The key names the list and its filters, nothing else. useListPage adds the prefix and the page and sort.
  2. satisfies checks the object against ListRequest<CustomerSort, …> without widening its type: sort must be a Customers sort, and the answer keeps its exact generated type (Page_CustomerRow_), not unknown.

Line 234 leaves descending out unless it's true, and sortQuery(null) sends no sort at all, so the backend uses the list's own default order. The Mortgages, Payments, Notices, Call List and Dormant lists below it follow the same pattern.

3. The hook

  1. hashKey is TanStack Query's own way of turning a key into a string, by value. Two filter objects with the same contents hash the same.
  2. The page number is remembered together with the filters it was chosen for. When the filters change, the stored page belongs to other filters, so the page is 1, with no effect or extra render needed.
  3. The full key: ['list', 'customers', { query: '', hasActiveMortgage: false }, { page: 1, sort: { column: 'name', descending: true } }]. Under keys.lists, so every Ledger change makes every list stale (lesson 5).
  4. keepPreviousData: while the new page or order loads, keep showing the last one (marked isPlaceholderData) instead of blanking the table.
  5. An empty page past page 1 steps back a page. React allows a component to set its own state while rendering, as long as it's guarded so it doesn't loop: here, only when page is still the emptied one.

A page using it (CustomersPage, line 31) writes useListPage(CUSTOMER_SORTS, lists.customers({ query: debouncedQuery, hasActiveMortgage: activeOnly })), then renders listed.items, a <SortHeading sorting={sorting} column="name"> per column, and {pager}.

Nuances

(a) A quick second click

Predict: on the Customers list, click Address, then click it again 130 ms later. The first answer (ascending) is slow and arrives 1.5 seconds later, after the second. Which order is on screen at the end?

WhenRequest
41 msGET /api/customers?page=1&q=&sort=address (held back 1.5 s)
173 msGET /api/customers?page=1&q=&sort=address&descending=true

At the end: URL ?sort=-address, rows Imran Qureshi, Farida Khan, Lakshmi Iyer, Kavita Joshi, Arjun Patel, Sunita Rao, Meera Sharma: descending, the second click's order. (From scripts/network.mjs, section L3, which held the first answer back.)

Nothing in useListPage cancels the first request or checks which answer is newer. It doesn't need to: each order has its own key. The slow answer is filed under the ascending key, which the page is no longer looking at, so it never reaches the screen. If the Lender clicks back to ascending, it's there in the cache.

(b) A page that comes back empty steps back

Predict: you're on page 2 of the Payments. Its rows stop being listed (on the Notices list, approving the last Notice on page 2 does exactly this). The page is asked for again and comes back with no items, and total is now 20. What does the Lender see?

Page 1. The script made page 2 answer {"items": [], "total": 20, "page": 2, "page_size": 20} and let the window regain focus, which asks for whatever is on screen again:

RequestWhy
GET /api/payments?page=2&q=asked again on focus: comes back empty
GET /api/payments?page=1&q=emptied, so setPage(1)

The pager then said "Showing 1–20 of 33" (the real page 1). Without line 53 it would have said "Showing 21–20 of 20". (From scripts/network.mjs, section L3; the empty answer stood in for the backend.) No test pins this rule today; if you change useListPage, check it by hand.

(c) Back and a reload keep the sort; the page number doesn't

The sort is in the URL, so the browser keeps it: Back to the Payments list from a Payment, or a reload, shows the same order. The page number isn't in the URL; it's React state, and starts at 1 whenever the list's page is drawn afresh. The filters vary by page: the Customers list keeps "Only Customers with an Active Mortgage" in the URL (?active=true), but not its search text.

(d) Adding a sortable column

Say the backend's Customers list gains a created sort. After npm run gen:types, CustomerSort includes "created", and CUSTOMER_SORTS in api.ts stops compiling until you add created: true (lesson 1, nuance f). Then add a <SortHeading sorting={sorting} column="created" firstDescending> to the table in CustomersPage.tsx. Nothing in requests.ts or useListPage changes.

Quiz

The Payments list is sorted by Amount (largest first). The Lender clicks Amount once more. What is the URL's sort now?

nextSort reverses the column that's already sorted, so -amount becomes amount, smallest first. firstDescending only decides the first click on a column. There's no click that clears the sort.

On page 3 of the Mortgages, the Lender ticks "owing" (a filter). Which page is asked for?

The filter is part of list.key. The stored page belongs to the old listKey, so page is 1 in the same render that sees the new filter, and only page 1 is asked for. Stepping back from an empty page is a different rule, for when the same list's page empties.

A bookmark has /customers?sort=-nickname, a column the list doesn't have. What happens?

sortFromParam only believes a column in CUSTOMER_SORTS, so it returns null and sortQuery(null) sends no sort. Nothing reaches the backend to refuse. Compiling is about code, not about a URL someone typed.
