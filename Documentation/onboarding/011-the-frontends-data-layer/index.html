Chapter 011

The frontend's data layer

The problem this chapter solves

The Lender only ever sees the screens. Every figure on them comes from the backend: the frontend works out no money of its own. So the frontend's whole job, as far as data goes, is asking the backend the right questions and showing the answers. There are 71 paths to ask, and the answers have to stay right while the Lender works.

That's harder than it sounds. Meera's chain appears on her Customer page, on its own Mortgage page, in the Mortgages list and on the Payment form. Ask the backend for it separately on each screen, and the app feels slow. Keep one copy and never ask again, and the screen still says she owes ₹83,333 after she has paid. A Preview asked for on every keystroke runs the real change four times for "8000". A request written by hand as fetch('/api/mortgage/' + id) compiles fine and fails only when the Lender opens the page. A refusal from the backend has to reach the Lender as one sentence they can act on, not as [object Object].

This chapter opens the small layer that handles all of that: one typed client generated from the backend's own schema, one cache that every screen reads through, one hook for a paged list, one for a Preview, and one place that says what each kind of change makes stale.

What you'll be able to do

  • Say how a backend Pydantic model becomes a TypeScript type, what to run when you change one, and what happens to a refusal and to a failure.
  • Write a read in requests.ts with the right query key, and say when it is asked for again.
  • Add a sortable, paged list whose sort lives in the URL.
  • Wire a form to its Preview, and say exactly when its Save button is enabled.
  • Save a change, and declare in serverState.ts what it makes stale.

Before you start

You need these ideas from earlier chapters:

  • Running the frontend. Chapter 002, lesson 5 showed the "serve the sample book on port 8000, then npm run dev" trick. This chapter uses it throughout.
  • One Payment, end to end. Chapter 003 followed a Payment from the form through its Preview to the save and the refresh. It showed you usePreview, useProposedChange and ledgerChanged from the outside. This chapter opens them.
  • Previews, from the backend. Chapter 006, lesson 4: a Preview runs the real change and rolls it back (trap #5), so it's refused exactly when saving would be. Here you see the other end: how the screen asks for one.
  • The Cash Limit. Chapter 007, lesson 4: the backend's Preview says which sums a change writes in cash; the screen warns. Lesson 4 here shows where the warning sits in Save.
  • Lists a page at a time, on the backend. Chapter 010, lesson 4: query_page sorts and pages in SQL, 20 rows a page, with total on every page. Lesson 3 is the screen's half.

Keep this open while you read. Build the sample book fresh into a new, empty folder (earlier chapters saved changes on the old one), then serve it on port 8000 and start the frontend:

# terminal 1, from backend/
export BOOK=$(mktemp -d)
uv run python ../docs/sample-book/book.py "$BOOK"
uv run python ../docs/sample-book/serve.py "$BOOK" 8000

# terminal 2, from frontend/
npm run dev

Open localhost:5173, open your browser's developer tools, and on the Network tab type /api/ in the filter box. Every lesson has you watch that tab. Lessons 1–4 only read and Preview. Lesson 5 saves one Payment and approves one Notice on that scratch book. It's a scratch book, so that's fine, but rebuild it before the next chapter.

Two things you'll see in development only. First, /api/payment-methods appears three times on a fresh load. Two are StartGate's check that the backend answers (chapter 012, lesson 6), made twice because React's StrictMode (in main.tsx) runs every effect twice in development to flush out bugs. The third is the query for the payment methods themselves. The built app makes the check once. Second, a form's date is your browser's today, not the served book's 19 Oct 2026. On the Payment form, set the date to 19 Oct 2026 first, or the backend refuses the list of Mortgages with "The date cannot be in the future".

The map

Notice that no page talks to the backend directly. A page names what it wants from requests.ts and hands it to a hook. The hooks talk to the cache, and only the cache's query functions reach the client. The left-hand arrows run at build time, not in the browser: they turn the backend's models into the types every request is checked against.
