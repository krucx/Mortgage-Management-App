Chapter 008 · Lesson 2

Referrers, and a Referrer who borrows

When the Lender types who introduced a new Customer, the app has to decide: is this someone it already knows, or a new person? And when a person who only ever introduced others starts borrowing, how do they become a Customer without leaving a second record behind?

By the end you can resolve any Referrer choice to the row it writes, and explain promotion.

The problem

A Referrer is whoever introduced a Customer to the Lender. Lenders like this kind of business care a lot about it: a good Referrer brings good Customers, and a Customer who stops paying is often reached through the person who brought them. A Referrer can be an existing Customer (Meera introduced Arjun) or someone who has never borrowed (Ravi Verma introduced Meera).

On the Customer form, the Lender picks a Referrer from a search, or types a new one: name, address, phone. Three things can go wrong:

  • The Lender types Ravi as "new" again for a second Customer, not noticing he's already there. Now there are two Ravis.
  • Ravi starts borrowing himself. Added as a Customer, he'd be a third Ravi, and Meera would still be "referred by" the old one.
  • Someone ends up as their own Referrer, by picking themselves or by typing their own number.

The idea

A Referrer choice is one of three kinds: an existing Customer, an existing Standalone Referrer, or a "new" one. A "new" one is looked up by its number first (lesson 1's Primary Number): if the number is known, the choice is linked to that person instead of creating anyone. When a new Customer is added on a Standalone Referrer's number, that Referrer is promoted: the Customers they referred are moved over to the new Customer, and the Standalone Referrer row is deleted. A person is never their own Referrer.

The flow

Notice that only one path, the bottom right, writes a new row. Every other "new" Referrer is really someone the book already has.

The code

1. The three kinds of choice: ReferrerChoice

This is a discriminated union: Pydantic reads the kind field first and then checks the body against just that one model. A body of {"kind": "new", …} needs a name, address and phone; {"kind": "customer", "id": 1} needs only an id. Any other kind is a 422 before your code runs.

2. One choice → two columns: _link_to and _referrer_columns

Every path builds both columns here, so a Customer can never end up with both set. The database itself doesn't forbid both; this function is why it never happens.

  1. match … case is Python's structural pattern matching (3.10+). case ExistingCustomerReferrer(id=referrer_id): means "if choice is that class, bind its id to referrer_id".
  2. The "new" Referrer's name and address are ignored if the number is known: the existing person keeps theirs.
  3. .returning(…) makes the INSERT hand back the new row's id; .scalar_one() takes that single value.

3. Promotion: _promote_referrer

Lesson 1's _checked set promoted to a Standalone Referrer's id when a new Customer takes their number. create_customer acts on it right after inserting the Customer:

  1. Everyone the Referrer introduced now points at the new Customer instead.
  2. Then the Standalone Referrer row goes. The order matters: the foreign key on referred_by_standalone_referrer_id would refuse the delete while anyone still pointed at it.

All of this happens in the one transaction the route opened, so if anything after it fails, the promotion is undone too.

4. Never their own Referrer: _is_themselves

_checked calls it at line 185 and refuses with 422 "A Customer cannot be their own Referrer". The third case has two halves because of edits: if Meera changes her contact number 1 and, in the same edit, types a "new" Referrer with her old number, owner_of still finds her (the row isn't updated yet).

Nuances

(a) A "new" Referrer on a Customer's number

Predict: a new Customer, Neha, is typed with a "new" Referrer "M. Sharma", phone 9810012345 (Meera's contact number 1). Which column is set, and does a Standalone Referrer row appear?

referred_by_customer_id = 1, and no row is written. owner_of finds Customer Meera, so Neha is linked to her. Typing a new Referrer "Salim Ali" on an unknown number 9855566677 is the only case that inserts: he becomes Standalone Referrer 2 (from scripts/run_throughs.py, section L2, on a separate copy).

(c) Promotion only on create

Predict: instead of adding Ravi as a new Customer, the Lender edits Arjun and changes his contact number 1 to Ravi's 9811122233. Is Ravi promoted into Arjun?

No: 409, "Contact number 1 9811122233 already belongs to Referrer Ravi Verma". Line 181 promotes only when customer_id is None, a new Customer. Promoting into an existing Customer would mean merging two records and choosing whose name and address win; the code doesn't attempt it. (test_primary_number.py::test_editing_contact_number_1_to_a_standalone_referrers_number_is_rejected.)

(d) What History says about a promotion

Predict: after step 2, Meera's referred_by_* columns changed. What does her History show for it?

Nothing. On 19 Oct, History has rows only for the two new Customers: Deepa's created rows (including referrer → "Ravi Verma") and Ravi's. _promote_referrer records nothing on the people it moves. That's consistent with how History records a Referrer: by name (lesson 3), and Meera's Referrer was "Ravi Verma" before and after. The person didn't change; only which table holds him did.

From scripts/run_throughs.py (section L2): audit_entry rows for Customers 1, 8 and 9 on 19 Oct.

(e) There's no route to edit or delete a Standalone Referrer

A Standalone Referrer can be read (GET /api/referrers/{id}: name, address, phone, and whom they referred), but no route changes or deletes one. They leave the book only by being promoted. To fix a Referrer's name today, the Lender would have to make them a Customer.

Trap #19 again: it's Referrer, not "reference". The columns say referred_by_…, the API says referrer, and the glossary lists "Reference" under Avoid. Write it the same way in code and issues (trap #19).

Quiz

A new Customer is typed with a "new" Referrer whose phone is Arjun's contact number 1. What is written?

_referrer_columns asks owner_of first, finds Customer Arjun (2), and links to him. Only an unknown number inserts a row. A known number is not a clash for a Referrer; it's the point.

When Ravi is promoted, why are his referrals moved before his row is deleted?

referred_by_standalone_referrer_id is a foreign key to standalone_referrer.id, and the app turns foreign keys on in SQLite. No History is written for the move, and the Customer id is known already: it was inserted at line 205.

Which of these can set both referrer columns on one Customer?

_link_to sets at most one, and every case of _referrer_columns returns through it. _promote_referrer also clears one as it sets the other.
