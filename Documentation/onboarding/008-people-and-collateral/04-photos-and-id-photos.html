Chapter 008 · Lesson 4

Photos and ID Photos

A photo is a file on disk, and the row that names it is in the database. A database transaction can roll back; a file on disk can't. This lesson shows the one function that makes a photo change all-or-nothing anyway.

By the end you can add a change that writes a file, keeping the file and the database consistent.

The problem

The app keeps three kinds of photo: a picture of each Customer, the Customer's ID Photos (their masked Aadhaar card and their PAN card), and pictures of each Mortgage's jewellery. They're stored as JPEG files in a photos folder beside the database, and the database stores only each file's name. Backups zip up the database and the folder together (chapter 015).

Replacing Meera's Aadhaar photo means three steps: write the new file, point her row at it, delete the old file. Now imagine any step going wrong:

If it fails……in this order: write file, update row, delete old
after writing the new file, the update is refused (no such Customer)An orphan file nobody points at, kept forever and copied into every Backup
after deleting the old file, the transaction rolls backThe row still names the old file, which is gone: a broken image

The database can undo its half. It can't undo a file.

The idea

Do the file work on either side of the transaction, never inside it. Write the new file before the transaction; if the transaction fails for any reason, delete that new file. Delete the old file only after the transaction has committed. Either way, the folder ends up matching the database. photo_change in platform/photos.py does this for every photo change in the app, Customer and Mortgage alike.

The flow

Notice there's no path where the old file is gone but the row still names it, or where a new file is kept that no row names.

The code

1. Saving a file: _save_photo

  1. A phone stores a portrait photo as a landscape image plus an EXIF tag (EXIF is metadata inside the JPEG) saying "rotate me". Browsers don't all honour it. exif_transpose rotates the pixels for real, so the photo looks right everywhere. .convert("RGB") lets a PNG with transparency be saved as JPEG.
  2. thumbnail shrinks the image, keeping its shape, so its longer side is at most 1,600 px. It never enlarges. Smaller files keep Backups small.
  3. The name is the owner, their id and a random UUID, as 32 hex characters. A replacement always gets a new name, so the old and new files exist side by side until the change is decided.

2. The change: photo_change

  1. The new file, if there is one, is written first. A file that isn't an image is refused here with 422, before any transaction opens.
  2. @contextmanager turns this generator into something used with with. Everything inside the caller's with photo_change(…) as change: block runs at the yield, inside engine.begin(). The caller gets the connection, the new file's name, and remove_when_saved, which just appends to replaced.
  3. If the caller's block raises (a 404, a 409, a bug), engine.begin() rolls back and the exception arrives here. The new file is deleted and the exception goes on to FastAPI. BaseException also catches the rare cancellations that aren't Exceptions.
  4. Only after engine.begin() has committed are the replaced files deleted. Asking for a file to be removed doesn't remove it; it's a promise to remove it if the change is saved.

3. Using it: an ID Photo

The change function knows nothing about files: it's handed a file name, and hands back the one it replaced. That split is what to copy. replace_photo (line 239) is the same for the Customer's own photo, and delete_id_photo (line 390) calls replace_id_photo with None and no NewPhoto. delete_customer (line 404) passes every file remove_customer returns (lesson 3) to remove_when_saved. Mortgage photos use the same pattern from lending/changes.py: add_photo (line 542) and remove_photo (line 556), called by post_photo and delete_photo (lines 1064–1090).

4. Serving a file: read_photo

The regex at line 25 accepts only names _save_photo could have made: lowercase letters, a dash, digits, a dash, 32 hex characters, .jpg. So /api/photos/mortgage.db can't hand out the database, and no ../ can climb out of the folder.

Nuances

(a) A refused change leaves no file

Predict: the same upload, to /api/customers/99/id-photos/pan. There's no Customer 99. What answers, and is a customer-99-… file left in the folder?

404 "Customer not found", and no file. _save_photo did write customer-99-….jpg at step ①. Then replace_id_photo's load_customer raised, the transaction rolled back, and step ③ deleted it. The folder held 5 files before and after (from scripts/run_throughs.py, section L4; test_photo_lifecycle.py::test_a_refused_change_leaves_no_new_file).

(c) Removing an ID Photo, and removing it again

DELETE /api/customers/1/id-photos/pan clears pan_photo, records photo_removed with note "PAN card", and, after the commit, deletes the file. Sending it a second time answers 200 again but writes nothing: line 271 returns early when there's nothing to remove, so History doesn't fill with removals of nothing.

(d) Where ID Photos are shown

Predict: which of GET /api/customers (the list) and GET /api/customers/1 (her page) include aadhaar_photo_url?

Only her page. A list row (CustomerRow) has photo_url, the Customer's own picture, but no ID Photos. They're added only in Customer (line 180), which load_customer builds for one Customer. The glossary says ID Photos are "shown only on their page and form"; test_customer_ids.py::test_id_photos_are_never_in_the_customers_list holds the code to it. A list of everyone's ID cards on one screen is exactly what shouldn't exist.

(e) History never names a file

Photo changes write photo_added or photo_removed, with the card's name ("Aadhaar card", "PAN card") for ID Photos and nothing for the Customer's own photo or a Mortgage's. A file name would be meaningless in History, and would point at a file that may since have been deleted.

(f) A deleted Customer takes their files

Deleting a Customer with a photo and an Aadhaar photo removed both customer-8-… files after the commit (from scripts/run_throughs.py, section L4; test_customer_ids.py::test_a_deleted_customer_takes_their_id_photos_with_them). Had the delete been refused, they'd still be there: remove_when_saved only promises.

The Customer form saves the details first and uploads the photos afterwards, one request each, so a photo that fails to upload doesn't lose the details. Chapter 012, lesson 4 covers the pages.

Quiz

When is the old Aadhaar file deleted, when Meera's is replaced?

replace_id_photo only returns the old name; remove_when_saved appends it to a list; photo_change deletes it after engine.begin() has committed (lines 105–106). Deleting it any earlier could leave the row naming a missing file if the change rolled back.

You add a "signature photo" change for Customers. What should your change function do with files?

Keep file work out of the change function. The route wraps it in photo_change, which writes the new file before and removes the old after, and passes the old name to remove_when_saved. That's exactly how replace_photo and replace_id_photo work.

Why can't GET /api/photos/mortgage.db download the database?

The database is beside the folder, not in it, but a name like ..%2Fmortgage.db could reach it if names weren't checked. read_photo refuses any name _save_photo couldn't have made, so both answer 404. FileResponse itself sends any file it's given.
