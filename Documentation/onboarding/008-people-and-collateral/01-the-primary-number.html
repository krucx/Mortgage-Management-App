Chapter 008 · Lesson 1

Who a person is: the Primary Number

How does the app know that the Meera Sharma typed in today is the Meera Sharma it already has? Not by her name. This lesson shows what it uses instead, and the one place the rule is enforced in code rather than by the database.

By the end you can say why a phone number, not a name, identifies a person, and where that rule is enforced.

The problem

The Lender's book has two kinds of people. A Customer has borrowed. A Standalone Referrer has only introduced someone: Ravi Verma brought Meera Sharma in, but has never borrowed himself. Both kinds turn up again and again: on a new Customer's form, in a search, on the phone.

The obvious way to tell people apart is by name. It fails at once. India has many Meera Sharmas. Names get typed with a middle initial one day and without it the next. And the Lender knows people by their phone, not by a spelling.

The next obvious way is "any phone number they have". That fails too. Meera's second number, 9810099999, is her family's phone. Sunita Rao lives in the same house and gives the same family phone as her second number. If every number identified a person, Meera and Sunita would be one person.

The idea

Each person has exactly one number that identifies them: their Primary Number. For a Customer it's contact number 1; for a Standalone Referrer it's their only phone. No two people, of either kind, may share a Primary Number. Contact number 2 identifies nobody, so sharing it only shows a warning (ADR 0005).

Think of the Primary Number as a seat number in a theatre with two seating areas. Each area numbers its own seats so no two seats in it clash, but someone also has to check that a ticket for seat 12 in one area isn't sold while seat 12 in the other is taken. The database checks each area. The code checks across them.

The flow

Notice where contact number 2 goes: nowhere near owner_of. It only feeds a warning list on the Customer's page.

The code

1. The tables

  1. unique=True makes the database refuse a second row with the same value in that table. Each table is unique on its own. Nothing in the schema stops a customer.phone_1 from equalling a standalone_referrer.phone.
  2. name isn't unique. Two Meera Sharmas are allowed, as long as their numbers differ.
  3. phone_2 has an index (so it can be searched quickly) but isn't unique.

2. One spelling for every number: normalise_phone

  1. \D is a regular expression for "any character that isn't a digit"; re.sub deletes them all. Spaces, dashes, brackets and the + go.
  2. Indian mobiles are 10 digits. Typed with the country code they're 12 (91…); typed with a trunk prefix they're 11 (0…).
  3. Annotated[str, AfterValidator(…)] is a Pydantic idiom: a field declared as Phone is a string that Pydantic passes through normalise_phone after reading it. So by the time any route code runs, every phone in the body is already 10 clean digits, or the request has been refused with a 422.

3. Whose number is this? owner_of

  1. It looks only at phone_1. A number that is only someone's contact number 2 belongs to nobody.
  2. This is the "across both tables" check the schema can't do. PersonSummary (line 129) is the small {kind, id, name} the API uses wherever it names a person.

4. Where the rule is enforced: _checked

Every create and edit of a Customer passes through _checked in customer_changes.py before anything is written. Its first lines are the Primary Number rule:

  1. A new Customer on a Standalone Referrer's number isn't a clash: it's that Referrer starting to borrow. Lesson 2 is about this.
  2. customer_id is None for a new Customer and the Customer's own id for an edit. Keeping your own number on an edit is fine; anyone else's is refused with 409 by _number_taken (line 70): "Contact number 1 … already belongs to Customer …" (or "Referrer …").

5. Contact number 2: a warning, never a block

load_customer (line 262) puts this list on the Customer's page as shares_phone_with. It only reads; nothing is refused because of it.

Nuances

(a) The same name with another number

Predict: the Lender adds a second "Meera Sharma" with contact number 1 9999911111. Refused or saved?

204: it would save. Nothing looks at the name. The same name with a different number is a different person (ADR 0005; test_primary_number.py::test_the_same_name_with_a_different_number_is_a_different_customer). The search and the Customers list show both, each with their number, so the Lender can tell them apart.

(b) Someone else's family phone as contact number 1

Predict: Rohan Sharma, Meera's son, is added with the family phone 9810099999 as his contact number 1. It's already Meera's and Sunita's contact number 2. Refused?

204: it would save. owner_of only looks at phone_1, and 9810099999 is nobody's phone_1. Once saved, it would be Rohan's Primary Number: the next person to type it as contact number 1 would get the 409. The same Rohan with 9810099999 as his contact number 2 also saves, and just joins Meera's and Sunita's warning list.

(e) Search: digits mean a phone, anything else a name

GET /api/search?q=… (line 376) finds Customers and Standalone Referrers together. phone_fragment (line 352) decides how to read the query: if it holds only digits, spaces, +, brackets and dashes, and at least 3 digits, it's part of a phone number, matched against both of a Customer's numbers and a Referrer's phone. Otherwise it's part of a name, matched ignoring case.

The last row surprises people. The +91 is only dropped from a complete number, because only then can normalise_phone tell a country code from the start of the number. A partial number typed with +91 keeps the 91 and finds nothing.

Trap #19: the glossary's Avoid words are kept by convention only. No linter or test stops you writing "borrower", "reference" or "customer ID". The people words are where it slips most: say Customer, not "borrower" or "client"; Referrer, not "reference"; Primary Number, not "customer ID" or "main phone". A Customer's id is a database key nobody outside the code sees; a Primary Number is how the Lender knows someone. Mixing the two words up in an issue or a variable name is how bugs like "look the customer up by ID" get written (trap #19, owned here).

Quiz

Which line stops a Customer being saved with a Standalone Referrer's number as contact number 1, on an edit?

The two unique=True columns are in different tables, so the database never compares them. normalise_phone only cleans the number. _checked asks owner_of, which looks in both tables, and refuses with 409 at line 184.

A new Customer gives 9810099999 as contact number 2. What happens?

Contact number 2 identifies nobody (ADR 0005). It's saved, and the new Customer, Meera and Sunita each list the others in shares_phone_with.

The Lender has typed "98100" into the Customer form's contact number 1. What does /people/by-phone answer?

The route catches normalise_phone's ValueError and answers null. It never matches a part of a number; that's what search is for.
